# SOP

## Phase 1 -- 確認報告與模式

1. `READ` 使用者指定的代號或路徑與使用者提供的驗證結果，列出 `specs/bugs/` 底下各代號目錄、其中的 `assessment.md`、`fix.md`、`test.md` 與 `test.md` 的結果欄位，並執行 `git status --short`，建立「候選清單」與「變更基準」。
2. `THINK` 決定「實測目錄」：使用者有指定時用 `specs/bugs/<代號>/`；沒有指定而且提供了驗證結果時，用「候選清單」中唯一一個 `test.md` 結果為「待使用者驗證」的目錄；都沒有時，用「候選清單」中唯一一個有 `assessment.md`、沒有 `test.md` 的目錄；把「實測目錄」中的 `assessment.md` 記為「評估報告」，`fix.md` 記為「修正報告」，`test.md` 記為「實測報告路徑」。
3. `CHECK` 「評估報告」不存在時，請使用者先執行 `bug-assess` 並停止；使用者沒有指定且有多個目錄符合時，列出這些目錄請使用者指定並停止；使用者提供了驗證結果時，「實測報告路徑」的結果為「待使用者驗證」則進入 Phase 4，不是則回報目前的結果並停止。
4. `READ` 「評估報告」全文與存在時的「修正報告」全文，建立「實測契約」：判定、核准狀態、完整預期行為（每項的量測方式與通過標準）、重現步驟、要補的測試、轉回 SDD 流程的項目，以及修正報告的狀態、修改的檔案、新增或修改的測試與本機驗證的命令。
5. `THINK` 依「實測契約」決定「模式」：「修正報告」存在且狀態為「已套用」時為修正後實測；「修正報告」不存在且判定為「待重現」時為修正前實測；其他情況沒有模式。
6. `CHECK` 沒有模式時，不修改任何檔案，回報原因與下一步並停止：修正報告狀態為「部分套用」或「未套用」時接 `bug-assess`；修正報告不存在且判定為「成立」時，已核准接 `bug-fix`，未核准接 `bug-assess`；判定為「不成立」或「意圖改變」時說明不需要實測。
7. `WRITE` 「實測報告路徑」已存在時，詢問使用者是否覆寫。
8. `CHECK` 「實測報告路徑」已存在時檢查使用者回覆：同意覆寫時繼續；拒絕或未回覆時不修改任何檔案並停止。

完成條件：已取得「變更基準」、「實測契約」、「模式」與尚未被占用或已同意覆寫的「實測報告路徑」；或已依使用者提供的驗證結果進入 Phase 4。

## Phase 2 -- 實測

1. `THINK` 依「實測契約」與「模式」寫出「實測計畫」：修正前版本（修正前實測時為工作目錄；修正後實測時，修正報告修改的檔案在「變更基準」中有未 commit 的修改則用 HEAD，沒有則用最後修改這些檔案的 commit 的父 commit）、修正後版本（工作目錄）、要啟動的服務、瀏覽器與寬度、要寫的量測腳本，以及每個版本要執行的檢查：完整預期行為的每一項、重現步驟、要補的測試，修正後實測時再加上修正報告本機驗證的命令；需要對外網路或會刪除、覆寫既有資料的命令不執行，記為略過。
2. `WRITE` 依「實測計畫」準備環境：修正後實測時用 `git worktree add` 在系統暫存目錄取出修正前版本，依賴套件用符號連結指向工作目錄，不重新安裝；需要量測腳本時寫在「實測目錄」，以參數接收應用程式路徑與網址，不寫死絕對路徑；啟動「實測計畫」列出的服務。
3. `READ` 判定實測結果時，讀取 `rules/實測結果-格式規範.md` 的所有 Rule，建立「實測結果檢查清單」。
4. `DELEGATE` 依「實測計畫」與「實測結果檢查清單」在各版本執行每項檢查，記錄命令、版本、結果、說明與輸出摘錄，建立「實測紀錄」；修正後失敗的檢查也在修正前版本執行；無法執行的檢查記錄原因後繼續；從本步驟到實測報告寫入前，不向使用者提問。
5. `WRITE` 停止準備環境時啟動的服務，用 `git worktree remove` 移除準備環境時建立的 worktree。

完成條件：「實測計畫」的每項檢查在「實測紀錄」都有結果；準備環境時啟動的服務已停止，建立的 worktree 已移除。

## Phase 3 -- 實測報告與回報

1. `READ` `templates/test.md` 與 `templates/test.example.md`，建立「實測報告樣板組」。
2. `WRITE` 依「實測報告樣板組」、「實測結果檢查清單」、「實測契約」、「實測計畫」與「實測紀錄」，把實測報告寫入「實測報告路徑」；使用者驗證段：結果為「待使用者驗證」時，每個驗證項目對應完整預期行為的編號，操作是一般使用者不用工具就能做的動作，通過標準用眼睛就能判斷，最後一項確認使用者原本回報的現象已消失，不列轉回 SDD 流程的項目，驗證日期與每項的結果寫「待使用者驗證」；其他結果時表格寫一列「無」，驗證日期寫「不適用」。
3. `CHECK` 逐條驗證「實測結果檢查清單」；確認實測報告的標題、開頭欄位與表格欄位和「實測報告樣板組」一致，沒有殘留 `{{`，完整預期行為實測表列出「實測契約」的每一項完整預期行為；確認量測腳本沒有寫死絕對路徑；執行 `git status --short` 和「變更基準」比對，確認本 Skill 造成的變更只有「實測目錄」中的實測報告與量測腳本，而且沒有 commit；執行 `git worktree list`，確認沒有留下 Phase 2 建立的 worktree。實測報告或量測腳本未通過時返回步驟 2；有其他由本 Skill 造成的變更（包含測試產生的暫存檔）或留下的 worktree 時進入步驟 4；全部通過時進入步驟 5。
4. `WRITE` 還原步驟 3 找到的其他變更，移除留下的 worktree，然後返回步驟 3。
5. `WRITE` 向使用者回報「實測報告路徑」、模式、結果、主要數值與剩餘風險。結果為「待使用者驗證」時，列出使用者驗證段的項目，請使用者操作後回覆每一項的結果。其他結果時給出下一步並結束：「已重現」或「未重現」時，以實測報告為新證據重新執行 `bug-assess`；「部分」時寫出要補齊的條件，補齊後重新執行 `bug-test`；「失敗」時接 `bug-assess`。

完成條件：實測報告已寫入「實測報告路徑」並通過步驟 3 的檢查；已向使用者回報結果，結果為「待使用者驗證」時已請使用者回覆驗證結果。

## Phase 4 -- 記錄使用者驗證

1. `READ` 「實測報告路徑」全文與使用者的驗證回覆，建立「驗證前報告」與「驗證項目」。
2. `CHECK` 使用者沒有回覆任何驗證項目時，結果維持「待使用者驗證」並停止；有回覆時進入步驟 3。
3. `WRITE` 只修改「實測報告路徑」的使用者驗證段與結果欄位：每項的「你的結果」寫使用者回覆的內容，沒有回覆的項目維持「待使用者驗證」；驗證日期寫收到回覆的日期；全部項目通過時結果寫「使用者已驗證（日期）」，任一項不通過時寫「使用者驗證未通過」，其他情況結果維持「待使用者驗證」。
4. `CHECK` 和「驗證前報告」比對，確認只有使用者驗證段與結果欄位改變，結果欄位與每項「你的結果」都來自使用者回覆；未通過時返回步驟 3。
