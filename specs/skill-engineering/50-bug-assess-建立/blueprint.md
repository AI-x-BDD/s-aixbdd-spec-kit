````markdown
name: bug-assess
description: （未驗證）收到錯誤回報、要在修正前評估時使用：讀取回報、spec、ui/plan、雛形、程式與測試，不啟動系統，寫出症狀、完整預期行為與量測方式、重現步驟、可疑程式路徑、根本原因假設、判定（成立／待重現／不成立／意圖改變）、嚴重度與修法；要改變已同意意圖的項目轉回 SDD 流程，待確認問題委派 clarify 問完後，再請使用者核准修法，寫成 specs/bugs/ 底下各代號目錄中的 assessment.md。觸發關鍵字：bug-assess、錯誤評估、bug 評估、assessment.md、修 bug 前先評估、評估錯誤回報。分流：依已核准的 assessment.md 修正改用 bug-fix；修正前後的實測改用 bug-test；要改變已同意的意圖時改用 s-specify、ui-plan 等處理 Skill；只想除錯、不產出評估報告時改用 diagnose。

# SOP

## Phase 1 -- 收斂回報與代號

1. `READ` 使用者的錯誤回報與附帶的路徑，並執行 `git status --short`，建立「回報內容」與「變更基準」。
2. `CHECK` 「回報內容」沒有描述任何症狀時，請使用者補充症狀並停止執行。
3. `THINK` 依「回報內容」擬定代號（只用小寫英文、數字與連字號，以 2～5 個英文單字描述症狀），把 `specs/bugs/<代號>/assessment.md` 記為「報告路徑」。
4. `CHECK` 「報告路徑」已存在時，詢問使用者要覆寫還是改用新代號，依回覆更新「報告路徑」；使用者未回覆時停止執行。

完成條件：已取得「回報內容」、「變更基準」與尚未被占用或已同意覆寫的「報告路徑」。

## Phase 2 -- 調查與判定

1. `READ` 依「回報內容」找出相關的 spec 目錄（`specs/[0-9][0-9][0-9]-*/`），讀取其中的 `spec.md`、`ui/plan.md`、雛形 HTML 與和症狀相關的其他 Planner 產出；以 `grep -rn` 搜尋症狀相關的文字、元件與 API，讀取相關程式與測試；不啟動系統，不執行會改變檔案或資料的命令，建立「調查證據」。
2. `READ` 列預期行為時，讀取 `rules/預期行為-格式規範.md` 的所有 Rule，建立「預期行為檢查清單」。
3. `THINK` 依「調查證據」與「預期行為檢查清單」，判斷問題類型，寫出症狀、完整預期行為（每項的目前、量測方式與通過標準）與重現步驟。
4. `THINK` 依「調查證據」寫出可疑程式路徑（`file:line`）與根本原因假設，寫明信心與沒有實測的部分；無法從證據確認的事項列為「待確認問題」，不猜測。
5. `READ` 判定時，讀取 `rules/判定與分流-格式規範.md` 的所有 Rule，建立「判定檢查清單」。
6. `THINK` 依「調查證據」與「判定檢查清單」，把每個要改的事分流為缺陷或意圖改變，決定判定、嚴重度與嚴重度理由，寫出修法首選、替代做法、要改的檔案、要補的測試、轉回 SDD 流程的項目與風險。

完成條件：報告各段落的內容都已決定，「待確認問題」已列出。

## Phase 3 -- 初稿與澄清

1. `READ` `templates/assessment.md` 與 `templates/assessment.example.md`，建立「評估報告樣板組」。
2. `WRITE` 依「評估報告樣板組」把初稿寫入「報告路徑」：判定為成立時，核准狀態與核准段各欄寫「待核准」，其他判定寫「不適用」；每個「待確認問題」在澄清紀錄寫一列，使用者回答與寫回位置寫「待回答」，沒有待確認問題時寫一列「無」。
3. `CHECK` 確認報告的標題、開頭欄位與表格欄位和「評估報告樣板組」一致，沒有殘留 `{{`；逐條驗證「預期行為檢查清單」與「判定檢查清單」；逐一開啟可疑程式路徑，確認每個 `file:line` 存在；未通過時修正報告後重新檢查。
4. `CHECK` 澄清紀錄沒有「待回答」時進入 Phase 4；有「待回答」時進入步驟 5。
5. `DELEGATE` 委派 `clarify` Skill（無法以 Skill 工具呼叫時，讀取 `clarify` 的 `SKILL.md` 並依其 SOP 執行），以澄清紀錄中「待回答」的問題為優先提問面向、每輪 3～5 題（不足 3 題時全部提問）、不要求詳記問答紀錄，取得使用者回答。
6. `WRITE` 把回答寫入澄清紀錄的「使用者回答」與「寫回位置」，依回答修改受影響的段落（判定、預期行為、修法、轉回項目等）；回答帶出新的待確認問題時，加入澄清紀錄並寫「待回答」；完成後返回步驟 3。

完成條件：報告通過步驟 3 的檢查，澄清紀錄沒有「待回答」。

## Phase 4 -- 核准與回報

1. `CHECK` 核准狀態為「不適用」時進入步驟 4；為「待核准」時進入步驟 2。
2. `WRITE` 向使用者展示判定、嚴重度、修法首選的每一項、替代做法與轉回 SDD 流程的項目，請使用者指定要核准的修法項目。
3. `CHECK` 使用者回覆：核准時，把核准日期、核准的修法與不在本次修正範圍的項目寫入核准段，核准狀態改為「已核准（<日期>，核准<修法項目>）」；要求修改修法或提出新事實時，記入澄清紀錄後返回 Phase 2 步驟 3；拒絕或未回覆時，核准狀態維持「待核准」。
4. `CHECK` 執行 `git status --short`，與「變更基準」比對，確認本 Skill 只新增或修改「報告路徑」所在的目錄；有其他由本 Skill 造成的變更時，還原這些變更。
5. `WRITE` 向使用者回報「報告路徑」、判定、嚴重度、核准狀態、轉回 SDD 流程的項目與處理 Skill，並給出下一步：已核准時接 `bug-fix`；有轉回項目時接該項目的處理 Skill；判定為待重現時，由 `bug-test` 做修正前實測後再重新執行 `bug-assess`；核准狀態為「待核准」時，說明核准後才能接 `bug-fix`。

完成條件：報告已寫入「報告路徑」且核准狀態反映使用者的回覆，工作目錄只有報告目錄的變更，已向使用者回報下一步。
````
