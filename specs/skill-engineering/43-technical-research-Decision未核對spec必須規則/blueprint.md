### 改寫後的 `rules/技術決策-格式規範.md` Rule 1 全文

````markdown
# Rule 1 - Decision 必須是單一確定、符合使用者限制與 spec 必須規則的方案

- 每個主題的 `Decision` 必須只採用一個方案；同一個需求點不得以「或」、「／」或括號並列兩個以上尚未決定的方案。
- 列舉同時採用的多個元件（例如「A 搭配 B」），或列舉不採用的項目（例如「不引入 X 或 Y」），不屬於並列未決方案。
- `Decision` 必須寫出採用的套件、API、資料結構或端點名稱，不得只寫方向，例如「使用適合的快取機制」。
- `Decision` 不得違反使用者在輸入中提出的技術限制。
- 使用者限制的字面有多種解讀，且 `Decision` 依其中一種解讀採用方案時，必須在 `Rationale` 寫出所採用的解讀。
- `Decision` 不得在任何適用情境下違反目標 spec 的必須／不得規則。比對前，必須列出「受影響的必須規則」：目標 spec 中，和 `Decision` 涉及同一個操作、狀態、實體或資料的 FR、NFR、SC、驗收情境、Edge Cases 與 Key Entities 的結構約束，以及 `Rationale` 寫為「滿足」的條目；不限本主題在「主題清單」列出的編號。
- 每條受影響的必須規則，必須列出 `Decision` 適用的情境：和其他操作同時發生、先後發生，以及需人工審核等分支。「其他操作」包括本次 spec 新增的操作，以及 spec 保留或沿用、會建立或改變該規則所依賴之狀態的既有操作；既有操作從既有 spec、程式與資料庫遷移找出。
- `Decision` 在任一情境下產生規則禁止的結果，或沒有產生規則要求的結果（包括規則指定的拒絕訊息與判斷順序），就是違反，必須改用能滿足規則的方案。
- 沒有候選方案能同時滿足受影響的必須規則，或要滿足規則必須先決定需求層面的問題（例如某個操作是否算規則的例外）時，不得自行決定，必須記為決策缺口，寫出規則的位置、衝突的情境，以及需要使用者決定的問題。
- 記為違反或決策缺口的每一項，必須指出目標 spec 中實際存在的條目；候選方案都滿足受影響的必須規則、只差在效能或維護等取捨時，不得記為規則衝突。

## Good Example

### Example 1

- 球場預約系統的「預約衝突」主題只採用一個方案，寫出具體的資料庫機制，且自架 PostgreSQL 符合使用者「不要用雲端服務」的限制。

```markdown
- **Decision**: 以 **PostgreSQL 16** 的 `EXCLUDE USING gist` 排除約束搭配 `tstzrange` 時段欄位，防止同一球場的預約時段重疊；後端以 **FastAPI** 在單一交易中寫入預約。
```

### Example 2

- 「停用球場的並發控制」主題列出受影響的必須規則與每個情境，包含上一個功能保留的會員報到；Decision 讓每個情境都滿足規則，並先比對預期狀態。

情境：

1. 目標 spec：
   - FR-005：管理員停用球場時，系統必須 (MUST) 取消該球場所有尚未開始的預約。
   - FR-006：球場有已報到的預約時，系統必須 (MUST) 拒絕停用。
   - FR-009：管理員送出時，球場狀態已被其他管理員變更（包含改成同一個狀態），系統必須 (MUST) 拒絕，並顯示「球場狀態已變更，請重新整理」。
   - FR-012：會員報到、候補遞補的現有行為保留不變。
2. 受影響的必須規則：FR-005、FR-006、FR-009。
3. 其他操作：新增預約、候補遞補（建立預約），會員報到（既有操作，把預約改成已報到）。
4. 情境：停用和新增預約同時；停用和候補遞補同時；停用和會員報到同時；另一位管理員先停用了同一個球場。
5. Decision：

```markdown
- **Decision**: 停用交易先以 `SELECT ... FOR UPDATE` 鎖定球場列，先比對送出時的預期狀態，不同就回 `COURT_STATUS_CHANGED`（FR-009 的訊息），再檢查已報到預約並取消尚未開始的預約；新增預約、候補遞補、會員報到都在各自交易開頭以 `SELECT ... FOR SHARE` 鎖定同一個球場列。
```

### Example 3

- 「demo seed 重設」主題沒有候選方案能同時滿足兩條必須規則，記為決策缺口，交給使用者決定。

情境：

1. 目標 spec：
   - FR-010：球場狀態變更紀錄不得 (MUST NOT) 刪除。
   - US2 驗收情境 4：執行 demo seed 後，資料回到初始狀態。
2. 候選方案：seed 以 `deleteMany` 清空後重建，會刪除紀錄，違反 FR-010；seed 只補資料不刪除，無法回到初始狀態，違反 US2 情境 4。
3. 決策缺口：`FR-010 與 US2 情境 4：demo seed 重設時，清空紀錄違反 FR-010，保留紀錄無法回到初始狀態；需決定 demo seed 重設是否算 FR-010 的例外。`

### Example 4

情境：

1. 候選方案：程序內 LRU 快取、Redis。兩者在每個情境都滿足 FR-003 與 SC-002。
2. Decision：採用程序內 LRU 快取，`Alternatives considered` 寫出 Redis 增加一個部署元件。
````

````markdown
# Rule 2 - Rationale 的依據必須可追溯

- 每個主題的 `Rationale` 必須至少有一條引用下列任一依據：使用者輸入中的技術限制、目標 spec 中的 FR／SC 等編號、專案原則文件中的條目、經 `clarify` 由使用者確認的決定。
````
