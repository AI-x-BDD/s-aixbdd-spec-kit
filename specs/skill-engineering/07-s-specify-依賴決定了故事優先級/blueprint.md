- 確認紀錄：使用者於 Phase 4 看過藍圖重點（刪除項目：Rule 2 第 1 條後半與標題的「與交付順序」），並聽取 E10 的白話說明後回覆「可以，開始施工」，同意工程藍圖、新增的既有驗收條件 E10 與施工工作項 W1～W3

## 1. 驗收條件

| 編號 | 驗收條件 | 來源 | 適用範圍 |
| ---- | -------- | ---- | -------- |
| E1 | 優先級依使用者價值排序：P1 是功能描述中使用者最想得到的核心體驗。每個故事的 `Why this priority`，排序理由只寫使用者價值；「本故事依賴其他故事」或「其他故事依賴本故事」都不作為排序理由 | 本次 | 通用 |
| E2 | 故事需要其他故事先提供的能力或資料時，`Why this priority` 在價值理由之後寫一句「實作前提：<前提>；不影響本故事優先級」；沒有這種前提的故事不寫這句 | 本次 | 通用 |
| E3 | 故事少了某項前置能力，它聲稱的核心體驗就無法成立時，該能力的最小版本寫進這個故事：故事敘述、驗收情境與 FR 都涵蓋它，而不是只靠另一個排在前面的故事提供 | 本次 | 通用 |
| E4 | 前置條件只是資料或狀態（例如題目已設定、菜單已有品項）時，寫在驗收情境的 `Given` 或 `Independent Test` 的準備步驟；`Given` 不預先完成該故事要驗收的成果 | 本次 | 通用 |
| E5 | 每個故事從使用者角度描述能得到的成果，不以技術工作作為故事；`Independent Test` 描述只實作該故事時的驗證方式與預期結果 | 既有 | 通用 |
| E6 | `Why this priority` 說明排序理由，不只重述優先級；優先級不只依功能描述中出現的順序決定 | 既有 | 通用 |
| E7 | 每條 FR 都有 `Then` 驗證它的驗收情境；故事專屬的 FR 由同一故事的驗收情境驗證 | 既有 | 通用 |
| E8 | 「需求缺口」不為空時，先委派 clarify；spec.md 寫入新編號的 `specs/<NNN>-<short-name>/`，不覆寫既有目錄，也不建立 git 分支；固定結構與樣板一致 | 既有 | 通用 |
| E9 | 完成回報包含 spec.md 路徑、是否進入 clarify、使用者故事與 FR／NFR 數量、全域需求、Assumptions 與下一步 | 既有 | 通用 |
| E10 | 推定需求、Assumptions 與 Out of Scope 的處理維持紀錄 06 驗收條件 E1～E8 的要求：AI 決定的值、未確認事項與推斷寫成推定需求並有推定引用，有來源的值不列推定，一般 Assumption 寫出預設內容，Out of Scope 標示來源 | 既有 | 通用 |

E10 是設計時補上的既有預期：SOP 的推定需求步驟與 FR 規則 Rule 6、spec 文件規則 Rule 4 都要追溯到某條驗收條件才能保留。根因報告寫的是「不受本次修改影響，不另列」，這裡改成明列，並在 S1、S2 以回歸檢查的方式驗收；請在確認藍圖時一併確認。

## 2. To-Be SOP

````markdown
---
name: s-specify
disable-model-invocation: true
description: 使用者要求把功能描述寫成 SDD 規格文件 spec.md 時使用：切分可獨立測試的使用者故事，把 FR／NFR 列管在所屬故事底下，跨故事的才放全域需求，並保留關鍵實體、可量測成果與假設；需求有高影響缺口時會先委派 clarify 訪談使用者。使用者提到 specify、寫規格、spec.md、需求規格、user story、FR／NFR 時使用。只需訪談釐清需求、不產出 spec.md 時改用 clarify；只做技術規劃（技術堆疊、架構、部署方式）時不使用此 Skill。
---

# SOP

## Phase 1 -- 對齊輸入與澄清需求

1. `READ` 使用者的功能描述，以及專案根目錄 `specs/` 下名稱符合 `<三位數編號>-<名稱>` 的目錄清單（以 `ls -d specs/[0-9][0-9][0-9]-*/` 取得；`specs/` 不存在或沒有符合的目錄時清單為空），建立「需求輸入」。
2. `CHECK` 使用者的功能描述為空或只有空白時，回覆使用者需要提供功能描述並停止執行，不委派 `clarify`，也不建立任何目錄或檔案。
3. `READ` `templates/spec.md` 與 `templates/spec.example.md`，載入骨架與範例，命名載入結果為「spec 樣板組」。
4. `THINK` 依「spec 樣板組」各段落需要的內容，盤點「需求輸入」中會改變使用者故事切分、需求歸戶、主要流程或正式驗收標準的缺漏、矛盾與歧義，建立「需求缺口」。
5. `DELEGATE` 「需求缺口」不為空時，委派 `clarify` Skill（無法以 Skill 工具呼叫時，讀取 `clarify` 的 `SKILL.md` 並依其 SOP 執行），以「需求缺口」為優先提問面向、不要求詳記問答紀錄，取得已確認決策、使用者補充與剩餘風險，建立「澄清結果」；「需求缺口」為空時略過本步驟。
6. `THINK` 合併「需求輸入」與「澄清結果」，建立「需求決策」；「澄清結果」的剩餘風險與未經使用者確認的推斷，列為「未確認事項」。

完成條件：「需求決策」已建立，「需求缺口」的每一項都已由使用者在 clarify 中決定或列入「未確認事項」，且尚未建立 spec.md；或功能描述為空，已停止執行。

## Phase 2 -- 重建需求骨架

1. `READ` 切分使用者故事時，讀取 `rules/使用者故事-格式規範.md` 的所有 Rule，建立「使用者故事檢查清單」。
2. `THINK` 依「需求決策」與已載入的「使用者故事檢查清單」，切出使用者故事，並為每個故事決定標題、敘述、優先級、優先級理由、獨立測試方式與驗收情境。
3. `CHECK` 依「需求決策」無法切出任何使用者故事時，向使用者說明無法切出的原因並停止執行，不建立 `specs/` 下的目錄與 spec.md。
4. `READ` 撰寫與歸屬需求時，讀取 `rules/功能與非功能需求-格式規範.md` 的所有 Rule，建立「需求歸屬檢查清單」。
5. `THINK` 依「需求決策」、「未確認事項」、已切出的使用者故事與已載入的「需求歸屬檢查清單」，寫出 FR 與 NFR，決定每條需求歸屬的使用者故事或全域需求並編號，並建立「推定需求」清單。
6. `CHECK` 逐條驗證「使用者故事檢查清單」與「需求歸屬檢查清單」；未通過時修正使用者故事或需求後重新驗證，最多 3 輪，第 3 輪仍未通過時停止修正，將未通過的 Rule 與所在的使用者故事或需求編號記為「未通過項」。

完成條件：每個使用者故事都有優先級、獨立測試方式與驗收情境，每條 FR／NFR 都已編號並歸屬到一個使用者故事或全域需求，且兩份檢查清單均已通過或未通過的項目已記為「未通過項」；或無法切出使用者故事，已停止執行。

## Phase 3 -- 產出 spec.md 與自檢

1. `THINK` 決定輸出目錄名稱 `<NNN>-<short-name>`：`<NNN>` 為「需求輸入」目錄清單中的最大編號加一，清單為空時為 `001`，不得使用或覆寫既有目錄；`<short-name>` 為 2 至 4 個小寫英文單字以連字號連接的功能簡稱。
2. `READ` 撰寫 spec.md 時，讀取 `rules/spec-文件-格式規範.md` 的所有 Rule，建立「spec 文件檢查清單」。
3. `WRITE` 依「spec 樣板組」與已載入的「spec 文件檢查清單」，以「需求決策」、Phase 2 的使用者故事與需求、「推定需求」、「未確認事項」及「澄清結果」，將 spec.md 寫入專案根目錄 `specs/<NNN>-<short-name>/spec.md`；內文使用繁體中文，`Feature Branch` 填入 `<NNN>-<short-name>`，`Created` 填入執行當日日期，不建立 git 分支。
4. `CHECK` 逐條驗證「spec 文件檢查清單」，並逐一比對 spec.md 與「spec 樣板組」的段落順序與各段落的條目格式，條目標題後的括號標記也必須與樣板相同；未通過時修正 spec.md 後重新驗證，最多 3 輪，第 3 輪仍未通過時停止修正，將未通過的 Rule 與 spec.md 中的位置加入「未通過項」。
5. `WRITE` 向使用者回報 spec.md 路徑、本次是否進入 clarify、使用者故事與 FR／NFR 數量、全域需求與 Assumptions；「需求輸入」含技術偏好（如框架、資料庫、部署方式）時，一併列出並說明這些內容留待技術規劃階段提供；最後給出下一步：有「未通過項」時逐項列出並建議先處理，沒有時建議先審閱 Assumptions 與 Out of Scope，確認後進入技術規劃階段。

完成條件：spec.md 已寫入 `specs/<NNN>-<short-name>/`，「spec 文件檢查清單」已通過或未通過的項目已記為「未通過項」，且已向使用者回報。
````

設計說明：從驗收條件推導。

- E1、E2、E6 都是「怎麼排序、理由怎麼寫」，P2-2 依「使用者故事檢查清單」決定優先級與理由，P2-6 依同一份清單驗證，所以都放在故事規則 Rule 2。R1 是衝突類型，修法是刪除或改寫其中一方：Rule 2 第 1 條的「依賴者排在後面」改寫成「依賴不得作為排序理由」，依賴資訊改由 E2 的「實作前提」承接，只保留「依使用者價值」這一個排序來源。
- E3、E4 是「故事需要前置能力或資料時，怎麼讓它仍能獨立交付與驗證」，和 Rule 1「只實作該故事時，必須仍能展示並驗證其價值」是同一個主題，所以擴充 Rule 1。
- 範例三個故事的 `Why this priority` 以依賴當理由，與修改後的 Rule 2 矛盾，必須改寫。
- SOP 的每個步驟追溯結果都與 As-Is 相同，全文保留原文。

Rule 1 改為下列全文，Rule 2、3 由 W2 與現況決定：

````markdown
# Rule 1 - 使用者故事必須是可獨立交付與驗證的使用者價值

- 每個使用者故事必須從使用者角度描述一段使用者能得到的成果，不得以技術工作或內部步驟（例如「建立資料表」、「實作 API」）作為故事。
- 只實作該故事時，必須仍能展示並驗證其價值。
- 故事少了某項前置能力，它聲稱的核心體驗就無法成立時，必須把該能力的最小版本寫進這個故事，由故事敘述、驗收情境與 FR 涵蓋，不得只靠另一個故事提供。
- 前置條件只是資料或狀態時，必須寫在驗收情境的 `Given` 或 `Independent Test` 的準備步驟；`Given` 不得預先完成該故事要驗收的成果。
- `Independent Test` 必須描述只實作該故事時的驗證方式，以及預期觀察到的結果。

## Good Example

### Example 1

- 故事描述使用者得到的瀏覽成果，獨立測試只需要這個故事就能執行並觀察結果。

```markdown
### User Story 2 - 相簿內照片平鋪式預覽 (Priority: P2)

使用者在主頁面檢視任一相簿時，相簿內的照片以平鋪式網格呈現縮圖，不需逐一點開即可瀏覽。

**Independent Test**: 開啟一個包含多張照片的相簿；驗證照片以整齊的網格排列，且會依視窗寬度調整每列張數。
```

### Example 2

- 即時協作是核心體驗，少了「加入同一張白板」就無法成立，所以以分享連結加入的最小版本寫進故事與驗收情境；白板上已有的便利貼只是狀態，寫在 `Given`。

```markdown
### User Story 1 - 與同事在同一張白板上即時協作 (Priority: P1)

使用者把白板的分享連結傳給同事，同事開啟連結後加入同一張白板；任一方新增或移動便利貼時，另一方立即看到變化。

**Independent Test**: 準備一張已有一張便利貼的白板；使用者 A 傳出分享連結，使用者 B 開啟後加入，A 新增一張便利貼；驗證 B 的畫面立即出現這張便利貼。

**Acceptance Scenarios**:

1. **Given** 使用者 A 開著一張白板，**When** 使用者 B 開啟 A 傳來的分享連結，**Then** B 進入同一張白板並看到 A 的游標。
2. **Given** A 與 B 在同一張白板上，且白板已有一張「待辦」便利貼，**When** A 把「待辦」便利貼拖到右側，**Then** B 的畫面上「待辦」便利貼立即移到右側。
```
````
