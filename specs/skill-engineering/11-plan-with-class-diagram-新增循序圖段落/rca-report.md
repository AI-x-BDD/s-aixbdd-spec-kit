## 1. 使用者回報的問題

提案檔只有類別圖，看不到本次變更範圍裡的類別怎麼互動。使用者要在類別圖下方加循序圖，呈現本次變更的重要情境流程。樣板組已經定稿成新格式，但 Skill 的 SOP 與規則還沒有涵蓋循序圖。

## 5. 根因

| 編號 | 位置 | 缺陷類型 | 說明與證據 | 反事實檢驗 |
| ---- | ---- | -------- | ---------- | ---------- |
| R1 | `plan-with-class-diagram`／`rules/類別圖提案-格式規範.md`／全檔（Rule 1～4） | 缺失 | 觀察：Rule 1～4 沒有循序圖的情境選擇、參與者與訊息要和類別圖一致，以及呼叫 `«new»` 的判定。推論：這些只能從範例推測，範例沒有涵蓋的情況（兩端都是新增類別的呼叫、已移除的呼叫）會由執行者自行決定（依據第 3 節 E13、E14 的觀察） | 假設 RuleFile 有這三項約束：P1-4 的檢查清單會包含它們，P1-7 寫出的情境、參與者、訊息與標記有規則可依，P1-8 能逐條檢查，E11～E14 可滿足 |
| R2 | `plan-with-class-diagram`／`SKILL.md`／Phase 1 P1-5、P1-8，Phase 3 P3-3 | 缺失 | 觀察：P1-5 的設計內容、P1-8 的渲染對象、P3-3 的核對對象都只寫類別圖。推論：即使規則齊備，設計步驟也不會先決定情境，渲染不會檢查循序圖，開發也不會核對呼叫流程（依據上述觀察） | 假設這三個步驟都涵蓋循序圖：P1-5 會先決定情境與流程，P1-8 會渲染並檢查每張循序圖，P3-3 會核對呼叫流程，E6、E11、E15 可滿足 |

## 6. 被排除的假設

| 假設 | 缺陷類型 | 排除依據 |
| ---- | -------- | -------- |
| H1：樣板範例已經示範循序圖，不需要規則 | 非 Skill 問題 | 觀察：範例的 `«new»` 呼叫，發送端都是修改類別或呼叫端；範例中沒有兩端都是新增類別的呼叫，也沒有說明為何不畫 `LegacyOrderDao.insert`。推論：範例無法讓執行者判斷這兩種情況（依據上述觀察） |
| H2：樣板在設計步驟之後才載入（未載入），只要把 P1-6 移到 P1-5 之前就能解決 | 未載入 | 推論：就算先載入樣板，P1-5 的步驟文字仍然只要求設計類別圖相關內容，P1-8、P3-3 也仍然不檢查循序圖；R2 的反事實檢驗不需要調整載入順序就能滿足 E11（依據 R2 的觀察） |
| H3：循序圖需要另開一份 RuleFile | 衝突 | 推論：參與者與訊息必須對應類別圖成員，`«new»` 判定也比照 Rule 2，循序圖約束和類別圖規則互相引用；分成兩份檔案時，P1-4 還得多讀一份，約束也會散在兩處（依據 R1 的觀察）。存放位置屬於重新設計，這裡只確認根因不是「缺少檔案」 |
