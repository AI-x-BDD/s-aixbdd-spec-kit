## 2. To-Be SOP

````markdown
---
name: s-specify
disable-model-invocation: true
description: 使用者要求把功能描述寫成 SDD 規格文件 spec.md 時使用：切分可獨立測試的使用者故事，把 FR／NFR 列管在所屬故事底下，跨故事的才放全域需求，並保留關鍵實體、可量測成果與假設；需求有高影響缺口時會先委派 clarify 訪談使用者。使用者提到 specify、寫規格、spec.md、需求規格、user story、FR／NFR 時使用。只需訪談釐清需求、不產出 spec.md 時改用 clarify；只做技術規劃（技術堆疊、架構、部署方式）時不使用此 Skill。
---

# SOP

## Phase 1 -- 對齊輸入與澄清需求

1. `READ` 使用者的功能描述，以及專案根目錄 `specs/` 下名稱符合 `<三位數編號>-<名稱>` 的目錄清單（以 `ls -d specs/[0-9][0-9][0-9]-*/` 取得；`specs/` 不存在或沒有符合的目錄時清單為空），建立「需求輸入」。
2. `CHECK` 使用者的功能描述為空或只有空白時，回覆使用者需要提供功能描述並停止執行，不委派 `clarify`，也不建立任何目錄或檔案。
3. `READ` `templates/spec.md` 與 `templates/spec.example.md`，載入骨架與範例，命名載入結果為「spec 樣板組」。
4. `THINK` 依「spec 樣板組」各段落需要的內容，盤點「需求輸入」中會改變使用者故事切分、需求歸戶、主要流程或正式驗收標準的缺漏、矛盾與歧義，建立「需求缺口」。
5. `DELEGATE` 「需求缺口」不為空時，委派 `clarify` Skill（無法以 Skill 工具呼叫時，讀取 `clarify` 的 `SKILL.md` 並依其 SOP 執行），以「需求缺口」為優先提問面向、不要求詳記問答紀錄，取得已確認決策、使用者補充與剩餘風險，建立「澄清結果」；「需求缺口」為空時略過本步驟。
6. `THINK` 合併「需求輸入」與「澄清結果」，建立「需求決策」；「澄清結果」的剩餘風險與未經使用者確認的推斷，列為「待寫入假設」。

完成條件：「需求決策」已建立，「需求缺口」的每一項都已由使用者在 clarify 中決定或列入「待寫入假設」，且尚未建立 spec.md；或功能描述為空，已停止執行。

## Phase 2 -- 重建需求骨架

1. `READ` 切分使用者故事時，讀取 `rules/使用者故事-格式規範.md` 的所有 Rule，建立「使用者故事檢查清單」。
2. `THINK` 依「需求決策」與已載入的「使用者故事檢查清單」，切出使用者故事，並為每個故事決定標題、敘述、優先級、優先級理由、獨立測試方式與驗收情境。
3. `CHECK` 依「需求決策」無法切出任何使用者故事時，向使用者說明無法切出的原因並停止執行，不建立 `specs/` 下的目錄與 spec.md。
4. `READ` 撰寫與歸屬需求時，讀取 `rules/功能與非功能需求-格式規範.md` 的所有 Rule，建立「需求歸屬檢查清單」。
5. `THINK` 依「需求決策」、已切出的使用者故事與已載入的「需求歸屬檢查清單」，寫出 FR 與 NFR，決定每條需求歸屬的使用者故事或全域需求，並編號。
6. `CHECK` 逐條驗證「使用者故事檢查清單」與「需求歸屬檢查清單」；未通過時修正使用者故事或需求後重新驗證，最多 3 輪，第 3 輪仍未通過時停止修正，將未通過的 Rule 與所在的使用者故事或需求編號記為「未通過項」。

完成條件：每個使用者故事都有優先級、獨立測試方式與驗收情境，每條 FR／NFR 都已編號並歸屬到一個使用者故事或全域需求，且兩份檢查清單均已通過或未通過的項目已記為「未通過項」；或無法切出使用者故事，已停止執行。

## Phase 3 -- 產出 spec.md 與自檢

1. `THINK` 決定輸出目錄名稱 `<NNN>-<short-name>`：`<NNN>` 為「需求輸入」目錄清單中的最大編號加一，清單為空時為 `001`，不得使用或覆寫既有目錄；`<short-name>` 為 2 至 4 個小寫英文單字以連字號連接的功能簡稱。
2. `READ` 撰寫 spec.md 時，讀取 `rules/spec-文件-格式規範.md` 的所有 Rule，建立「spec 文件檢查清單」。
3. `WRITE` 依「spec 樣板組」與已載入的「spec 文件檢查清單」，以「需求決策」、Phase 2 的使用者故事與需求、「待寫入假設」及「澄清結果」，將 spec.md 寫入專案根目錄 `specs/<NNN>-<short-name>/spec.md`；內文使用繁體中文，`Feature Branch` 填入 `<NNN>-<short-name>`，`Created` 填入執行當日日期，不建立 git 分支。
4. `CHECK` 逐條驗證「spec 文件檢查清單」，並確認 spec.md 的固定結構與「spec 樣板組」一致；未通過時修正 spec.md 後重新驗證，最多 3 輪，第 3 輪仍未通過時停止修正，將未通過的 Rule 與 spec.md 中的位置加入「未通過項」。
5. `WRITE` 向使用者回報 spec.md 路徑、本次是否進入 clarify、使用者故事與 FR／NFR 數量、全域需求與 Assumptions；「需求輸入」含技術偏好（如框架、資料庫、部署方式）時，一併列出並說明這些內容留待技術規劃階段提供；最後給出下一步：有「未通過項」時逐項列出並建議先處理，沒有時建議先審閱 Assumptions 與 Out of Scope，確認後進入技術規劃階段。

完成條件：spec.md 已寫入 `specs/<NNN>-<short-name>/`，「spec 文件檢查清單」已通過或未通過的項目已記為「未通過項」，且已向使用者回報。
````

## 4. 淨增減

| 項目 | As-Is | To-Be | 增減 |
| ---- | ----- | ----- | ---- |
| Phase | 3 | 3 | 0 |
| 步驟 | 15 | 17 | +2 |
| RuleFile | 3 | 3 | 0 |
| Rule | 12 | 14 | +2 |
| 樣板組 | 1 | 1 | 0 |
| 腳本 | 0 | 0 | 0 |

增加理由：

- 步驟 +2：P1-2 與 P2-3 是 R1（流程缺陷）要求的停止出口。這兩個是分支，依約束分配規則必須留在 SOP 流程；既有步驟中，P1-1 是 `READ`、P2-2 是 `THINK`，把分支塞進去會讓一個步驟同時做兩件事，因此新增獨立的 `CHECK`。
- Rule +2：R3、R4 是缺失類型，沒有可刪除或改寫的既有內容能表達。FR 與驗收情境的對應屬於 FR 主題，擴充既有 RuleFile；Out of Scope 屬於 spec 文件格式主題，擴充既有 RuleFile。`rules/使用者故事-格式規範.md` Rule 3 雖然規範驗收情境，但它在 P2-2 載入，當時 FR 還不存在，無法檢查對應。
- 內容刪改：刪除 Rule 4 Good Example 與範例 Assumptions 中的範圍排除；改寫 Rule 4 第一條，與新增的 Rule 6 分工。

#### W2：`rules/功能與非功能需求-格式規範.md` 新增 Rule 5

- 標題：每條 FR 都必須有驗證它的驗收情境。
- 條列：
  - 每條 FR 必須至少有一條驗收情境，其 `Then` 驗證該 FR 規定的行為；只在 `Given` 中預設該行為已發生，不算驗證。
  - 列在使用者故事底下的 FR，必須由同一個故事的驗收情境驗證；全域 FR 可由任一故事的驗收情境驗證。
  - 找不到驗證它的驗收情境時，必須在所屬故事補上驗收情境，不得為了通過檢查而刪除或弱化該 FR。
  - NFR 不適用本 Rule。
- Good Example：照片相簿情境，FR-002「刪除仍含照片的相簿時先顯示含照片數量的確認提示」，同一故事有一條 `Then` 為「顯示確認提示並標明相簿內照片數量」的驗收情境。
- Bad Example：同一情境，FR-002 只出現在某條情境的 `Given`（「使用者已刪除一個相簿」），沒有任何 `Then` 驗證確認提示。
- Rule 1～4 保留原文。

#### W3：`rules/spec-文件-格式規範.md` 修改 Rule 4、新增 Rule 6

- Rule 4 第一條改為：「待寫入假設」中屬於範圍排除的項目，依 Rule 6 寫入 Out of Scope；其餘每一項必須寫成一條 Assumption，並寫出本次採用的預設內容。
- Rule 4 Good Example 改為只寫預設內容，不含範圍排除，例如「**個人單機／本地優先使用情境**：預設本應用程式為個人照片整理工具，由單一使用者直接操作管理。」
- Rule 4 其餘條列、Bad Example 保留原文。
- 新增 Rule 6，標題：Out of Scope 必須列出本次不做的範圍並標示來源。
- Rule 6 條列：
  - `## Out of Scope` 必須至少列出一項，每項描述一個本次不提供的功能或範圍，不得寫成預設值或假設。
  - 每一項必須在標題後以括號標示來源：使用者在功能描述或 clarify 中明確排除的，標「使用者決定」；其餘由 AI 推定排除的，標「推定」。
  - 同一項排除內容只能出現在 Out of Scope，不得同時寫在 Assumptions。
- Rule 6 Good Example：照片相簿情境，「**多人帳號與權限管理**（推定）：第一版不提供帳號登入、多人共用相簿與權限設定。」Assumptions 中只保留「預設為個人照片整理工具」。
- Rule 6 Bad Example：同一個排除同時寫在 Assumptions 與 Out of Scope，且沒有標示來源。
- Rule 1、2、3、5 保留原文。
