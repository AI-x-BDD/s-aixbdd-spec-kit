# 根因報告：skill-engineering－驗收子代理未指定模型

- 紀錄目錄：`specs/skill-engineering/17-skill-engineering-驗收子代理未指定模型/`
- 問題證據：本次對話上下文（建立 `system-analysis` 時，使用者於 Phase 4 回覆「驗收用 Sonnet」；使用者詢問「如果我是用 Codex 來執行這個 Skill 會怎麼做」；與 Codex pane `codexmate` 兩輪討論的查證結果）；`.agents/skills/skill-engineering/SKILL.md` Phase 5 步驟 10–14；`specs/skill-engineering/16-system-analysis-建立/blueprint.md` 的確認紀錄與驗收結果

## 1. 使用者回報的問題

課程建議「要測試的話，用笨一點的模型」，使用者在建立 `system-analysis` 時同意驗收子代理改用 Sonnet，但這只寫在當次藍圖的確認紀錄，`skill-engineering` 本身沒有規定驗收子代理用哪個模型。使用者同時使用 Claude Code 與 Codex，希望以 Codex 執行 `skill-engineering` 時，驗收子代理也會改用定位較低的中階模型，而不是沿用平台預設。

## 2. 驗收條件

| 編號 | 驗收條件 | 來源 | 適用範圍 | 驗收情境 |
| ---- | -------- | ---- | -------- | -------- |

| E2 | 平台支援指定推理強度時，啟動驗收子代理時一併顯式指定推理強度；不支援時在驗收結果記為「不適用」 | 本次 | 通用 | S1、S2 |
| E3 | 選定的模型在該平台不可用時，執行者向使用者回報並請使用者選定模型，在使用者回覆前不啟動驗收子代理，也不自動改用其他模型 | 本次 | 通用 | S3 |

## 5. 根因

| 編號 | 位置 | 缺陷類型 | 說明與證據 | 反事實檢驗 |
| ---- | ---- | -------- | ---------- | ---------- |
| R1 | `skill-engineering`／`SKILL.md`／Phase 5 步驟 12 | 缺失 | 觀察：步驟 12 只規定子代理不帶本次分析脈絡與要提供的輸入，沒有規定模型、推理強度，也沒有模型不可用時的處理；其他 RuleFile 與樣板也沒有（`rules/` 中唯一提到「模型」的是根因分析 Rule 3 的「非 Skill 問題」定義）。推論：沒有使用者額外指定時，Claude Code 會用 Agent 工具的預設模型、Codex 會用 config 的子代理預設（依據步驟 12 與 Codex 查證的觀察）。 | 假設步驟 12 要求顯式指定較低定位的中階模型與推理強度、不可用時回報：Claude Code 與 Codex 都會選定並指定模型，E1–E3 可滿足；若同時要求記錄實際模型與執行方式，E4 可滿足；E6 的既有要求不變。 |

## 6. 被排除的假設

| 假設 | 缺陷類型 | 排除依據 |
| ---- | -------- | -------- |
| H2：選模是使用者每次的偏好，不需寫進 Skill | 非 Skill 問題 | 觀察：使用者明確要求以 Claude Code 與 Codex 執行時都採用同一原則，且依據是課程的通用建議，屬於每次驗收都適用的預期 |
| H3：呼叫 `skill-engineering` 的 Skill 應在委派時傳入模型 | 交接缺陷 | 觀察：`artifact-to-skill-engineering` Phase 4 步驟 2 與 `user-verify-skill` Phase 3 步驟 7 的委派內容都不涉及驗收執行方式；驗收子代理由 `skill-engineering` Phase 5 步驟 12 自行啟動 |
| H4：應寫成 RuleFile 讓 AI 依正反例判斷 | 載體過弱 | 觀察：目前沒有任何部位表達此預期，不是「已有要求但載體太弱」；存放位置於設計階段依約束分配規則決定 |
