# SOP

## Phase 1 -- 收斂規劃輸入

1. `READ` 使用者需求或委派內容，以及專案根目錄下符合 `specs/<三位數編號>-<名稱>/spec.md` 的檔案清單（以 `ls specs/[0-9][0-9][0-9]-*/spec.md` 取得；沒有符合的檔案時清單為空），建立「規劃輸入」。
2. `THINK` 決定「目標 spec」：使用者或委派內容指定 spec.md 路徑或功能目錄時使用該 spec，未指定且清單只有一份時使用該份，其餘情況視為未決定。
3. `CHECK` 「目標 spec」不存在時，告知使用者需要先產出 spec.md（可使用 `s-specify`）並停止執行；清單有多份且未指定時，列出清單請使用者指定並停止執行。
4. `READ` 「目標 spec」全文，以及同目錄的 `plan.md`、`techstack.md`、`research.md` 與 `ui/` 下的既有檔案清單（不存在的略過），加入「規劃輸入」。
5. `READ` 專案根目錄的 `.agents/constitution/shared.md`、`.agents/constitution/skills/ui-plan/ui-plan.md` 與 `.agents/constitution/skills/ui-plan/ui-page.md`（不存在的略過），建立「憲法檢查清單」；鎖定項目不受憲法覆寫：`ui/plan.md` 的章節編號、第 1 節只列負責介面、第 3.1 節頁面清單以反引號標出 HTML 檔名且第一列為 `index.html`、第 3.2 節流程節點代號不得與介面編號相同、第 4 節各頁狀態；每個 HTML 的 `const STATES = [ … ];` 雛形狀態面板、不引用外部資源、只連到頁面清單內的頁面。
6. `CHECK` 同目錄沒有 `plan.md` 時，告知使用者需要先做系統分析（可使用 `system-analysis`）並停止執行。
7. `THINK` 決定「負責介面」：委派內容指定介面編號時使用這些編號，否則使用 `plan.md`「系統介面盤點」表中端點類型為前端的所有介面；每個介面記下 plan.md 中的編號、名稱與需求依據。
8. `CHECK` 「負責介面」為空時，回報 `plan.md` 沒有前端介面、不產出 UI 規劃與雛形，並停止執行。
9. `WRITE` `ui/` 下已有檔案，且委派內容沒有說明使用者已同意覆寫時，列出這些檔案並詢問使用者是否覆寫；`ui/` 不存在、沒有檔案，或委派內容已說明同意時，略過本步驟與下一步。
10. `CHECK` 使用者回覆：同意覆寫時進入 Phase 2；不同意或未回覆時，回報沒有修改既有 UI 規劃與雛形、沒有產出任何檔案，並停止執行。

完成條件：「目標 spec」、`plan.md` 與技術研究結果已讀取，「負責介面」已決定，且 `ui/` 沒有既有檔案或使用者已同意覆寫；或缺少輸入、沒有前端介面、使用者不同意覆寫，已停止執行並回報。

## Phase 2 -- 確認視覺風格與憲法衝突

1. `THINK` 依「規劃輸入」判斷使用者需求或委派內容是否已指定視覺風格的氣質、配色與字體：三項都已指定時記為「視覺風格」，有未指定的項目時列為「風格缺口」。
2. `THINK` 比對「憲法檢查清單」的必須／不得規則與「規劃輸入」，列出和 spec、`plan.md` 或技術研究無法同時滿足的項目，建立「憲法衝突」。
3. `DELEGATE` 「風格缺口」或「憲法衝突」不為空時，讀取專案根目錄的 `.agents/skills/clarify/SKILL.md`（不存在時改讀 `.claude/skills/clarify/SKILL.md`）並依其 SOP 執行，不使用 Skill 工具呼叫 `clarify`，以「風格缺口」與「憲法衝突」為優先提問面向、不要求詳記問答紀錄，取得使用者確認的項目，與已指定的項目合併為「視覺風格」，並把使用者對「憲法衝突」的決定記為「憲法決策」；兩者都為空，或兩個 `SKILL.md` 都不存在時，略過本步驟。
4. `CHECK` 「風格缺口」或「憲法衝突」不為空，且兩個 `SKILL.md` 都不存在時，回報需要先在專案加入 `clarify`、沒有產出任何檔案，並停止執行；使用者未回覆或 `clarify` 停止時，回報沒有產出任何檔案並停止執行；與已指定的項目合併後，「視覺風格」的氣質、配色與字體都已確定時進入 Phase 3。

完成條件：「視覺風格」的氣質、配色與字體都已確定；或專案沒有 `clarify`、使用者未回覆，已停止執行並回報。

## Phase 3 -- 規劃畫面並產出 ui/plan.md

1. `READ` 規劃畫面時，讀取 `rules/畫面規劃-格式規範.md` 的所有 Rule，建立「畫面規劃檢查清單」。
2. ★ `THINK` 依「規劃輸入」、「視覺風格」、「憲法檢查清單」、「憲法決策」與已載入的「畫面規劃檢查清單」，為「負責介面」規劃畫面範疇、頁面清單、流程、使用者操作、各頁狀態、驗證與錯誤回饋，以及跨頁共用的假資料；只寫使用者操作與畫面回饋，不寫 API 路徑、HTTP 狀態碼或錯誤碼，建立「畫面規劃」，並把規劃時發現的上游問題建立為「上游衝突」；「上游衝突」只在 Phase 4 步驟 6 回報，不委派 `clarify`，也不停止產出。
3. `READ` `templates/ui-plan.md` 與 `templates/ui-plan.example.md`，載入骨架與範例，命名載入結果為「UI 規劃樣板組」。
4. `WRITE` 依「UI 規劃樣板組」與「畫面規劃」，將 `plan.md` 寫入「目標 spec」所在目錄的 `ui/`：標題填 spec.md 的功能名稱，`Date` 填執行當日日期，第 2 節填「視覺風格」與依它決定的色碼、字體與版面；說明文字的語言依「憲法檢查清單」，沒有規定時使用繁體中文，檔名與識別字使用英文。

完成條件：`ui/plan.md` 已寫入，且「畫面規劃」涵蓋每個「負責介面」。

## Phase 4 -- 產出 HTML 雛形並驗證

1. `READ` `templates/ui-page.html` 與 `templates/ui-page.example.html`，載入骨架與範例，命名載入結果為「HTML 頁面樣板組」。
2. `READ` 撰寫 HTML 雛形時，讀取 `rules/HTML雛形-格式規範.md` 的所有 Rule，建立「HTML 雛形檢查清單」。
3. `WRITE` 依「HTML 頁面樣板組」、已載入的「HTML 雛形檢查清單」、「憲法檢查清單」與 `ui/plan.md`，為第 3.1 節頁面清單的每一頁在 `ui/` 寫入一個 HTML 檔；已同意覆寫時，刪除 `ui/` 中不在頁面清單的既有 HTML；不建立或修改 `ui/` 以外的檔案。
4. `DELEGATE` 在本 Skill 目錄執行 `uv run --script scripts/check_ui.py --spec <目標 spec 絕對路徑> --interfaces <負責介面編號，以逗號分隔> <ui 目錄絕對路徑>`，取得「UI 檢查結果」；若缺少 `uv`，依 https://docs.astral.sh/uv/getting-started/installation/ 的目前平台安裝說明安裝後重試，安裝失敗時回報原因並停止。
5. `CHECK` 「UI 檢查結果」沒有問題，逐條驗證「憲法檢查清單」、「畫面規劃檢查清單」與「HTML 雛形檢查清單」（「憲法檢查清單」和其他兩份衝突時以「憲法檢查清單」為準，規則會改變鎖定項目時不套用並記入「未套用規則」，偏離「應」規則時把規則與理由記入「憲法偏離」），比對 `ui/plan.md` 與「UI 規劃樣板組」的標題與表格欄位、每個 HTML 與「HTML 頁面樣板組」的固定部分，並確認步驟 3 與 Phase 3 步驟 4 的填寫要求均已滿足；有瀏覽器自動化工具時，以 `file://` 打開每頁、逐一切換雛形狀態並確認沒有 JS 錯誤，沒有工具時將瀏覽器檢查記為「未驗證」；腳本因參數或環境錯誤而失敗時修正後重新執行步驟 4；未通過時修正 `ui/` 下的檔案後返回步驟 4，最多 3 輪，第 3 輪仍未通過時將未通過的項目記為「未通過項」。
6. ★ `WRITE` 向使用者或委派方回報 `ui/plan.md` 與每個 HTML 的路徑（標出入口 `index.html`）、每個「負責介面」對應的頁面、「視覺風格」摘要、瀏覽器檢查結果、「上游衝突」（沒有時寫「無」），以及「未通過項」（沒有時說明全部通過）與「憲法遵循」（已讀取的憲法檔路徑，都不存在時寫「沒有憲法檔」；必須／不得規則是否全部通過；「憲法偏離」；「未套用規則」；「憲法決策」）。

完成條件：`ui/plan.md` 與頁面清單的每個 HTML 已寫入，UI 檢查結果、兩份檢查清單與樣板結構已通過或未通過的項目已記為「未通過項」，且已回報。

# Rule 4 - 畫面規劃不得改寫上游決策，上游問題必須記為上游衝突

- 第 3.3 節的操作、第 4 節的狀態呈現與第 5 節的畫面回饋，必須與 `research.md` 各主題 `Decision` 中規定畫面的內容（例如顯示的欄位、文字、狀態或操作）及 spec 的需求一致，不得寫出相反的顯示方式或另一種做法。

- 每項上游衝突必須寫出四件事：衝突內容、上游位置（`research.md` 的 § 編號、spec 的需求編號或前面 Wave 產出的檔案與位置）、`ui/plan.md` 中受影響的頁面與節，以及建議的處理 Skill（`research.md` 為 `technical-research`，spec 為 `clarify-over-specs`，前面 Wave 的產出為產出它的 Planner）。

- 補上上游沒有規定的畫面細節（例如提示文字、空狀態、確認方式），且沒有與上游相反時，不得記為上游衝突。
