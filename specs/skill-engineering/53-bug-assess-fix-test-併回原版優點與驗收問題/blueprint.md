````markdown
# SOP

## Phase 1 -- 收斂回報與代號

1. `READ` 使用者的錯誤回報與附帶的路徑，並執行 `git status --short --untracked-files=all`，建立「回報內容」與「變更基準」。
2. `CHECK` 「回報內容」沒有描述任何症狀時，請使用者補充症狀並停止執行。
3. `THINK` 使用者指定了代號時用該代號；沒有指定時依「回報內容」擬定代號（只用小寫英文、數字與連字號，以 2～5 個英文單字描述症狀）；把 `specs/bugs/<代號>/assessment.md` 記為「報告路徑」。
4. `WRITE` 「報告路徑」已存在，而且使用者沒有指明要重新評估、覆寫或改用新代號時，詢問使用者選擇其中一種。
5. `CHECK` 「報告路徑」不存在時進入 Phase 2；已存在時依使用者的指明或回覆：重新評估時進入步驟 6，覆寫時進入 Phase 2，改用新代號時返回步驟 3，未回覆時停止執行。
6. `READ` 重新評估時，讀取「報告路徑」全文與同目錄存在時的 `fix.md`，建立「前次評估」：澄清紀錄、核准段、修法首選的各項，以及修正報告中已套用的修法項目。

完成條件：已取得「回報內容」、「變更基準」與尚未被占用、已同意覆寫或要重新評估的「報告路徑」；重新評估時已取得「前次評估」。

## Phase 2 -- 調查與判定

1. `READ` 調查時，讀取 `rules/調查範圍-格式規範.md` 的所有 Rule，建立「調查範圍檢查清單」。
2. `READ` 依「回報內容」與「調查範圍檢查清單」，找出相關的 spec 目錄（`specs/[0-9][0-9][0-9]-*/`），讀取其中的 `spec.md`、`ui/plan.md`、雛形 HTML 與和症狀相關的其他 Planner 產出；讀取 `specs/bugs/` 其他代號目錄中 `assessment.md` 的症狀段；以 `grep -rn` 搜尋，讀取相關程式與測試；不啟動系統，不執行會改變檔案或資料的命令，建立「調查證據」。
3. `READ` 列預期行為時，讀取 `rules/預期行為-格式規範.md` 的所有 Rule，建立「預期行為檢查清單」。
4. `THINK` 依「調查證據」與「預期行為檢查清單」，判斷問題類型，寫出症狀、完整預期行為（每項的目前、量測方式與通過標準）與重現步驟。
5. `THINK` 依「調查證據」寫出可疑程式路徑（`file:line`）與根本原因假設，寫明信心與沒有實測的部分。
6. `READ` 判定時，讀取 `rules/判定與分流-格式規範.md` 的所有 Rule，建立「判定檢查清單」。
7. `THINK` 依「調查證據」與「判定檢查清單」，把每個要改的事分流為缺陷或意圖改變，決定判定、嚴重度與嚴重度理由，寫出修法首選、替代做法、要改的檔案、要補的測試、需要核准的命令（重現步驟、要補的測試與量測方式中，會刪除、覆寫既有資料或需要對外網路的命令）、轉回 SDD 流程的項目、風險與「待確認問題」。

完成條件：報告各段落的內容都已決定，「待確認問題」已列出。

## Phase 3 -- 初稿與澄清

1. `READ` `templates/assessment.md` 與 `templates/assessment.example.md`，建立「評估報告樣板組」。
2. `WRITE` 依「評估報告樣板組」把初稿寫入「報告路徑」，核准狀態與核准段依「判定檢查清單」寫入；每個「待確認問題」在澄清紀錄寫一列，使用者回答與寫回位置寫「待回答」，沒有待確認問題時寫一列「無」；重新評估時，澄清紀錄先保留「前次評估」的各列，新問題接續編號，修法首選中前次已套用的項目標「（已套用）」。
3. `CHECK` 確認報告的標題、開頭欄位與表格欄位和「評估報告樣板組」一致，沒有殘留 `{{`；逐條驗證「調查範圍檢查清單」、「預期行為檢查清單」與「判定檢查清單」；逐一開啟可疑程式路徑，確認每個 `file:line` 存在；未通過時修正報告後重新檢查。
4. `CHECK` 澄清紀錄沒有「待回答」時進入 Phase 4；有「待回答」時進入步驟 5。
5. `DELEGATE` 委派 `clarify` Skill（無法以 Skill 工具呼叫時，讀取 `clarify` 的 `SKILL.md` 並依其 SOP 執行），以澄清紀錄中「待回答」的問題為優先提問面向、題數上限為「待回答」的題數、不要求詳記問答紀錄，取得使用者回答。
6. `WRITE` 把回答寫入澄清紀錄的「使用者回答」與「寫回位置」，依回答修改受影響的段落（判定、預期行為、修法、轉回項目等）；回答帶出新的待確認問題時，加入澄清紀錄並寫「待回答」；完成後返回步驟 3。

完成條件：報告通過步驟 3 的檢查，澄清紀錄沒有「待回答」。

## Phase 4 -- 核准與回報

1. `CHECK` 核准狀態為「不適用」時進入步驟 4；為「待核准」或「待核准命令」時進入步驟 2。
2. `WRITE` 核准狀態為「待核准」時，向使用者展示判定、嚴重度、修法首選的每一項、替代做法、需要核准的命令與轉回 SDD 流程的項目，請使用者指定要核准的修法項目與命令；為「待核准命令」時，展示判定、重現步驟與需要核准的命令，請使用者指定要核准的命令，並說明核准命令不代表核准修法。
3. `CHECK` 使用者回覆：核准修法時，依「判定檢查清單」把核准日期、核准的修法、核准執行的命令與不在本次修正範圍的項目寫入核准段，核准狀態改為「已核准（<日期>，核准<修法項目>）」，有前次已套用的項目時改為「已核准（<日期>，核准<修法項目>；前次已套用<修法項目>）」；核准命令時，依「判定檢查清單」把核准日期與核准執行的命令寫入核准段，核准狀態改為「已核准命令（<日期>）」；要求修改修法或提出新事實時，記入澄清紀錄後返回 Phase 2 步驟 4；拒絕或未回覆時，核准狀態維持原值。
4. `CHECK` 執行 `git status --short --untracked-files=all`，與「變更基準」比對，確認本 Skill 只新增或修改「報告路徑」所在的目錄；有其他由本 Skill 造成的變更時，還原這些變更。
5. `WRITE` 向使用者回報「報告路徑」、判定、嚴重度、核准狀態、轉回 SDD 流程的項目與處理 Skill，並給出下一步：已核准時接 `bug-fix`；有轉回項目時接該項目的處理 Skill；判定為待重現時，由 `bug-test` 做修正前實測後再重新執行 `bug-assess`；核准狀態為「待核准」時，說明核准後才能接 `bug-fix`；核准狀態為「待核准命令」時，說明沒有核准的命令不會執行，`bug-test` 修正前實測的結果可能只到「部分」。

完成條件：報告已寫入「報告路徑」且核准狀態反映使用者的回覆，工作目錄只有報告目錄的變更，已向使用者回報下一步。
````

````markdown
## Phase 2 -- 套用核准修法

2. `READ` 實作修法時，讀取 `rules/修正範圍-格式規範.md` 的所有 Rule，建立「修正範圍檢查清單」。

4. `READ` 依「修正契約」的可疑程式路徑與根本原因假設驗證根本原因：讀取相關程式，必要時執行不改變檔案或資料的命令，建立「根因驗證」。
5. `CHECK` 依「修正範圍檢查清單」判斷「根因驗證」：屬於判斷錯誤時，把新發現記入「偏離紀錄」，不修改程式，進入 Phase 3；其他情況進入步驟 6。
6. `WRITE` 依「修正契約」、「實作計畫」與「修正範圍檢查清單」，實作下一個修法項目，並新增或修改該項目對應的測試。
7. `CHECK` 依「修正範圍檢查清單」判斷本項目和「修正契約」的差異：屬於補充時記入「偏離紀錄」後繼續；屬於判斷錯誤時把新發現記入「偏離紀錄」，停止修改程式並保留已改的內容，進入步驟 8；還有未實作的修法項目時返回步驟 6，全部完成時進入步驟 8。
8. `DELEGATE` 執行「修正契約」中要補的測試列出的測試與命令，以及涵蓋修改檔案的既有測試（在測試目錄以 `grep -rl` 搜尋修改檔案的模組名稱），取得「驗證結果」；會刪除、覆寫既有資料或需要對外網路的命令，只執行「修正契約」中核准執行的命令，其他不執行並記入「驗證結果」。
9. `CHECK` 已因判斷錯誤停止時，只把失敗記入「驗證結果」並進入 Phase 3；「驗證結果」有本次修改造成的失敗時，依「修正範圍檢查清單」修正後返回步驟 8，最多 3 輪；第 3 輪仍失敗時，記入「偏離紀錄」為判斷錯誤並進入 Phase 3；失敗的測試沒有涉及本次修改的檔案與行為時，視為和本次修改無關，只記入「驗證結果」，不修改。

完成條件：實作計畫已寫入修正報告；每個要實作的修法項目都已實作，「驗證結果」沒有本次修改造成的失敗；或已因判斷錯誤停止，新發現已記入「偏離紀錄」，已修改程式時也已取得「驗證結果」。

## Phase 3 -- 修正報告與回報

1. `WRITE` 依「修正報告樣板組」、「修正範圍檢查清單」、「修正契約」、「實作計畫」、「偏離紀錄」與「驗證結果」，完成「修正報告路徑」中的修正報告，保留實作計畫段；狀態：要實作的修法項目全部完成且沒有判斷錯誤時寫「已套用」，因判斷錯誤停止且已修改程式時寫「部分套用」，因判斷錯誤停止且沒有修改程式時寫「未套用」。
2. `CHECK` 確認修正報告的標題、開頭欄位與表格欄位和「修正報告樣板組」一致，沒有殘留 `{{`，實作計畫段的點數等於要實作的修法項目數；執行 `git status --short --untracked-files=all` 和「變更基準」比對，確認本 Skill 造成的變更只有「修正範圍檢查清單」允許的檔案與「修正報告路徑」，而且沒有 commit；修正報告未通過時修正後重新檢查；有其他由本 Skill 造成的變更（包含測試產生的暫存檔）時進入步驟 3，沒有時進入步驟 4。
3. `WRITE` 還原步驟 2 找到的其他變更，然後返回步驟 2。
4. `WRITE` 向使用者回報「修正報告路徑」、「解析方式」、狀態、修改的檔案、驗證結果、偏離與未執行的項目，並給出下一步：狀態為「已套用」時接 `bug-test`；為「部分套用」或「未套用」時，依偏離重新執行 `bug-assess`。

完成條件：修正報告已寫入「修正報告路徑」並通過步驟 2 的檢查，已向使用者回報下一步。
````

### 2.3 bug-test

````markdown

name: bug-test
description: （未驗證）錯誤修正前後要實測、確認修法真的有效時使用：讀取 bug-assess 的 assessment.md 與 bug-fix 的 fix.md，沒有指定代號時沿用同一個對話中的代號；修正報告狀態為已套用、而且列出本次核准的每個修法項目時做修正後實測，用 git worktree 取出修正前版本，依完整預期行為的量測方式和通過標準在修正前後各量一次，並重跑重現步驟、新測試、修改模組的既有測試與 lint／type-check，會覆寫資料的命令只執行已核准的；評估判定為待重現時，不論有沒有 fix.md 都做修正前實測，確認錯誤能否重現。不修改程式，只在報告目錄寫入量測腳本與 specs/bugs/ 底下各代號目錄中的 test.md，結果為待使用者驗證、部分、失敗、已重現或未重現；不代替使用者宣稱已驗證，依症狀列出畫面操作或終端機命令的驗證項目請使用者執行，使用者要求時代為執行並標示，依回覆記錄為使用者已驗證或使用者驗證未通過。觸發關鍵字：bug-test、錯誤實測、修正後實測、修正前實測、test.md、驗證修正、記錄驗證結果、代為驗證。分流：還沒有評估報告或要重新評估時改用 bug-assess；要修改程式時改用 bug-fix；只想除錯、不產出實測報告時改用 diagnose。

# SOP

## Phase 1 -- 確認報告與模式

1. `READ` 使用者指定的代號或路徑與使用者提供的驗證結果，列出 `specs/bugs/` 底下各代號目錄、其中的 `assessment.md`、`fix.md`、`test.md`、`assessment.md` 的核准狀態與 `test.md` 的結果欄位，並執行 `git status --short --untracked-files=all`，建立「候選清單」與「變更基準」。

3. `CHECK` 「評估報告」不存在時，請使用者先執行 `bug-assess` 並停止；沒有明確指定、沒有沿用對話，而且有多個目錄符合時，列出這些目錄與各自的核准狀態、已有的報告，請使用者指定並停止；使用者提供了驗證結果或要求代為執行驗證時，「實測報告路徑」的結果為「待使用者驗證」則進入 Phase 4，不是則回報目前的結果並停止。
4. `READ` 「評估報告」全文與存在時的「修正報告」全文，建立「實測契約」：判定、核准狀態、核准的修法（標出前次核准與前次已套用的項目）、核准執行的命令、完整預期行為（每項的量測方式與通過標準）、重現步驟、要補的測試、轉回 SDD 流程的項目，以及修正報告的狀態、執行的修法、修改的檔案、新增或修改的測試與本機驗證的命令。
5. `THINK` 依「實測契約」決定「模式」：判定為「待重現」時為修正前實測，不論「修正報告」是否存在；判定為「成立」、核准狀態為「已核准（…）」、「修正報告」狀態為「已套用」，而且「執行的修法」列出本次核准的每個修法項目時，為修正後實測；其他情況沒有模式。
6. `CHECK` 沒有模式時，不修改任何檔案，回報原因與下一步並停止，依序判斷：判定為「不成立」或「意圖改變」時說明不需要實測；判定為「成立」而核准狀態不是「已核准（…）」時接 `bug-assess`；修正報告狀態不是已套用、部分套用、未套用之一時，回報無法辨識的狀態並接 `bug-fix`；修正報告不存在，或「執行的修法」沒有列出本次核准的某個修法項目時接 `bug-fix`；修正報告狀態為「部分套用」或「未套用」時接 `bug-assess`。
7. `WRITE` 「實測報告路徑」已存在時，詢問使用者是否覆寫。
8. `CHECK` 「實測報告路徑」已存在時檢查使用者回覆：同意覆寫時繼續；拒絕或未回覆時不修改任何檔案並停止。

完成條件：已取得「變更基準」、「解析方式」、「實測契約」、「模式」與尚未被占用或已同意覆寫的「實測報告路徑」；或已依使用者提供的驗證結果或代為執行的要求進入 Phase 4。

## Phase 2 -- 實測

1. `THINK` 依「實測契約」與「模式」寫出「實測計畫」：修正前版本（修正前實測時為工作目錄；修正後實測時，修正報告修改的檔案在「變更基準」中有未 commit 的修改則用 HEAD，沒有則用最後修改這些檔案的 commit 的父 commit）、修正後版本（工作目錄）、要啟動的服務、瀏覽器與寬度、要寫的量測腳本，以及每個版本要執行的檢查：完整預期行為的每一項、重現步驟、要補的測試，修正後實測時再加上修正報告本機驗證的命令、修改檔案所屬模組的既有測試與專案定義的 lint／type-check 命令；會刪除、覆寫既有資料或需要對外網路的命令，只執行「實測契約」中核准執行的命令，其他不執行，記為略過。
2. `WRITE` 依「實測計畫」準備環境：修正後實測時用 `git worktree add` 在系統暫存目錄取出修正前版本，依賴套件與被 git 忽略、啟動服務需要的設定檔（例如 `.env`）用符號連結指向工作目錄，不重新安裝，再把修正報告新增或修改的測試檔複製到修正前版本；需要量測腳本時寫在「實測目錄」，以參數接收應用程式路徑與網址，不寫死絕對路徑；啟動「實測計畫」列出的服務。
3. `READ` 判定實測結果時，讀取 `rules/實測結果-格式規範.md` 的所有 Rule，建立「實測結果檢查清單」。
4. `DELEGATE` 依「實測計畫」與「實測結果檢查清單」在各版本執行每項檢查，記錄命令、版本、結果、說明與輸出摘錄，建立「實測紀錄」；修正後失敗的檢查也在修正前版本執行；無法執行的檢查記錄原因後繼續；從本步驟到實測報告寫入前，不向使用者提問。
5. `WRITE` 停止準備環境時啟動的服務，刪除準備環境時建立的符號連結，再用 `git worktree remove --force` 移除準備環境時建立的 worktree。

完成條件：「實測計畫」的每項檢查在「實測紀錄」都有結果；準備環境時啟動的服務已停止，建立的 worktree 已移除。

## Phase 3 -- 實測報告與回報

1. `READ` `templates/test.md` 與 `templates/test.example.md`，建立「實測報告樣板組」。
2. `WRITE` 依「實測報告樣板組」、「實測結果檢查清單」、「實測契約」、「實測計畫」與「實測紀錄」，把實測報告寫入「實測報告路徑」；使用者驗證段：結果為「待使用者驗證」時，驗證日期與每項的結果寫「待使用者驗證」；其他結果時表格寫一列「無」，驗證日期寫「不適用」。
3. `CHECK` 逐條驗證「實測結果檢查清單」；確認實測報告的標題、開頭欄位與表格欄位和「實測報告樣板組」一致，沒有殘留 `{{`，完整預期行為實測表列出「實測契約」的每一項完整預期行為；確認量測腳本沒有寫死絕對路徑；執行 `git status --short --untracked-files=all` 和「變更基準」比對，確認本 Skill 造成的變更只有「實測目錄」中的實測報告與量測腳本，而且沒有 commit；執行 `git worktree list`，確認沒有留下 Phase 2 建立的 worktree。實測報告或量測腳本未通過時返回步驟 2；有其他由本 Skill 造成的變更（包含測試產生的暫存檔）或留下的 worktree 時進入步驟 4；全部通過時進入步驟 5。
4. `WRITE` 還原步驟 3 找到的其他變更，移除留下的 worktree，然後返回步驟 3。
5. `WRITE` 向使用者回報「實測報告路徑」、「解析方式」、模式、結果、主要數值與剩餘風險。結果為「待使用者驗證」時，列出使用者驗證段的項目，請使用者操作後回覆每一項的結果，或要求代為執行。其他結果時給出下一步並結束：「已重現」或「未重現」時，以實測報告為新證據重新執行 `bug-assess`；「部分」時寫出要補齊的條件，補齊後重新執行 `bug-test`；「失敗」時接 `bug-assess`。

## Phase 4 -- 記錄使用者驗證

1. `READ` 「實測報告路徑」全文與使用者的驗證回覆，建立「驗證前報告」與「驗證項目」。
2. `CHECK` 使用者沒有回覆任何驗證項目、也沒有要求代為執行時，結果維持「待使用者驗證」並停止；明確要求代為執行時進入步驟 3；有回覆時進入步驟 4。
3. `DELEGATE` 依「驗證項目」每一項的操作代為執行，依通過標準判斷，取得「代為執行結果」。

5. `CHECK` 和「驗證前報告」比對，確認只有使用者驗證段與結果欄位改變，結果欄位與每項「你的結果」都來自使用者回覆或「代為執行結果」；未通過時返回步驟 4。
6. `WRITE` 向使用者回報結果與下一步：「使用者已驗證（日期）」或「使用者已驗證（日期，agent 代為執行）」時錯誤修正流程結束，轉回 SDD 流程的項目交給處理 Skill；「使用者驗證未通過」時，以實測報告為新證據重新執行 `bug-assess`；結果維持「待使用者驗證」時，請使用者補回覆缺少的項目後再執行 `bug-test`。

完成條件：使用者驗證段與結果欄位已依使用者回覆或代為執行結果寫入並通過步驟 5 的檢查，已向使用者回報下一步。
````
