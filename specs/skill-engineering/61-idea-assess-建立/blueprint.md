推定理由：

- E3 已存在時詢問：覆寫既有產出前要先問使用者（CLAUDE.md 與 `bug-assess` 相同做法）；這一問在 Phase 1 開始研究之前，不在 5 個 Phase 之間。
- E6 low 與 medium 上限：定稿範例的 Booked Scheduler（只有搜尋摘要）為 low、廠商文章為 medium 或 low；寫成規則，讓評分可以重現。
- E8：計畫只定義 go 的門檻，kill 與 needs-clarification 不定義時，同一個構想每次判定可能不同。
- E10 不引用報告：交接是手動貼上，`s-specify` 不讀 `specs/ideas/`。
- E11 引用評級與證據：定稿範例是 go，沒有示範 kill；不規定時決定性理由可能只寫結論。
- E13：構想評估只產出報告，不應改動其他檔案（`bug-assess` 相同做法）。
- E14：「初步未知事項」與「缺口」小節存在的前提是不自行補上事實。
- E18 排除先例查證項目（第 3 輪）：證據缺口常有「某個先例是否有某功能」這類只影響評估的問題（例如定稿範例 `:83` 的 Snipe-IT、S1r2 `:72` 的 pretix 功能細節）；`s-specify` 寫規格時用不到，全部帶過去會讓待確認清單變長、模糊重點。

## 2. To-Be SOP

````markdown
---
name: idea-assess
description: （未驗證）有一個產品或功能構想、要在寫規格之前判斷值不值得做時使用：寫出構想收件、證據研究（一定要寫反對這個構想的證據；可抓取公開的 https 網頁並記錄每個網址的抓取結果）、問題定義、方案構想（2～3 個方案並推薦一個）與判定（6 項準則評分，結論為 go、needs-clarification 或 kill）五段的評估報告，評估過程中不向使用者提問，寫成 specs/ideas/ 底下各 slug 目錄中的 assessment.md；go 時附可直接貼上的 s-specify 指令，由使用者決定是否採用並手動交接，本 Skill 不執行 s-specify。觸發關鍵字：idea-assess、構想評估、評估構想、選題評估、值不值得做、go／kill 判定、assessment.md。分流：已決定要做、要寫 spec.md 時改用 s-specify；只需訪談釐清需求、不產出評估報告時改用 clarify；已有 spec 要做技術選型改用 technical-research；評估錯誤回報改用 bug-assess。

# SOP

## Phase 1 -- 構想收件

1. `READ` 使用者的構想描述與附帶的路徑，並執行 `git status --short --untracked-files=all`，建立「構想輸入」與「變更基準」。
2. `CHECK` 「構想輸入」沒有描述任何構想時，請使用者提供構想並停止執行。
3. `THINK` 使用者指定了 slug 時用該 slug；沒有指定時依「構想輸入」擬定 slug（只用小寫英文、數字與連字號，以 2～5 個英文單字描述構想）；把 `specs/ideas/<slug>/assessment.md` 記為「報告路徑」。
4. `WRITE` 「報告路徑」已存在，而且使用者沒有指明覆寫或改用新 slug 時，詢問使用者選擇其中一種。
5. `CHECK` 「報告路徑」不存在時進入步驟 6；已存在時依使用者的指明或回覆：覆寫時進入步驟 6，改用新 slug 時返回步驟 3，未回覆時停止執行。
6. `READ` `templates/assessment.md` 與 `templates/assessment.example.md`，建立「評估報告樣板組」。
7. `THINK` 依「構想輸入」與「評估報告樣板組」的構想收件段，寫出構想收件段的內容；「構想輸入」沒有說明的事寫成初步未知事項，不自行補上。

完成條件：已取得「構想輸入」、「變更基準」、「評估報告樣板組」、尚未被占用或已同意覆寫的「報告路徑」，以及構想收件段的內容。

## Phase 2 -- 證據研究

1. `READ` 「構想輸入」附帶的專案檔案，以及 `.agents/constitution/` 存在時其中的所有檔案，建立「專案證據」。
2. `THINK` 依構想收件段與「評估報告樣板組」證據研究段的小節，擬定要查證的主題與搜尋詞。
3. `READ` 研究證據時，讀取 `rules/證據研究-格式規範.md` 的所有 Rule，建立「證據研究檢查清單」。
4. `READ` 依「證據研究檢查清單」，以網頁搜尋與網頁抓取工具查證每個主題，記錄每個網址的抓取結果，建立「研究證據」；平台沒有網頁工具時，只用「專案證據」與「構想輸入」研究，並在證據概述寫明沒有上網查證。
5. `THINK` 依「研究證據」、「專案證據」與「證據研究檢查清單」，寫出證據研究段的內容。
6. `CHECK` 逐條驗證「證據研究檢查清單」；缺少證據時返回步驟 4 補查，其他未通過時修正證據研究段的內容。

完成條件：證據研究段的內容通過「證據研究檢查清單」。

## Phase 3 -- 問題定義

1. `THINK` 依構想收件段與證據研究段寫出問題定義段的內容；問題陳述只寫問題，不寫方案與技術選型；每個成功指標標出類型與基準，基準未知時寫 unknown；沒有證據支持的使用者、目標與限制寫成待確認問題。

完成條件：問題定義段的每個小節都已有內容。

## Phase 4 -- 方案構想

1. `THINK` 依問題定義段寫出 2～3 個做法或投入規模不同的方案，推薦其中一個方案並引用問題定義段的目標說明理由；證據研究段的先例或市場與現況列出可直接採用的現成產品，而推薦方案不是採用現成產品時，推薦理由寫出不直接採用該產品的原因；再列出推薦方案不在範圍內的項目與待驗證的假設。

完成條件：方案構想段有 2～3 個方案與一個推薦方案。

## Phase 5 -- 判定與交付

1. `READ` 判定時，讀取 `rules/判定-格式規範.md` 的所有 Rule，建立「判定檢查清單」。
2. `THINK` 依前四段的內容與「判定檢查清單」，為評分表的每項準則評級，決定結論與整體證據信心，寫出判定理由與和結論相符的判定段內容。
3. `WRITE` 依「評估報告樣板組」把檔頭與五段內容寫入「報告路徑」；只有 2 個方案時刪除方案 C 的區塊，未使用的欄位與段落整段刪除，以「／」列出的固定值只留一個。
4. `CHECK` 確認報告的標題、檔頭欄位、段落順序與表格欄位和「評估報告樣板組」一致，沒有殘留 `{{` 與以「／」列出的固定值；逐條驗證「證據研究檢查清單」與「判定檢查清單」；未通過時修正報告後重新檢查。
5. `CHECK` 執行 `git status --short --untracked-files=all`，與「變更基準」比對，確認本 Skill 只新增或修改「報告路徑」所在的目錄；有其他由本 Skill 造成的變更時，還原這些變更。
6. `WRITE` 向使用者回報「報告路徑」、結論、推薦方案與整體證據信心，請使用者決定是否採用：go 時展示判定段的 `s-specify` 指令區塊，說明採用時由使用者貼上執行；needs-clarification 時列出阻擋問題，說明回答後帶著回答重新執行 `idea-assess`；kill 時列出決定性理由。本 Skill 不執行 `s-specify`。

完成條件：報告已寫入「報告路徑」並通過步驟 4 的檢查，工作目錄只有報告目錄的變更，已向使用者回報結論並請使用者決定是否採用。
````
