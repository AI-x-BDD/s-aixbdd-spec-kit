# 選模評估做法

本文件規定怎麼用實際執行的結果，決定開發執行時用哪個模型、哪個 editor。
目前的建議見 [開發執行選模評估.md](./開發執行選模評估.md)。本評估的目的是驗證或推翻那份建議。

- 建立：2026-11-11
- 狀態：只有規劃，尚未執行
- 結果寫到：`docs/選模評估/結果.md`（第一次執行時建立）

## 1. 要決定的 3 件事

| 編號 | 問題 | 比較的選項 | 預設（評估不通過時採用） |
|---|---|---|---|
| Q1 | `implement` 由哪個模型執行？ | Opus 5.5 high／Sonnet 5.5 high | Opus 5.5 high |
| Q2 | 檢查類步驟（以 `analyze` 代表）要不要升級模型？ | Opus 5.5 high／Fable 5.2 high | Opus 5.5 high |
| Q3 | 執行者用哪個 editor？ | Claude Code／Codex／OpenCode | Claude Code |

原則：

1. 新選項必須「品質不輸、成本明顯較低」或「品質明顯較好」，才取代預設。結果不明確時，維持預設。
2. 一次只改一個變數。同一組比較裡，Skill 版本、輸入、電腦、Node 版本都相同。
3. 判定規則在執行前就固定（第 6 節），看到結果後不改。

## 2. 開始前的條件

1. iter-6 的 A/B 比較已經結束。本評估不得用 iter-6 的 worktree，也不得改 `main`。
2. 評估用的 worktree 放在 `../s-aixbdd-spec-kit-eval/`，每個執行一個 worktree，評估完不 merge。
3. 確認用的 Skill 是起點 commit 的版本。`implement`、`analyze` 在 `96ef51b` 之後沒有 commit 修改。主目錄的工作區有未 commit 的 `analyze` 修改，但 worktree 從 commit 建立，不受影響。
4. 測試依賴實際時間（12:00–21:00 才通過）。執行測試時，必須在這個時段內，或先重建假時鐘（iter-5 的工具在 `/tmp/iter5-fakeclock/`，可能已不存在）。
5. Docker、Node.js 版本與 iter-5 不同時，記下版本。iter-5 用 Node.js 24.14.1。

## 4. 執行組別

| 組別 | 問題 | 執行者 | 次數 | 備註 |
|---|---|---|---|---|
| A | Q1 | Claude Code＋Opus 5.5 high | 1 次新跑＋iter-5 原始結果 | iter-5 結果當作第 1 次 |
| B | Q1 | Claude Code＋Sonnet 5.5 high | 2 次 | 啟動：`claude --model sonnet --effort high` |
| C | Q1（選做） | Claude Code＋Sonnet 5.5 medium | 2 次 | B 通過時才跑，看能不能再省 |
| D | Q2 | Claude Code＋Opus 5.5 high | 3 次 | `analyze` 很便宜，多跑幾次看變異 |

每次執行都用新的 session，提示詞相同（第 4.1 節），不帶之前的對話。子代理一律明確指定和主 session 相同的模型（本機的 `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` 會改掉子代理的模型）。

模型一律寫完整 ID，不用別名：`claude-opus-5-5`、`claude-sonnet-5-5`、`claude-fable-5-2`。例如：`claude --model claude-sonnet-5-5 --effort high`。

## 5. 量測項目

### 5.1 Q1（每次執行都記）

1. 陷阱分數：K1～K7 每項 0～2 分。
   - 2 分：發現，處理正確，寫進決策紀錄。
   - 1 分：發現，但處理錯誤或沒有記錄。
   - 0 分：沒有發現。
2. Phase 4 Checkpoint 的測試結果：backend、frontend、e2e 的通過數。K3、K6 造成的已知失敗分開記。
3. 規則遵循：有沒有只讀 Must Read、有沒有驗證後才打勾、有沒有自行提問。違反一次記一筆。
4. 受阻任務數、自行決策數。
5. 成本：token 數（從 `~/.claude/projects/` 下該 session 的 JSONL 加總 `usage`）、換算的金額（依官方價目表）、實際時間。
6. 參考項：用 iter-5 最終 commit `c7c2ac6` 中 US1、US2 的整合測試，跑在本次產出的程式上。這些測試是 Opus 寫的，可能偏向 Opus 的寫法，只當參考，不列入判定。

### 5.2 Q2（每次執行都記）

1. 召回：G1～G7 抓到幾項。G7 單獨記。
2. 誤報：標為 HIGH、但經評分者判定不是真問題的數量。
3. 嚴重度：G3、G4 有沒有標成 HIGH。
4. 成本：同 5.1 第 5 點。

### 5.3 Q3：editor 檢查表（不必實跑，查文件與 `--help` 即可）

| 代號 | 條件 | 必要 |
|---|---|---|
| H1 | 讀得到 `.claude/skills/` 或 `.agents/skills/` 的 Skill | 是 |
| H2 | 每次輸入時執行 `scripts/hooks/answer-style.sh` | 是 |
| H3 | 委派子代理時可以指定模型與 effort | 是 |
| H4 | 可以用 `herdr agent start` 啟動，並轉接確認閘門 | 否 |
| H5 | 可以取得每個 session 的 token 用量 | 否 |

目前已知的狀況（執行時要重新確認）：Claude Code 符合 H1～H3；Codex 符合 H1、H2，H3 依 `.codex/model-routing.md`；OpenCode 不執行 `answer-style.sh`（runbook 第 2 節），子代理只用同一個模型。

## 6. 判定規則（執行前固定）

### Q1：`implement` 改用 Sonnet 5.5 的條件

全部成立才改用：

1. B 組 2 次的 K4、K5 都是 2 分。
2. B 組 2 次的陷阱總分，都不低於 A 組 2 次中較低的那一次。
3. B 組 Phase 4 Checkpoint 的測試，除了 K3、K6 的已知失敗以外全部通過。
4. B 組的平均成本不超過 A 組平均的 60%。

有一項不成立就維持 Opus 5.5 high。B 成立時才跑 C，用同樣的規則和 A 比。

### Q2：`analyze` 改用 Fable 5.2 的條件

全部成立才改用：

1. E 組 3 次中至少 2 次抓到 G7，而 D 組抓到 G7 的次數比 E 組少。
2. E 組的 G1～G6 平均召回不低於 D 組。
3. E 組的平均誤報不比 D 組多 1 項以上。

有一項不成立就維持 Opus 5.5 high。成立時只對 `analyze` 改用 Fable 5.2，其他步驟不改。

### Q3：editor

1. H1～H3 有一項不符合的 editor，不能當執行者。
2. 符合的 editor 有兩個以上時，維持 Claude Code。除非 F 組的結果依 Q1 的規則勝過 A 組。

## 7. 評分

1. 能用指令檢查的項目，用指令檢查。例如：`grep` 確認 T021、T022 的交易裡有沒有加鎖，並執行測試。
2. 需要判斷的項目（K 分數、誤報）由 Codex 獨立評分。給 Codex 的只有：本文件第 3、5 節、產出檔案與決策紀錄。不告訴它組別與模型名稱。
3. Claude Code 也評一次。兩者分數不同時，把兩個分數都記下，再由使用者決定。理由：Claude（Opus）評自己的模型，可能偏心。

## 8. 執行步驟

1. 確認第 2 節的條件，記進 `結果.md` 的「環境」。請使用者定出本次評估的花費上限，也記進 `結果.md`。
2. 填寫 Q3 檢查表（第 5.3 節）。
3. 跑 D、E 組（`analyze`，共 6 次）並評分。
4. 跑 B 組（Sonnet 5.5 `implement`，2 次）並評分。
5. 跑 A 組的新執行（Opus 5.5 `implement`，1 次）並評分。iter-5 的原始結果也用同一份評分表評一次。
6. 依 Q1 的規則判定。B 成立時跑 C 組。
7. Q3 檢查表顯示 Codex 可行、而且使用者想比較時，跑 F 組。
8. 依第 6 節寫出 Q1～Q3 的判定，更新 `開發執行選模評估.md` 的結論與狀態。
9. 判定改變了現行設定時，更新 `CLAUDE.md` 的「模型與 effort（Claude Code）」與 runbook，並執行 `scripts/sync-skills.sh --from claude`。

## 9. 成本控制

1. 先跑最便宜的 Q2（第 3 步）。第 3 步結束後，用 D、E 組的實際花費估算 Q1 的花費。已花費加上估算超過第 1 步定的上限時，在第 4 步之前停下來，請使用者決定。
2. Q1 只跑 Phase 1～4，不跑整個迭代。
3. 選做組別（C、F）只在前面的結果需要時才跑。
