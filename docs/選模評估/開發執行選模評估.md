# 開發執行選模評估

- 日期：2026-11-11
- 問題：執行開發（迭代的 `s-specify` → `implement`）時，該用哪個模型、哪個 editor？
- 前提：不再考慮「Argon 額度要用完」這個條件，只依整體開發流程評估。
- 依據：最近 40 個 commit、`docs/iterations/iter-1.md`～`iter-6.md`、`docs/dev/迭代-runbook.md`。
- 狀態：Claude Code（Opus 5.5）的分析建議，使用者尚未確認。要用實際執行結果驗證時，照 [評估做法.md](./評估做法.md) 執行。

## 結論

1. 主 session 整段流程都用 **Claude Code＋Opus 5.5、effort high**，包括 `implement`。
2. 委派 Planner 等子代理時，明確指定 Opus。
3. Fable 5.2、Sonnet 5.5 都不當開發執行者。
4. editor 維持 Claude Code CLI；看 diff 與文件用 VS Code。

## 為什麼執行者的模型重要

這套流程的品質，靠執行者在每一步主動找出上游文件的矛盾，不只靠照著做。

| 迭代 | 執行者 | 任務數 | 自行決策 | 找到的 Skill 缺陷 |
|---|---|---|---|---|
| 1～3 | Argon | 35／28／23 | 每次 3 條 | 0 |
| 4 | Argon → Opus（步驟 2 中途換） | 60 | 65 條 | 有（`api-plan`） |
| 5 | Opus 5.5 high | 46 | 54 條 | 5 |

1. Argon 回報的「沒有問題」只能當弱證據。
2. iter-5 的 Opus 抓到 4 個 HIGH 衝突，實作時都真的出現。如果照 research 實作，F3、F4 會變成程式錯誤。Opus 在 `implement` 推翻合約、加了鎖，才避免這些錯誤。
3. 干擾因素：iter-4 之後的功能比較複雜，Skill 也在修正，所以兩組數字不能直接比較（runbook 第 6 節第 5 點）。但這不改變結論：`implement` 也要判斷上游錯誤。

## 各工作的模型

| 工作 | 模型與 effort | 理由 |
|---|---|---|
| 主 session：步驟 2～8 | Opus 5.5、high | 每一步的缺陷都是跨文件矛盾，需要強推理；iter-5 已有實績 |
| Planner 等子代理 | 明確指定 Opus | 本機設了 `CLAUDE_CODE_SUBAGENT_MODEL=sonnet`，不指定就會變成 Sonnet |
| Skill 驗收、機械性複核 | Sonnet 5.5、medium | 照 `CLAUDE.md` 既有規則 |

不採用的選項：

1. **Sonnet 5.5 跑 `implement`**：價格是 Opus 5.5 的一半（$2/$10 對 $4/$20，每百萬 token），但它比較可能照錯誤的合約實作。成本要算完成一次迭代的總成本。多一次重工或一個漏掉的錯誤，就會抵掉省下的錢。
2. **Fable 5.2**：價格是 Opus 5.5 的 2 倍（$8/$40）。iter-5 的 `analyze` 已抓到全部 HIGH，沒有證據顯示還有提升空間。
3. **effort xhigh 或 max**：目前的缺陷出在 Skill 規則，不是推理深度不夠。

## 什麼時候重新評估

1. iter-6 的 A/B 兩組必須維持 Opus 5.5 high，A/B 做完之前不改。
2. A/B 做完後如果想省成本，用 Sonnet 5.5 跑一個 Phase 的 `implement`，和 Opus 比較自行決策的品質，再決定。
3. Skill 修正後，如果同一類缺陷還是出現，用 Fable 5.2 跑一次 `analyze` 或根因分析，比較結果。
4. 一次只改一個變數（模型或 effort），並記進迭代紀錄的「固定環境」。

## Editor

1. **執行者用 Claude Code CLI。** 只有它同時支援這個專案的 `answer-style.sh` hook、`.claude/agents/`（`implementer`、`skill-tester`）和子代理選模。OpenCode 這三項都沒有。
2. **Codex 當第二意見。** 照現在的做法，用在討論與交叉檢查，不當執行者。
3. **VS Code 只用來人工看 diff 與 spec**，可以裝 Claude Code 擴充套件，不改變執行者。

## 附錄：與選模無關的觀察

這些是分析時順便看到的流程問題，不屬於選模的主題。要處理時，另外決定。

1. 同一類缺陷一再出現：Planner 改寫了 research 或 spec 的決策，卻沒有回報衝突。iter-4 出現在 `api-plan`，iter-5 又出現在 `ui-plan`、`api-plan`、`technical-research`。可以考慮寫成共用規則，一次檢查所有 Planner（屬於 `skill-engineering` 的範圍）。
2. iter-5 的正式 `spec.md`、`research.md`、`contracts/openapi.yaml` 和程式不一致；SC-002 的計算時間點還沒有人決定。
3. 既有測試只在 12:00–21:00 能通過。假時鐘工具放在 `/tmp/iter5-fakeclock/`，沒有進版控。
4. iter-4、iter-5 的使用者驗證都由 AI 代做。依專案規則第 6 條，這樣還不能提議打 tag。
5. 子代理遇到 429 中止，`analyze` 子代理寫檔被擋下，這兩件事各發生 2 次。
