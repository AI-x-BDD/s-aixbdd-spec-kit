## 3. 檢查結果

課程要求檢查的兩項：

- **DBML 生命週期欄位**：`chat_messages` 有 `created_at`、`updated_at`、`updated_by`、`deleted_at`，符合 `data-model.md` Rule 1。
- **API 分頁**：`GET /api/rooms/{roomId}/chat-messages`（`listChatMessages`）有 `page`／`pageSize`（預設 20、上限 100），回應有 `items`、`page`、`pageSize`、`totalItems`、`totalPages`，有 400 `PAGINATION_INVALID`，`description` 寫明依 `sequence` 排序，符合 `openapi.md` Rule 1–5。

檢查腳本：`check_ui.py`、DBML 檢查、`check_contracts.py`（Redocly lint）都回報沒有問題。

### 3.1 尚未解決：軟刪除和 FR-008 衝突

- `data-model.md` Rule 2 規定：刪除必須是軟刪除。
- spec FR-008 規定：房間關閉後不保留聊天訊息。research §1 因此決定 `onDelete: Cascade`。
- `data-plan` 依 spec 保留連帶刪除（`Ref: chat_messages.room_id > rooms.id [delete: cascade]`）。`deleted_at` 欄位保留，一律為 null。
- 這項衝突沒有經過 `clarify`，使用者還沒有決定。
- `data-model.md` Rule 1 對 `rooms` 也沒有通過。原因是 DBML 只列出 `rooms.id` 作為參照，要加欄位就必須修改 001 的 `rooms`。

### 3.2 Planner 自行決定、和上游不一樣的地方

1. **分頁**：research §3 原本寫「不分頁」，`api-plan` 依憲法改成分頁。主 session 已修改 research §3。
2. **新事件 `room:player-left`**：既有 001 合約在對局結束（`finished`）後有人離開時，不推播任何事件。所以新增這個事件，對應 US1 情境 11。其他階段沿用 `game:ended`、`room:closed`。
3. **事件命名不一致**：`chatMessageCreated`（依 research §2）和既有事件的冒號格式（例如 `room:updated`）不一樣，目前沒有修改。
4. **`content` 用 `text`**：100 字以 grapheme 計算，由後端驗證，不用 `varchar(100)`。

## 4. 驗收時發現的問題（待記到 `docs/待確認.md`，記之前先問使用者）
