# 概念解說偏好

## 用途與正式規則

本文件保存使用者確認有效的解說背景與範例。正式規則集中在 AGENTS.md／CLAUDE.md 的「回答方式」，本文件不另維護一份規則清單。

## 使用者回饋

在 Steve Orchestrator 討論中，使用者尚未理解助手能做什麼。過早列出「第一版先不做」清單，反而引出額外疑問。抽象術語層層疊加，也讓使用者難以判斷實際用途。

使用者確認有幫助的改進是：先展示具體工作與互動，說清楚助手會協助哪些判斷，以及哪些決定仍由使用者做。理解用途之後，再討論 Skill 設計。

## 範例

較難理解：Steve 整合跨領域決策流，建立持續演進的知識複利系統。

較容易理解：你告訴 Steve 想完成的事。Steve 協助判斷下一步，找適合的 Skill 執行，再根據結果調整安排。若這次發現方法有缺陷，再提出改善建議，讓下次遇到同類問題時能使用改善後的做法。

假設情境：使用者想開發付費工具。Steve 建議先訪談可能付費的人。使用者說明這次目的是練習開發，Steve 就依這個目標重新安排工作。這個例子呈現「助手提出建議，使用者決定目標與取捨」。

## 工作回報規則的來源與調整

來源：[GPT-6.2 Astra 受到了不公平的對待](https://jot.zerotype.ai/s/SwNZhwl5QtvDea6xAejfT5ds)。標題與模型名稱沿用原文，不代表本專案驗證其產品主張。

使用者確認以文章的五項回報要求為主：結果、需要使用者決定的事、先做什麼、重要變更或發現、確定程度。融合後保留獨立可讀、證據來源與驗證缺口的要求；簡單問答用短句呈現，沒有實質內容的區塊省略。

原本的結論先行與精簡理由目的保留。理由依決策需要取捨，不限三點。等待使用者時仍說明原因與下一個動作；多步驟工作流統一使用完成步驟、下一步與末尾提示詞格式，以消除「結尾只寫兩行」的矛盾。
