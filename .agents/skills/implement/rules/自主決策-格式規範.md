# Rule 1 - 執行期間不得中途停止或提問，矛盾必須依權威順序自行決策

- 從執行第一個任務到回報完成報告之前，不得向使用者提問或等待回覆。
- 範圍內所有任務都已打勾或記為受阻之前，不得結束回合；不得因任務數量、執行時間、上下文用量或想讓使用者確認進度而中途停止，也不得詢問是否繼續。
- 本規則優先於 tasks.md Reference Loading Contract 中「停下來回報」與「回報缺少什麼」的要求；遇到這些情況時，必須依本 RuleFile 決策並記錄後繼續執行。
- 文件之間的內容互相矛盾時，必須採用下表中權威較高者。

| 權威 | 文件 |
| ---- | ---- |
| 1（最高） | spec.md 的需求（FR、NFR）、驗收情境與 Edge Cases |
| 2 | contracts、data、ui 的介面規格 |
| 3 | research.md、techstack.md 的技術決策 |
| 4 | tasks.md 的任務描述 |

- tasks.md Notes 的「待確認」已寫出暫行做法，且暫行做法不違反權威較高的文件時，必須沿用暫行做法。
- 同一權威層級的文件互相矛盾（例如資料表的 Enum 值與 API 的狀態值不同）時，必須讓兩邊的對外契約維持原樣，在兩者之間加入轉換。
- 上游沒有規定的細節，必須選擇最符合 spec.md 需求與驗收情境的做法。
- 不得修改 spec 目錄中的上游文件（spec.md、plan.md、research.md、techstack.md、contracts、data、ui）。

## Good Example

### Example 1

- 診所掛號系統中，data-model 的 `appointment_status` 為 `booked`、`cancelled`，openapi 的 `Appointment.status` 為 `BOOKED`、`CANCELLED`；兩者同屬介面規格，因此資料庫與 API 各自維持原樣，在回應轉換處加上對照，記錄決策後繼續。

```text
決策（T015）：data/data-model.dbml `Enum appointment_status` 與 contracts/openapi.yaml `Appointment.status` 值不同，同屬權威 2；
資料庫維持 booked/cancelled，API 回應維持 BOOKED/CANCELLED，在 toAppointmentDto() 轉換。影響：T015、T021。
```

### Example 2

- 診所掛號系統共 49 個任務，T009 打勾後腳本提示還剩 40 個任務，回報完進度就直接取下一個任務。

```text
T009 已通過，回寫後繼續下一個任務
範圍內還剩 40 個任務：立即執行 next；全部完成前不得停下來或詢問是否繼續
next → T010
```

## Bad Example

### Example 1

- 同一個矛盾讓執行停下來詢問使用者，等待回覆期間沒有繼續任何任務。

```text
T015：資料模型與合約的狀態值不同，請問要以哪一個為準？（等待回覆）
```

### Example 2

- 同一個情境在 T009 打勾後，以工作量大為由結束回合，等待使用者回覆。

```text
T009 已通過。目前完成 9／49，後面還有 40 個任務，需要長時間逐一執行。
我先停在這裡回報進度，要繼續的話請告訴我，我會從 T010 接著做。
```

# Rule 2 - 只有環境限制與憲法衝突可以記為受阻，且不得假裝完成

- 因環境限制導致任務驗證 3 輪仍未通過時，必須先找出根因，並至少嘗試一種替代做法（例如改用相容的套件版本、改用其他啟動方式）。
- 可以記為受阻的原因只有兩種：
  - 環境限制：外部服務無法啟動、套件或映像無法下載、缺少權限、憑證或硬體，導致任務無法完成。
  - 憲法衝突：任務要求和「憲法檢查清單」的「必須」或「不得」規則無法同時滿足，例如任務描述要求「不得」規則禁止的套件、設定或做法，或照任務描述實作就無法符合「必須」規則。
- 憲法衝突不屬於 Rule 1 的文件矛盾，不得依權威順序自行決定採用憲法或任務描述，也不需要嘗試替代做法。
- 不得刪除、略過或改寫任務要求中和憲法衝突的部分，再以其餘部分完成並打勾。
- 程式本身的錯誤不得記為受阻；必須修正到驗證通過。
- 受阻任務不得打勾。
- 直接使用受阻任務產物（檔案、資料表、啟動的服務）的後續任務必須一併記為受阻；不使用這些產物的任務必須照常執行。
- 不得以假實作、以 mock 或其他技術取代任務指定的依賴、略過驗證或降低任務要求，讓受阻任務看起來已完成。

## Good Example

### Example 1

- 診所掛號系統執行時 Docker daemon 沒有啟動，`T009 套用 migration` 無法連到 PostgreSQL；嘗試改用 `docker compose up -d` 啟動容器也失敗後，記為受阻，依賴資料表的 T010–T014 一併受阻，前端任務照常執行。

```text
受阻：T009（根因：Docker daemon 未啟動，`docker compose up -d` 回報 Cannot connect to the Docker daemon）
一併受阻：T010–T014（需要 appointments 資料表）
照常執行：T015–T018（前端畫面）
```

### Example 2

- 診所掛號系統的憲法 `code.md` Rule 3 規定「不得使用 moment.js」，T006 卻要求安裝 `moment` 並建立日期工具；T006 記為受阻並寫出 `code.md` Rule 3，直接使用該日期工具的 T012 一併受阻，其餘任務照常執行。

```text
受阻：T006（憲法衝突：任務要求安裝 `moment`，違反 `.agents/constitution/skills/implement/code.md` Rule 3「不得使用 moment.js」）
一併受阻：T012（使用 T006 建立的日期工具）
照常執行：其餘不使用日期工具的任務
```

## Bad Example

### Example 1

- 同一個情況改用 SQLite 代替任務指定的 PostgreSQL，跳過 migration 驗證後把 T009 打勾。

```text
T009：Docker 無法啟動，改用 SQLite 建立資料表，已完成 [X]
```

### Example 2

- 同一個憲法衝突情境把 `moment` 換成其他套件或刪掉，以其餘部分完成 T006 並打勾，把衝突寫進「憲法偏離」。

```text
T006：`moment` 違反 code.md Rule 3，改用 dayjs 建立日期工具，已完成 [X]
憲法偏離：T006 未安裝 `moment`，與任務描述不同
```

# Rule 3 - 每個決策必須留下可追溯的紀錄

- 決策紀錄的每一項必須包含：任務 ID、情況（引用矛盾或缺漏的檔案與部位）、決定、理由（引用權威順序、待確認編號或需求編號）、影響範圍（受影響的檔案或後續任務）。
- 依 Rule 1 處理的每一個文件矛盾都必須記入決策紀錄，即使最後採用的做法與任務描述相同。
- 受阻也必須記入決策紀錄；環境受阻的理由必須寫出根因與已嘗試的替代做法，憲法衝突受阻的理由必須寫出衝突的憲法檔路徑與 Rule 編號。
- 沿用 Notes 待確認的暫行做法時，也必須記入決策紀錄。

## Good Example

- 每一項都能追到矛盾的部位與依據，讀者不必重跑一次就能判斷決策是否合理；T011 最後採用的保留時間與任務描述相同，仍記入紀錄。

| 任務 | 情況 | 決定 | 理由 | 影響範圍 |
| ---- | ---- | ---- | ---- | -------- |
| T011 | `research.md` §4 寫未付款預約保留 10 分鐘，任務描述與 `spec.md` FR-007 寫 15 分鐘 | 保留 15 分鐘 | `spec.md` 屬權威 1，高於 `research.md` 的權威 3 | `appointmentService.ts` 的過期排程 |
| T015 | `data-model.dbml` `Enum appointment_status` 與 `openapi.yaml` `Appointment.status` 值不同 | 兩邊維持原樣，在 `toAppointmentDto()` 轉換 | 同屬權威 2，維持兩邊對外契約 | T015、T021 |
| T017 | `ui/plan.md` §5 沒有 `CLINIC_CLOSED` 的畫面文字 | 沿用 Notes 待確認 2，顯示「目前無法預約，請稍後再試」 | 待確認 2 的暫行做法，不違反 FR-006 | `frontend/src/text/zh-TW.ts` |

## Bad Example

- 同一批決策只寫結果，看不出依據哪份文件、影響哪些任務；T011 的保留時間矛盾因為最後照任務描述實作，沒有記入紀錄。

| 任務 | 決策 |
| ---- | ---- |
| T015 | 已處理狀態值 |
| T017 | 用通用文字 |
