# Rule 1 - 動詞版定義必須對應可觀察的學習成果

- 動詞版定義必須是一句話，包含讀者、預期時間、認知轉變及可觀察的解釋、判斷或操作成果。
- 時間必須標為預期；實際讀者效果依證據檢查清單處理。
- 範圍必須從讀者現在會的程度往前推進一段，不得要求讀者在一篇內從入門走到精通。
- 超出本篇成果的內容必須列入範圍外清單。

## Good Example

- 一句話包含四個要素，只要求讀者學會一種做法。

| 要素       | 內容                                         |
| ---------- | -------------------------------------------- |
| 誰         | 會寫 Dockerfile 的後端工程師                 |
| 多少時間內 | 30 分鐘內                                    |
| 相信什麼   | 映像檔大多被 build 工具佔掉                  |
| 做到什麼   | 用 multi-stage build 把映像檔縮小到原本的一半以下 |

- 範圍外：distroless 映像檔、layer 快取順序、映像檔安全掃描。

## Bad Example

- 同一個主題缺少時間與相信什麼，範圍也從入門一路排到 distroless 與安全掃描。

| 要素       | 內容                                                          |
| ---------- | ------------------------------------------------------------- |
| 誰         | 後端工程師                                                    |
| 多少時間內 | （缺少）                                                      |
| 相信什麼   | （缺少）                                                      |
| 做到什麼   | 精通映像檔最佳化，包含 multi-stage、distroless、layer 快取與安全掃描 |

# Rule 2 - 受眾詞彙表每類必須有 3–5 個詞

- 已懂的詞、容易誤解的詞、一定要先定義的詞，每類必須有 3–5 個詞。
- 正文使用讀者尚未懂、且為理解本段所需的新詞前，必須先定義該詞。

## Good Example

- 三類各有 3–4 個詞。

| 類別             | 詞彙                                             |
| ---------------- | ------------------------------------------------ |
| 已懂的詞         | `Dockerfile`、`docker build`、映像檔、容器       |
| 容易誤解的詞     | stage（以為是部署階段）、base image、`COPY`      |
| 一定要先定義的詞 | layer、`docker history`、`COPY --from`           |

## Bad Example

- 同一個主題，已懂的詞只有 1 個，一定要先定義的詞多達 7 個。

| 類別             | 詞彙                                                                       |
| ---------------- | -------------------------------------------------------------------------- |
| 已懂的詞         | Docker                                                                     |
| 容易誤解的詞     | stage、base image、`COPY`                                                  |
| 一定要先定義的詞 | layer、`docker history`、`COPY --from`、distroless、alpine、musl、BuildKit |

# Rule 3 - 專家方法必須寫出具體做法

- 原始資料、工具或步驟必須寫出具體名稱，例如檔案、指令、工具或資料來源。
- 不得只把一般做法改寫成專家的口吻。

## Good Example

- 每一項都指出可以照著找到的資料或指令。

- 從哪些原始資料開始：`docker history my-app:latest` 的 `SIZE` 欄位、專案的 `Dockerfile`。
- 用哪些工具或步驟：`docker images` 量大小、`COPY --from=build` 只複製編譯產物。
- 做哪些一般人沒想到的事：先看哪一層最大再動手，而不是先換 base image。

## Bad Example

- 同一個主題只有口吻像專家，讀者找不到任何可以執行的做法。

- 從哪些原始資料開始：資深工程師會先全面檢視映像檔的結構。
- 用哪些工具或步驟：運用業界最佳實踐，從根本思考最佳化策略。
- 做哪些一般人沒想到的事：用系統化思維看待映像檔。

# Rule 4 - 教學結構必須符合成果類型

- 解釋或判斷成果必須規劃概念關係、推理與判斷依據；不得為湊操作形式加入無關動作。
- 操作成果必須規劃可執行流程，檢查定義、找資料、準備、確認、執行、監控、修正及收尾是否漏掉必要工作；不適用者必須說明理由。
- 步驟數必須由完成任務所需工作決定。

## Good Example

- 自製書目例依判斷成果安排關係，沒有加入無關操作。

1. 解釋同名作品與同一作品的差別。
2. 比較作者、版本及缺值的影響。
3. 用兩筆同名書資料判斷能否合併。

## Bad Example

- 同一判斷成果被換成無關操作，作者與版本關係未教。

1. 安裝書目管理工具。
2. 按新增按鈕。
3. 截圖並上傳。

# Rule 5 - 解說與檢核必須循序對應成果

- 每個教學單元必須有一個主要成果與一句重點；銜接或前提段必須說明支援哪個成果。
- 解說必須先交代必要原因、前提與前後段銜接，再安排對應檢核。
- 段落必須依Rule 8的成果檢核配置，引用相應檢核位置；可以共用整合檢核，無須逐段另造題。
- 操作段落必須對應操作流程；概念段落必須對應概念關係與判斷依據。
- 練習必須運用已教內容；新增應用必須標明延伸範圍及所需前提，不得只要求閱讀或跳到未教的任務。

## Good Example

- 三列依序對應 SOP 1～3，每列只有一件小事與一句重點。

| 段落標題               | 對應 SOP 步驟 | 讀者的小練習                       | 一句重點                   |
| ---------------------- | ------------- | ---------------------------------- | -------------------------- |
| 1. 量出映像檔有多大    | 1             | 執行 `docker images` 記下大小      | 先量，才知道有沒有變小     |
| 2. 找出最大的 layer    | 2             | 執行 `docker history` 找最大的一列 | 最大的通常是 build 工具    |
| 3. 拆成兩個 stage      | 3             | 改寫 `Dockerfile` 後重新 build     | runtime 只需要編譯產物     |

## Bad Example

- 同一份 SOP，第 1 列同時對應兩個步驟，第 2 列的小練習只是閱讀，重點也超過一句。

| 段落標題               | 對應 SOP 步驟 | 讀者的小練習           | 一句重點                                                 |
| ---------------------- | ------------- | ---------------------- | -------------------------------------------------------- |
| 1. 量出大小並找出 layer | 1、2          | 執行兩個指令           | 先量再找。最大的通常是 build 工具。                      |
| 2. 拆成兩個 stage      | 3             | 閱讀官方文件的範例     | runtime 只需要編譯產物。這樣可以縮小映像檔。也更安全。   |

# Rule 6 - 範圍必須由成果必要性判斷

- 內容必要性必須以已讀素材與本篇承諾成果為比較基準。
- 新增案例、練習與重複解說必須逐項交代具體理解缺口或新增用途、可沿用的既有解說或課內例、額外術語／設定／資料負擔，以及刪除後缺少的解釋或判斷依據。
- 比較後必須決定保留、縮短／合併或待刪減，並保存理由；同一材料多次出現可以合列位置及各次用途。
- 只有「較生動」「讓題目有答案」且未指出課程理解收益時，理由必須列待補；無新增用途的重述必須列待刪減。
- 對理解成果必要的前提、推理與對照例必須保留；新增材料有具體收益且負擔必要時，可以展開。
- 不得以固定字數、案例數或題數取代必要性比較。
- 未選入文章的原收穫必須保留；範圍外延伸必須列明與本篇成果的差異。

## Good Example

- 自製書目教材依新增判斷用途與負擔選材。

| 內容 | 理解收益與負擔 | 刪除影響 | 處置 |
| --- | --- | --- | --- |
| 同名不同作者例後新增缺作者例 | 補證據不足時暫緩合併的判斷；只增加一個缺值 | 會缺少暫緩合併的對照依據 | 保留 |
| 表格後逐字復述兩筆資料 | 表格已提供相同資訊，無新增用途 | 不影響辨識作者差異 | 合併，刪除逐字重述 |
| 結尾準則索引 | 協助回找已教判準，不重列資料 | 少了回找入口 | 保留短連結 |

## Bad Example

- 相同書目教材只證明題答相符，沒有比較對課程理解的收益。

1. 以「增加真實感」加入借還書紀錄、日期與費用。
2. 為新增資料再造三題，答案全部可從紀錄抄出。
3. 以「每題都有答案」保留全部資料及表後重述，未交代對同名書判斷的用途。

# Rule 7 - 全貌筆記與第一步必須可取用

- 全貌筆記必須讓讀者回想概念關係、取用判斷準則或重跑操作流程，形式必須配合成果類型。
- 今天就能做的第一步必須符合讀者現有知識、資料及工具前提；可以是解釋、判斷或操作。

## Good Example

- 第一步只需要讀者已經裝好的 Docker。

- 今天就能做的第一步：對你的專案執行 `docker images`，記下映像檔目前的大小。

## Bad Example

- 同一篇的第一步需要團隊決策與 CI 權限，讀者今天做不到。

- 今天就能做的第一步：制定公司的映像檔規範，並導入 CI 自動檢查。

# Rule 8 - 成果與三種用途必須各有可觀察的檢核

- 每項解釋、判斷或操作成果必須有對應檢核及答案或判準；同一整合檢核可以涵蓋多項成果，銜接段可以引用其位置。
- 文件檢查必須分列結構、課程／素材貼合及內容必要性；必要性必須依Rule 6判定。
- 整體內容品質必須在三項均通過時才列通過；任一項未通過時必須列未通過，優先於待補；其餘缺理由或依據時必須列待補。保留待刪減重述時，內容必要性及整體內容品質必須維持未通過。
- 自用必須檢查能否找回來源、觀念解說、適用步驟及提示詞。
- 教學文件判斷必須同時檢查內容品質，以及讀者能否只依文章前提與解說完成成果檢核。
- 搜尋必須檢查問題、標題及相關文章連結是否相符；沒有既有相關文時必須如實記錄。
- 三種用途必須分別列通過、未通過或待補及其依據與缺口，不得以曝光或篇幅代替教學檢查。
- 使用者驗證必須另列實際狀態與回覆／紀錄來源；讀者效果標示必須依已載入的證據Rule 3處理。
- 作者採用與內容品質必須分開記錄；作者保留缺口時必須如實保留品質判定。
- 不得以「感覺清楚」「讀起來順」等感受作為外部標準。

## Good Example

- 自製書目教材有完整題答，仍依實際重述缺口分列品質與效果。

| 項目 | 結果與依據 |
| --- | --- |
| 成果檢核 | 同名不同作者與缺作者兩種判斷共用一題，答案含保留兩列及待查判準 |
| 結構／素材貼合 | 均通過，章節齊全且主張對回素材 |
| 內容必要性／整體內容品質 | 均未通過，表後逐字重述仍待刪減 |
| 教學文件 | 未通過，內容品質尚有缺口 |
| 使用者驗證 | 未執行；待請書目整理新手判斷兩組資料並說明依據 |

## Bad Example

- 同一教材忽略重述，且把文件檢查擴成真人結果。

1. 題目與答案齊全，就將教學及整體內容品質列通過。
2. 作者選擇保留表後重述，就把必要性改列通過。
3. 未取得讀者回答，便將使用者驗證列通過。

# Rule 9 - 讀者提示詞必須有適用理由

- 必須逐項判斷讀者工作是否適合 AI 協助，並將讀者任務與作者產製文章的任務分開。
- 不適用時必須說明具體理由，不得為湊格式加入提示詞。

## Good Example

- 自製書目例的提示詞協助讀者比較資料，適用理由可判斷。

- 任務：比較二十筆同名書的作者與版本。
- 適用：AI 可整理候選差異，讀者再核對原始書目。

## Bad Example

- 同一任務附上作者寫稿指令，讀者無法用它整理書目。

- 任務：比較二十筆同名書。
- 提示詞：請替我寫一篇吸引人的書目整理文章。

# Rule 10 - 讀者提示詞必須交付同一任務的完整使用鏈

- 適用的提示詞必須交代輸入、完整可複製指令、執行方式、預期輸出及核對方法，並對回文章段落。
- 輸入、指令、例子、輸出及核對必須接續同一個任務；轉換任務時必須交代前提。
- 提示詞必須放在讀者需要的步驟，全文結尾必須提供可回找的位置索引。

## Good Example

- 自製書目例從原資料到核對都處理同名書差異。

1. 輸入：兩筆「旅行」，作者分別為甲與乙。
2. 指令：「逐筆列書名、作者與版本；缺值寫待查，不自行合併。指出哪些欄位不同。」
3. 執行：把資料與指令一起貼入聊天視窗。
4. 預期：保留兩列，指出作者不同，版本待查。
5. 核對：逐欄比對原資料；結尾索引連回「比較同名書」段落。

## Bad Example

- 同一份資料跳到推薦購書，缺少原任務輸出與核對方法。

1. 輸入：兩筆「旅行」。
2. 指令：「推薦最值得買的版本。」
3. 結果：直接採用 AI 推薦，未核對作者或版本。
