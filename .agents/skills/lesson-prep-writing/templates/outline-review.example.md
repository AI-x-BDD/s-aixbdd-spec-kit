## 2. 候選完整大綱（套用全部建議，待作者採用）

# 備課大綱：用 JPA 樂觀鎖擋住重複預約

- 狀態：候選，待作者採用

## 1. 動詞版定義

讓會用 Spring Data JPA 寫 CRUD 的後端工程師，在 20 分鐘內相信「先讀再寫」的程式會讓同一個名額被搶兩次，並用 `@Version` 擋住它。

### 範圍外（留待下一篇）

- Redis 分散式鎖
- 悲觀鎖 `SELECT ... FOR UPDATE`
- 搶輸的一方要重試還是回傳錯誤訊息
- 用 JMeter 等工具做壓力測試

## 2. 受眾詞彙表

| 類別             | 詞彙                                                         |
| ---------------- | ------------------------------------------------------------ |
| 已懂的詞         | `@Entity`、`JpaRepository`、`@Transactional`、JUnit 測試     |
| 容易誤解的詞     | 交易（以為加上 `@Transactional` 就能擋住同時寫入）、樂觀鎖（以為會鎖住資料列）、同時 |
| 一定要先定義的詞 | `CountDownLatch`、版本號（`@Version`）、`OptimisticLockingFailureException` |

## 3. 專家方法

### 從哪些原始資料開始

- 預約服務 `SlotService.reserve()` 的原始碼
- 兩個執行緒同時呼叫 `reserve(1L)` 的測試輸出（待補證據：未加 `@Version` 時 `ConcurrentReserveTest` 的輸出）

### 用哪些工具或步驟

- JUnit 5 與 `ExecutorService` 開兩個執行緒
- `CountDownLatch` 讓兩個執行緒同時出發
- Spring Data JPA 的 `@Version`

### 做哪些一般人沒想到的事

- 不靠手動在兩個終端機送 `curl`，而是用 `CountDownLatch` 讓兩個執行緒卡在同一條起跑線，問題才能穩定重現。
- 先寫出會失敗的測試證明問題存在，再加上 `@Version`，用同一個測試證明修好了。

## 4. 概念關係／操作流程

1. 寫出「先讀再寫」的 `reserve()`，把名額設成 1。
2. 用 `CountDownLatch` 讓兩個執行緒同時呼叫 `reserve(1L)`，記錄兩邊結果，不預設每次都成功。
3. 在 `Slot` 加上 `@Version`，重跑同一個測試，確認只有一邊成功。

## 6. 全貌筆記

1. 找出「先讀再寫」的欄位。
2. 用 `CountDownLatch` 讓兩個執行緒同時執行。
3. 在 entity 加上 `@Version`。
4. 重跑同一個測試，確認只有一方成功。

### 今天就能做的第一步

在你的專案找一個「先讀再寫」的欄位，寫一個用 `CountDownLatch` 同時呼叫兩次的測試。

## 4. 紅隊仍認為有風險的地方

1. 「## 7. 外部標準」：要求讀者「未加 `@Version` 時看到兩個執行緒都成功」，但兩個執行緒不保證每次都讀到同一個值；讀者某次只看到一邊成功時，可能以為自己的程式沒有問題。
2. 「3. 加上 `@Version` 再搶一次」：加上 `@Version` 後，搶輸的一方會拋出 `OptimisticLockingFailureException`，詞彙表把它列為一定要先定義的詞，但這一段沒有規劃說明這個例外代表什麼，讀者可能把它當成測試失敗。
3. 「## 3. 專家方法」的「從哪些原始資料開始」：未加 `@Version` 時的測試輸出仍是待補證據；作者重跑測試前，第 2 段的重點與外部標準都建立在尚未取得的輸出上。
