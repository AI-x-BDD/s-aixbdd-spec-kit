# Rule 1 - 評級與結論必須依門檻決定

- 評分表的每項準則必須評為 `strong`、`adequate`、`weak`、`unknown` 其中一個。
- 每項準則的理由必須引用前四段的具體發現，例如來源、先例名稱、目標或方案，不得只寫評級的同義詞。
- 沒有證據可以判斷時，該準則必須評為 `unknown`；證據顯示不成立或不足時，必須評為 `weak`。
- 結論必須先判斷 kill；符合下列任一項時，結論必須為 `kill`：
  - 問題成立度為 `weak`。
  - 反對證據顯示構想無法達成目標。
  - 可行性與投入規模為 `weak`，而且所有方案都無法縮小到可行的規模。
- 不是 kill 時，問題成立度與證據強度都至少 `adequate`、方案構想段有推薦方案，而且沒有阻擋問題時，結論必須為 `go`。
- 不符合 kill 與 go 的情況，結論必須為 `needs-clarification`。
- 阻擋問題指回答不同時結論會改變的待確認問題；回答只影響規格細節的問題不是阻擋問題。
- 判定理由必須寫出結論符合哪一個門檻條件。

## Good Example

- 構想：大學生家教媒合網站。每項理由引用具體發現；不是 kill，問題成立度與證據強度都是 `adequate`，有推薦方案，待確認問題只影響規格細節，因此結論為 `go`。

| 準則 | 評級 | 理由 |
| ---- | ---- | ---- |
| 問題成立度 | adequate | 證據研究找到 2 個仍在營運的家教媒合平台，需求存在；目標族群的人數沒有資料。 |
| 證據強度 | adequate | 先例已抓取官方頁面；需求面的人數是 `ASSUMPTION`。 |
| 價值與不做的代價 | adequate | 不做時家長仍可用現成平台，主要價值是練習目的。 |
| 可行性與投入規模 | strong | 方案 A 為 small，可在 2 次迭代內完成。 |
| 策略契合度 | adequate | 符合問題定義段的目標「單人可完成的練習題」。 |
| 風險掌握度 | adequate | 金流與身分驗證列為不在範圍內。 |

- 判定理由：結論為 go。沒有符合 kill 的條件；問題成立度與證據強度皆為 adequate，有推薦方案 A；「每堂課的時長」只影響規格細節，帶到交接段的待確認問題。

## Bad Example

- 同一個構想，問題成立度是 `unknown`，結論卻寫 `go`；理由只寫評級的同義詞，判定理由沒有寫出符合的門檻條件。

| 準則 | 評級 | 理由 |
| ---- | ---- | ---- |
| 問題成立度 | unknown | 不確定。 |
| 證據強度 | adequate | 證據還可以。 |

- 判定理由：結論為 go，構想看起來可行。

# Rule 2 - 整體證據信心必須依主要發現的信心決定

- 主要發現指評分表中問題成立度與證據強度的理由所引用的發現。
- 主要發現都是 high，而且都已抓取或來自專案檔案時，整體證據信心必須為 `high`。
- 主要發現多數是 `ASSUMPTION` 或信心為 low 時，整體證據信心必須為 `low`。
- 不符合 `high` 與 `low` 的情況，整體證據信心必須為 `medium`。

## Good Example

- 構想：大學生家教媒合網站。主要發現有 2 個已抓取、信心 high 的先例，以及 1 個 `ASSUMPTION` 的人數推估；不是全部 high，也不是多數 `ASSUMPTION`，因此為 `medium`。

| 主要發現 | 來源 | 信心 |
| -------- | ---- | ---- |
| 先例甲仍在營運 | 已抓取的官方頁面 | high |
| 先例乙仍在營運 | 已抓取的官方頁面 | high |
| 目標族群的人數 | `ASSUMPTION` | low |

- 整體證據信心：medium。

## Bad Example

- 同一組主要發現含有 `ASSUMPTION`，整體證據信心卻寫成 `high`。

| 主要發現 | 來源 | 信心 |
| -------- | ---- | ---- |
| 先例甲仍在營運 | 已抓取的官方頁面 | high |
| 先例乙仍在營運 | 已抓取的官方頁面 | high |
| 目標族群的人數 | `ASSUMPTION` | low |

- 整體證據信心：high。

# Rule 3 - 判定段與檔頭必須和結論相符

- 判定段必須只保留和結論相符的一段，另外兩段的標題與內容必須整段刪除：
  - `go`：只保留「交接給 `s-specify`」。
  - `needs-clarification`：只保留「阻擋問題與要補的段落」。
  - `kill`：只保留「決定性理由」。
- `go` 的條列中，問題取自問題陳述，採用方案取自推薦方案，範圍取自推薦方案與其不在範圍內的項目，成功指標取自成功指標。
- `go` 的帶到規格的待確認問題，必須收集構想收件的初步未知事項、證據研究的缺口與待確認問題，以及問題定義段的待確認問題；重複的項目只列一次；必須去除報告中已解答的項目，以及只關於先例或來源查證、不影響規格內容的項目。
- `go` 的指令區塊中，功能描述必須寫出問題、採用方案、範圍（含不做的項目），並列出交接條列中成功指標與帶到規格的待確認問題的每一項。
- `go` 的功能描述不得引用報告檔的路徑，也不得寫「詳見報告」等要讀者另外讀檔的文字。
- `needs-clarification` 的每個阻擋問題必須以 `[NEEDS CLARIFICATION: …]` 寫出，並在同一條列寫出回答後要補的報告段落名稱。
- `kill` 的決定性理由必須寫出符合的 kill 條件，並引用造成 kill 的評級與證據來源。
- `kill` 的決定性理由可以寫出另提構想時可參考的方案。
- 結論為 `kill` 時，檔頭的推薦方案必須寫「無（kill）」；方案構想段的推薦方案保留不變。

## Good Example

### Example 1

- 構想：自動讀取個人 LINE 帳號訊息並轉發到 Email 的工具。結論為 `kill`，檔頭的推薦方案寫「無（kill）」；判定段只有「決定性理由」，並寫出符合的條件、評級與證據來源。

```markdown
- **結論**：kill
- **推薦方案**：無（kill）

### 決定性理由

符合 kill 條件「反對證據顯示構想無法達成目標」：構想要自動讀取個人帳號的訊息，但服務條款禁止以自動化程式存取個人帳號（來源：已抓取的服務條款頁面）；可行性與投入規模評為 weak，方案 A、B 都需要存取個人帳號，沒有可縮小的方案。
```

### Example 2

- 構想：社區共乘媒合。結論為 `needs-clarification`，判定段只有「阻擋問題與要補的段落」，每個問題都寫出要補的段落。

```markdown
### 阻擋問題與要補的段落

- [NEEDS CLARIFICATION: 共乘是否收費？收費會牽涉營業登記，可能使可行性變成 weak] — 要補的段落：證據研究的「資料與限制」、方案構想
- [NEEDS CLARIFICATION: 目標社區是否已有 LINE 群組在做共乘？] — 要補的段落：證據研究的「先例」、問題定義的問題陳述
```

### Example 3

- 構想：大學生家教媒合網站。初步未知事項有「家教可教的年級範圍」、「每堂課的時長」；證據研究的缺口有「平台乙的媒合費是否屬實」、「時薪由平台規定還是家教自訂」；問題定義段的待確認問題有「每堂課的時長」、「學生能否同時向多位家教申請」。交接段合併重複的「每堂課的時長」，去除只關於先例查證的「平台乙的媒合費是否屬實」；指令區塊列出每個成功指標與待確認問題。

```markdown
- **成功指標**：學生 3 步內送出媒合申請；每筆申請都有處理狀態
- **帶到規格的待確認問題**：家教可教的年級範圍；每堂課的時長；時薪由平台規定還是家教自訂；學生能否同時向多位家教申請
```

```text
讀取 `.agents/skills/s-specify/SKILL.md` 並依其 SOP 執行。功能描述：做一個大學生家教媒合網站，解決學生找不到合適家教的問題。採用方案 A：學生依科目與地區篩選家教並送出媒合申請，家教接受或婉拒。不做金流、身分驗證與評價機制。成功指標：學生 3 步內送出媒合申請、每筆申請都有處理狀態。待確認：家教可教的年級範圍、每堂課的時長、時薪由平台規定還是家教自訂、學生能否同時向多位家教申請。
```

## Bad Example

### Example 1

- 同一個 LINE 轉發構想，結論為 `kill`，檔頭仍寫推薦方案；判定段保留了交接段；決定性理由只寫結論，沒有寫出符合的條件、評級與證據。

```markdown
- **結論**：kill
- **推薦方案**：A — 桌面版自動轉發工具

### 交接給 `s-specify`

- **問題**：LINE 訊息不方便備份。

### 決定性理由

這個構想不值得做。
```

### Example 2

- 同一個共乘構想，結論為 `needs-clarification`，阻擋問題沒有寫成 `[NEEDS CLARIFICATION: …]`，也沒有寫出要補的段落。

```markdown
### 阻擋問題與要補的段落

- 收費方式還不確定。
- 不知道社區有沒有現成做法。
```

### Example 3

- 同一個家教構想，待確認問題只取問題定義段，漏掉初步未知事項的「家教可教的年級範圍」與證據缺口的「時薪由平台規定還是家教自訂」；指令區塊漏寫成功指標「每筆申請都有處理狀態」。

```markdown
- **成功指標**：學生 3 步內送出媒合申請；每筆申請都有處理狀態
- **帶到規格的待確認問題**：每堂課的時長；學生能否同時向多位家教申請
```
