# SOP

## Phase 1 -- 確認評估報告

1. `READ` 使用者指定的代號或路徑，列出 `specs/bugs/` 底下各代號目錄、其中的 `assessment.md`、`fix.md` 與 `assessment.md` 的核准狀態，並執行 `git status --short --untracked-files=all`，建立「候選清單」與「變更基準」。
2. `THINK` 決定「修正目錄」與「解析方式」：使用者有指定時用 `specs/bugs/<代號>/`（明確指定）；沒有指定、而且同一個對話中上一個 bug Skill 回報的代號目錄有 `assessment.md` 時用該目錄（沿用對話）；都沒有時，用「候選清單」中唯一一個有 `assessment.md`、沒有 `fix.md` 的目錄（唯一候選）；把「修正目錄」中的 `assessment.md` 記為「評估報告」，`fix.md` 記為「修正報告路徑」。
3. `CHECK` 「評估報告」不存在時，請使用者先執行 `bug-assess` 並停止；沒有明確指定、沒有沿用對話，而且有多個目錄符合時，列出這些目錄與各自的核准狀態、已有的報告，請使用者指定並停止。
4. `READ` 「評估報告」全文，建立「修正契約」：判定、核准狀態、核准段（核准的修法、核准執行的命令、不在本次修正範圍）、澄清紀錄、修法首選的各項與已套用的標示、可疑程式路徑、根本原因假設、要改的檔案、要補的測試、轉回 SDD 流程的項目與風險。
5. `CHECK` 判定不是「成立」、核准狀態不是「已核准（…）」或澄清紀錄有「待回答」時，回報原因與下一步（判定為待重現時接 `bug-test` 修正前實測，其他情況回到 `bug-assess` 完成澄清或核准），不修改任何檔案並停止。
6. `WRITE` 「修正報告路徑」已存在時，詢問使用者是否覆寫。
7. `CHECK` 「修正報告路徑」已存在時檢查使用者回覆：同意覆寫時繼續；拒絕或未回覆時不修改任何檔案並停止。

完成條件：已取得「變更基準」、「解析方式」、「修正契約」與尚未被占用或已同意覆寫的「修正報告路徑」，評估報告已核准且沒有待回答的問題。

## Phase 2 -- 套用核准修法

1. `READ` `templates/fix.md` 與 `templates/fix.example.md`，建立「修正報告樣板組」。
2. `READ` 實作修法時，讀取 `rules/修正範圍-格式規範.md` 的所有 Rule，建立「修正範圍檢查清單」。
3. `WRITE` 依「修正契約」與「修正範圍檢查清單」寫出「實作計畫」：每個要實作的修法項目寫一點，寫出要改的檔案；依「修正報告樣板組」把只填好開頭欄位與實作計畫段的初稿寫入「修正報告路徑」，並向使用者展示，不等待回覆；從本步驟到 Phase 3 結束，不向使用者提問。
4. `READ` 依「修正契約」的可疑程式路徑與根本原因假設驗證根本原因：讀取相關程式，必要時執行不改變檔案或資料的命令，建立「根因驗證」。
5. `CHECK` 依「修正範圍檢查清單」判斷「根因驗證」：屬於判斷錯誤時，把新發現記入「偏離紀錄」，不修改程式，進入 Phase 3；其他情況進入步驟 6。
6. `WRITE` 依「修正契約」、「實作計畫」與「修正範圍檢查清單」，實作下一個修法項目，並新增或修改該項目對應的測試。
7. `CHECK` 依「修正範圍檢查清單」判斷本項目和「修正契約」的差異：屬於補充時記入「偏離紀錄」後繼續；屬於判斷錯誤時把新發現記入「偏離紀錄」，停止修改程式並保留已改的內容，進入步驟 8；還有未實作的修法項目時返回步驟 6，全部完成時進入步驟 8。
8. `DELEGATE` 執行「修正契約」中要補的測試列出的測試與命令，以及涵蓋修改檔案的既有測試（在測試目錄以 `grep -rl` 搜尋修改檔案的模組名稱），取得「驗證結果」；會刪除、覆寫既有資料或需要對外網路的命令，只執行「修正契約」中核准執行的命令，其他不執行並記入「驗證結果」。
9. `CHECK` 已因判斷錯誤停止時，只把失敗記入「驗證結果」並進入 Phase 3；「驗證結果」有本次修改造成的失敗時，依「修正範圍檢查清單」修正後返回步驟 8，最多 3 輪；第 3 輪仍失敗時，記入「偏離紀錄」為判斷錯誤並進入 Phase 3；失敗的測試沒有涉及本次修改的檔案與行為時，視為和本次修改無關，只記入「驗證結果」，不修改。

完成條件：實作計畫已寫入修正報告；每個要實作的修法項目都已實作，「驗證結果」沒有本次修改造成的失敗；或已因判斷錯誤停止，新發現已記入「偏離紀錄」，已修改程式時也已取得「驗證結果」。

## Phase 3 -- 修正報告與回報

1. `WRITE` 依「修正報告樣板組」、「修正範圍檢查清單」、「修正契約」、「實作計畫」、「偏離紀錄」與「驗證結果」，完成「修正報告路徑」中的修正報告，保留實作計畫段；狀態：要實作的修法項目全部完成且沒有判斷錯誤時寫「已套用」，因判斷錯誤停止且已修改程式時寫「部分套用」，因判斷錯誤停止且沒有修改程式時寫「未套用」。
2. `CHECK` 確認修正報告的標題、開頭欄位與表格欄位和「修正報告樣板組」一致，沒有殘留 `{{`，實作計畫段的點數等於要實作的修法項目數；執行 `git status --short --untracked-files=all` 和「變更基準」比對，確認本 Skill 造成的變更只有「修正範圍檢查清單」允許的檔案與「修正報告路徑」，而且沒有 commit；修正報告未通過時修正後重新檢查；有其他由本 Skill 造成的變更（包含測試產生的暫存檔）時進入步驟 3，沒有時進入步驟 4。
3. `WRITE` 還原步驟 2 找到的其他變更，然後返回步驟 2。
4. `WRITE` 向使用者回報「修正報告路徑」、「解析方式」、狀態、修改的檔案、驗證結果、偏離與未執行的項目，並給出下一步：狀態為「已套用」時接 `bug-test`；為「部分套用」或「未套用」時，依偏離重新執行 `bug-assess`。

完成條件：修正報告已寫入「修正報告路徑」並通過步驟 2 的檢查，已向使用者回報下一步。
