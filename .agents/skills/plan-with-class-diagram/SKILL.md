# SOP

## Phase 1 -- 設計並產出類別圖提案

1. `READ` 使用者需求，以及需求涉及的既有程式碼與測試（沒有既有程式碼時視為空），建立「程式碼現況」。
2. `THINK` 依使用者需求與「程式碼現況」，盤點會改變類別、成員或關係設計的缺漏、矛盾與歧義，建立「設計缺口」。
3. `DELEGATE` 「設計缺口」不為空時，委派 `clarify` Skill（無法以 Skill 工具呼叫時，讀取 `clarify` 的 `SKILL.md` 並依其 SOP 執行），以「設計缺口」為優先提問面向、不要求詳記問答紀錄，取得使用者已確認的決策，建立「澄清決策」；「設計缺口」為空時略過本步驟。
4. `READ` 設計類別圖提案時，讀取 `rules/類別圖提案-格式規範.md` 的所有 Rule，建立「提案檢查清單」。
5. `THINK` 依使用者需求、「程式碼現況」、「澄清決策」與已載入的「提案檢查清單」，決定類別圖納入的類別、類別與成員及關係的變更狀態、設計說明與實作順序。
6. `READ` `templates/class-diagram-proposal.md` 與 `templates/class-diagram-proposal.example.md`，載入骨架與範例，命名載入結果為「類別圖提案樣板組」。
7. `WRITE` 依「類別圖提案樣板組」與步驟 5 的設計建立計畫目錄，將提案檔寫入專案根目錄下的 `specs/plan/<NN>-<計畫名稱>/class-diagram-proposal.md`；`<NN>` 為 `specs/plan/` 下既有最大兩位數編號加一，沒有既有計畫時為 `01`；`<計畫名稱>` 為描述本次功能的英文小寫 kebab-case。
8. `CHECK` 逐條驗證「提案檢查清單」，並以 Mermaid 渲染工具渲染提案檔中的類別圖，確認每個變更標記都顯示在該成員或關係標籤的最後，成員名稱與關係標籤沒有變成粗體或斜體；未通過、渲染失敗或顯示不符時修正提案檔後重新驗證。

完成條件：「設計缺口」的每一項都已由使用者決定，提案檔已寫入指定路徑，通過「提案檢查清單」，類別圖渲染後變更標記與名稱顯示正確，程式碼尚未修改。

## Phase 2 -- 確認提案

1. `WRITE` 向使用者展示提案檔路徑與完整內容，請求明確確認是否依此開發。
2. `CHECK` 使用者回覆：要求修改時依回覆返回 Phase 1 步驟 5；明確確認時進入 Phase 3；未明確確認時停止執行。

完成條件：使用者已明確確認目前版本的提案檔。

## Phase 3 -- 按圖開發與驗證

1. `READ` 已確認的提案檔與最新的相關程式碼。
2. `WRITE` 依提案檔「實作順序」逐項修改程式碼。
3. `CHECK` 程式碼中的類別、成員與關係符合已確認的類別圖，並執行專案適用的測試；需要改變類別圖才能完成時，返回 Phase 1 步驟 5 修訂提案並重新取得確認。
4. `WRITE` 向使用者回報已完成的實作順序項目與測試結果。

完成條件：程式碼符合已確認的類別圖，測試結果已回報使用者。
