# Rule 1 - 使用者故事必須是可獨立交付與驗證的使用者價值

- 每個使用者故事必須從使用者角度描述一段使用者能得到的成果，不得以技術工作或內部步驟（例如「建立資料表」、「實作 API」）作為故事。
- 只實作該故事時，必須仍能展示並驗證其價值。
- 故事少了某項前置能力，它聲稱的核心體驗就無法成立時，必須把該能力的最小版本寫進這個故事，由故事敘述、驗收情境與 FR 涵蓋，不得只靠另一個故事提供。
- 前置條件只是資料或狀態時，必須寫在驗收情境的 `Given` 或 `Independent Test` 的準備步驟；`Given` 不得預先完成該故事要驗收的成果。
- `Independent Test` 必須描述只實作該故事時的驗證方式，以及預期觀察到的結果。

## Good Example

### Example 1

- 故事描述使用者得到的瀏覽成果，獨立測試只需要這個故事就能執行並觀察結果。

```markdown
### User Story 2 - 相簿內照片平鋪式預覽 (Priority: P2)

使用者在主頁面檢視任一相簿時，相簿內的照片以平鋪式網格呈現縮圖，不需逐一點開即可瀏覽。

**Independent Test**: 開啟一個包含多張照片的相簿；驗證照片以整齊的網格排列，且會依視窗寬度調整每列張數。
```

### Example 2

- 即時協作是核心體驗，少了「加入同一張白板」就無法成立，所以以分享連結加入的最小版本寫進故事與驗收情境；白板上已有的便利貼只是狀態，寫在 `Given`。

```markdown
### User Story 1 - 與同事在同一張白板上即時協作 (Priority: P1)

使用者把白板的分享連結傳給同事，同事開啟連結後加入同一張白板；任一方新增或移動便利貼時，另一方立即看到變化。

**Independent Test**: 準備一張已有一張便利貼的白板；使用者 A 傳出分享連結，使用者 B 開啟後加入，A 新增一張便利貼；驗證 B 的畫面立即出現這張便利貼。

**Acceptance Scenarios**:

1. **Given** 使用者 A 開著一張白板，**When** 使用者 B 開啟 A 傳來的分享連結，**Then** B 進入同一張白板並看到 A 的游標。
2. **Given** A 與 B 在同一張白板上，且白板已有一張「待辦」便利貼，**When** A 把「待辦」便利貼拖到右側，**Then** B 的畫面上「待辦」便利貼立即移到右側。
```

## Bad Example

### Example 1

- 故事是技術工作，使用者得不到可展示的成果；獨立測試也依賴其他故事。

```markdown
### User Story 2 - 建立相簿資料表與查詢 API (Priority: P2)

建立 albums 與 photos 資料表，並提供查詢相簿照片的 API。

**Independent Test**: 等其他故事完成後一起測試。
```

### Example 2

- 加入同一張白板是即時協作成立的前提，卻只寫在 `Given`，故事敘述與驗收情境都沒有涵蓋；只實作這個故事時，使用者無法讓同事加入。

```markdown
### User Story 1 - 與同事在同一張白板上即時協作 (Priority: P1)

任一方新增或移動便利貼時，另一方立即看到變化。

**Acceptance Scenarios**:

1. **Given** A 與 B 已在同一張白板上，**When** A 新增一張便利貼，**Then** B 的畫面立即出現這張便利貼。
```

### Example 3

- `Given` 已經寫出 `Then` 要驗證的結果，這條情境沒有驗證任何事。

```markdown
1. **Given** A 與 B 在同一張白板上，且 B 的畫面已顯示 A 剛新增的便利貼，**When** A 新增這張便利貼，**Then** B 的畫面出現這張便利貼。
```

# Rule 2 - 優先級必須依使用者價值排列並寫出理由

- 優先級必須依使用者價值排列：`P1` 必須是功能描述中使用者最想得到的核心體驗，其餘故事依對使用者的重要程度排列。
- 本故事依賴其他故事，或其他故事依賴本故事，都不得作為排序理由。
- 優先級不得只依需求描述中出現的順序決定。
- 每個故事的 `Why this priority` 必須以使用者價值說明排序理由，不得只重述優先級。
- 故事需要其他故事先提供的能力或資料時，`Why this priority` 必須在價值理由之後寫「實作前提：<前提>；不影響本故事優先級」；沒有這種前提的故事不寫這句。

## Good Example

- 依使用者想得到的成果排序；拖放需要已分組的相簿與平鋪預覽，寫成實作前提，不作為排序理由。

| 故事 | 優先級 | Why this priority |
| ---- | ------ | ----------------- |
| 將照片整理至依日期分組的單層相簿 | P1 | 使用者要的就是把照片整理進相簿，並依日期找到它們，這是本功能最核心的成果 |
| 在主頁面上透過拖放重新排列與整理照片 | P3 | 讓使用者直覺地微調整理結果，但沒有它仍能完成整理。實作前提：需要已分組的相簿與平鋪預覽；不影響本故事優先級 |

## Bad Example

### Example 1

- 排序理由寫的是依賴：P1 因為其他故事都需要它而排第一，P3 因為依賴前面的故事而排最後，看不出使用者最想要什麼。

| 故事 | 優先級 | Why this priority |
| ---- | ------ | ----------------- |
| 將照片整理至依日期分組的單層相簿 | P1 | 核心資訊架構；沒有相簿與分組，預覽與拖放都無從運作 |
| 在主頁面上透過拖放重新排列與整理照片 | P3 | 需要已分組的相簿與預覽成立後，才能微調排列順序 |

### Example 2

- 理由只重述優先級，看不出拖放為什麼比相簿分組更重要。

| 故事 | 優先級 | Why this priority |
| ---- | ------ | ----------------- |
| 在主頁面上透過拖放重新排列與整理照片 | P1 | 這是 P1 |
| 將照片整理至依日期分組的單層相簿 | P2 | 這是 P2 |

# Rule 3 - 驗收情境必須以 Given／When／Then 描述可觀察結果

- 每條驗收情境必須包含 `Given`、`When` 與 `Then`，且 `Then` 必須描述使用者或系統可觀察的結果。
- 每條驗收情境必須只驗證一個結果。
- 每個故事的驗收情境必須涵蓋主要成功路徑，並至少包含一個例外或邊界情況。

## Good Example

- 兩條情境各驗證一個可觀察結果，第二條涵蓋相簿沒有照片的邊界情況。

```markdown
1. **Given** 某相簿內已包含多張照片，**When** 使用者檢視該相簿內容，**Then** 所有照片皆以平鋪式介面呈現清晰縮圖。
2. **Given** 某相簿內尚無任何照片，**When** 使用者檢視該相簿，**Then** 系統顯示繁體中文空白狀態提示，引導使用者新增照片。
```

## Bad Example

- 只有一條情境，同時驗證多個結果，`Then` 也無法觀察，且沒有例外或邊界情況。

```markdown
1. **Given** 使用者有相簿，**When** 使用者瀏覽、調整視窗並新增照片，**Then** 系統運作正常。
```
