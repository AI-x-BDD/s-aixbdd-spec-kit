# Rule 1 - FR 與 NFR 必須依需求性質區分並以可驗證的 MUST 陳述

- FR 必須描述系統必須提供的功能，或系統對使用者操作必須產生的反應。
- NFR 必須描述系統運作時須滿足的限制或品質，例如效能、可用性、易用性、語系或安全。
- 每條 FR 與 NFR 必須以「必須 (MUST)」陳述，並包含可驗證的條件。

## Good Example

- 拖放排序是功能，列為 FR；回饋延遲是運作品質，列為 NFR，並給出可驗證的門檻。

```markdown
- **FR-006**: 使用者必須 (MUST) 能夠在主頁面上透過拖放手勢重新排列相簿內照片的顯示順序。
- **NFR-002**: 從放開照片到畫面完成重新排版，視覺回饋延遲必須 (MUST) 低於 100 毫秒。
```

## Bad Example

- 拖放排序是功能卻被列為 NFR；另一條 FR 只描述感受，沒有可驗證的條件。

```markdown
- **NFR-002**: 使用者可以拖放重新排列照片。
- **FR-006**: 系統要讓整理照片的過程很好用。
```

# Rule 2 - 需求必須歸屬到主要服務的使用者故事

- 只服務單一使用者故事的需求，必須列在該故事底下。
- 被多個故事間接使用、但主要服務其中一個故事的需求，應歸到該故事。
- 只有無法歸屬單一故事，或明確約束多個故事的需求，才可以列在全域需求；全域需求不得作為未分類需求的預設位置。
- 每條需求必須只出現在一個位置，不得同時列在故事底下與全域需求。

## Good Example

- 平鋪預覽只服務「平鋪式預覽」故事，列在該故事底下；相簿不可巢狀同時約束「建立相簿」與「拖放整理」兩個故事，列在全域需求。

| 需求 | 服務的故事 | 位置 |
| ---- | ---------- | ---- |
| FR-005 平鋪式網格預覽照片 | 故事 2 | 故事 2 底下 |
| NFR-001 200 張照片 2 秒內呈現 | 故事 2 | 故事 2 底下 |
| FR-004 相簿維持單層、禁止巢狀 | 故事 1 的建立相簿、故事 3 的拖放 | 全域需求 |

## Bad Example

- 只屬於故事 2 的 NFR-001 被放進全域需求，FR-004 又同時出現在故事 1 底下與全域需求。

| 需求 | 服務的故事 | 位置 |
| ---- | ---------- | ---- |
| NFR-001 200 張照片 2 秒內呈現 | 故事 2 | 全域需求 |
| FR-004 相簿維持單層、禁止巢狀 | 故事 1、故事 3 | 故事 1 底下與全域需求 |

# Rule 3 - 需求編號必須唯一且不重排

- FR 必須使用 `FR-###`，NFR 必須使用 `NFR-###` 三位數格式。
- 同一份 spec 中，FR 與 NFR 的編號各自不得重複。
- 編號不得因需求在文件中的位置而重新排序；Clarifications 等處引用的編號必須指向同一條需求。

## Good Example

- 需求歸屬後保留原編號，故事 1 底下是 FR-001～FR-003、故事 2 底下是 FR-005，FR-004 在全域需求；Clarifications 的 `(FR-003)` 仍指向年月分組那一條。

```markdown
- Q: 相簿日期分組應該採用哪種時間粒度? (FR-003) → A: 依「年＋月」分組。

### User Story 2 - 相簿內照片平鋪式預覽 (Priority: P2)

- **FR-005**: 系統必須 (MUST) 在主頁面各相簿區塊預設內嵌展開平鋪式介面以預覽照片縮圖。
```

## Bad Example

- 依閱讀順序把故事 2 的 FR-005 重編為 FR-004，與全域需求的 FR-004 重複，原本指向 FR-005 的引用也失效。

```markdown
### User Story 2 - 相簿內照片平鋪式預覽 (Priority: P2)

- **FR-004**: 系統必須 (MUST) 在主頁面各相簿區塊預設內嵌展開平鋪式介面以預覽照片縮圖。

#### Functional Requirements

- **FR-004**: 系統必須 (MUST) 嚴格限制相簿為單層扁平結構。
```

# Rule 4 - 需求不得描述技術實作

- FR 與 NFR 必須描述系統要做到的行為或品質，不得指定框架、程式語言、資料庫或部署方式。
- 使用者輸入中的技術偏好不得改寫成 FR 或 NFR。

## Good Example

- 需求只要求狀態持久化保存，沒有指定如何保存。

```markdown
- **FR-009**: 系統必須 (MUST) 自動且持久化保存相簿分組、照片歸屬與自訂排列順序，重新開啟應用程式後狀態一致。
```

## Bad Example

- 同一條需求指定了資料庫與部署方式，屬於技術規劃階段的決策。

```markdown
- **FR-009**: 系統必須 (MUST) 以 Docker Compose 啟動 MySQL，保存相簿分組、照片歸屬與自訂排列順序。
```

# Rule 5 - 每條 FR 都必須有驗證它的驗收情境

- 每條 FR 必須至少有一條驗收情境，其 `Then` 驗證該 FR 規定的行為；只在 `Given` 中預設該行為已發生，不算驗證。
- 列在使用者故事底下的 FR，必須由同一個故事的驗收情境驗證。
- 全域 FR 可以由任一故事的驗收情境驗證。
- 找不到驗證它的驗收情境時，必須在所屬故事補上驗收情境，不得為了通過檢查而刪除或弱化該 FR。
- 本 Rule 只適用於 FR，不得套用到 NFR。

## Good Example

- FR-002 規定刪除前要顯示含照片數量的確認提示，同一故事有一條情境的 `Then` 直接驗證這個提示。

```markdown
1. **Given** 使用者有一個包含 12 張照片的相簿，**When** 使用者選擇刪除該相簿，**Then** 系統先顯示繁體中文確認提示，並標明相簿內有 12 張照片。

**Functional Requirements**:

- **FR-002**: 系統必須 (MUST) 在刪除仍包含照片的相簿時，先顯示標明照片數量的繁體中文確認提示，經確認後才移除相簿與其照片。
```

## Bad Example

- 同一條 FR-002 只出現在情境的 `Given`，預設相簿已被刪除，沒有任何 `Then` 驗證確認提示。

```markdown
1. **Given** 使用者已刪除一個相簿，**When** 使用者回到主頁面，**Then** 該相簿不再出現在日期分組中。

**Functional Requirements**:

- **FR-002**: 系統必須 (MUST) 在刪除仍包含照片的相簿時，先顯示標明照片數量的繁體中文確認提示，經確認後才移除相簿與其照片。
```

# Rule 6 - 未確認事項與 AI 自訂的門檻，要求系統做到時必須寫成推定需求

- 「未確認事項」的每一項都必須有本次採用的預設內容；clarify 交回的剩餘風險還沒有預設內容時，必須在寫需求之前，依需求輸入與已確認的決策先決定一個。
- 預設內容若要求系統對使用者操作或事件做出某個反應、提供某個功能，或滿足某個品質，必須寫成 FR 或 NFR，並列入「推定需求」。
- 寫 FR 或 NFR 時，為了滿足 Rule 1 的可驗證條件而由 AI 決定的數值門檻（例如時限、誤差、容量、比率），以及需求輸入、clarify 已確認的決策與使用者補充都沒有提出、由 AI 加上的品質要求（例如介面語系），所在的需求也必須列入「推定需求」。
- 需求輸入、clarify 已確認的決策或使用者補充提供的值與要求，以及由它們直接換算出來的值（例如「5 天」換算成「120 小時」），不得作為列入推定需求的理由。
- 推定需求必須與其他需求同樣適用 Rule 1～5；需求內文不得另外標示推定。
- 預設內容只描述使用者、使用環境或系統外部作業的前提，或只表示系統不對某件事加上限制時，不得寫成需求。

## Good Example

### Example 1

- 同一批未確認事項都先有預設內容再分流：clarify 沒問到的剩餘風險先決定預設內容；系統的反應與品質寫成需求並列入推定需求，使用情境前提與「不加限制」不寫成需求。

| 未確認事項 | 預設內容 | 判斷 | 寫法 |
| ---------- | -------- | ---- | ---- |
| 剩餘風險：刪除某日期分組下的最後一個相簿後，該分組標題如何處理 | 主頁移除該分組標題 | 系統對操作的反應 | 寫成 US1 的 FR-011，列入推定需求，並在 US1 補上驗證它的驗收情境 |
| 推斷：介面符合 WCAG 2.1 AA，拖放排序與跨相簿移動可僅以鍵盤完成 | 同左 | 系統須滿足的品質 | 寫成全域 NFR-004，列入推定需求 |
| 推斷：由單一使用者在個人裝置上使用 | 同左 | 使用情境前提 | 不寫成需求 |
| 推斷：不限制單一相簿的照片數量 | 同左 | 系統不加限制 | 不寫成需求 |

### Example 2

- 寫需求時逐項確認每個數值與品質要求的來源：AI 決定的門檻與 AI 加上的品質要求列入推定需求，Clarifications 已確認的值不列入。

| 需求中的內容 | 來源 | 判斷 | 寫法 |
| ------------ | ---- | ---- | ---- |
| NFR-002 的視覺回饋延遲低於 100 毫秒 | 需求輸入與 Clarifications 都沒有提到回饋延遲 | AI 決定的數值門檻 | NFR-002 列入推定需求 |
| NFR-003 所有介面文字使用臺灣繁體中文 | Clarifications 只確認錯誤提示使用繁體中文，其餘介面文字沒有提到 | AI 加上的品質要求 | NFR-003 列入推定需求 |
| FR-001 的單檔上限 20 MB | Clarifications 已確認 | 有來源 | 不因此列入推定需求 |

## Bad Example

### Example 1

- 同一批未確認事項處理錯誤：剩餘風險沒有先決定預設內容，寫需求時被略過；系統須滿足的品質只寫在 Assumptions；使用情境前提反而被寫成 FR。

| 未確認事項 | 寫法 |
| ---------- | ---- |
| 剩餘風險：刪除某日期分組下的最後一個相簿後，該分組標題如何處理 | 寫需求時因為沒有預設內容而略過，到寫 Assumptions 時才補成 FR |
| 推斷：介面符合 WCAG 2.1 AA，拖放排序與跨相簿移動可僅以鍵盤完成 | 只寫在 Assumptions，沒有 NFR |
| 推斷：由單一使用者在個人裝置上使用 | 寫成「**FR-012**: 系統必須 (MUST) 只允許單一使用者登入」 |

### Example 2

- 同一批需求的判斷錯誤：推定需求只看未確認事項，寫需求時才決定的門檻沒有列入；使用者已確認的值反而因為是數值而被列入。

| 需求中的內容 | 寫法 |
| ------------ | ---- |
| NFR-001 的 200 張照片 2 秒內呈現 | 寫成 NFR，但因為不在未確認事項中，沒有列入推定需求 |
| FR-001 的單檔上限 20 MB | 因為是數值門檻就列入推定需求，Assumptions 出現「**單檔上限 20 MB**（推定）：見 FR-001。」 |
