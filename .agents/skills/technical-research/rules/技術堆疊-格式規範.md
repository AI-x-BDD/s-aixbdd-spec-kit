# Rule 1 - 總覽表的每一列必須取自 research.md 的 Decision

- 「技術堆疊總覽」每一列的技術都必須出現在 research.md 某個主題的 `Decision` 中。
- 決策來源欄必須寫 `research §<主題編號>`；同一技術出現在多個主題時，必須合併為一列，來源以「、」並列（例如 `research §1、§2`）。
- research.md 各 `Decision` 採用的語言、框架、套件、執行環境、資料儲存與工具，都必須有對應的列。
- 只決定設計或實作方式、沒有引入技術的內容（例如資料表欄位、排序策略、API 端點）不得列入。

## Good Example

- 球場預約系統的 research.md 有兩個主題；兩個主題採用的技術各有一列，PostgreSQL 同時出現在 §1 與 §2，合併為一列；`tstzrange` 欄位與交易寫入屬於設計方式，不列。

research.md 片段：

```markdown
## 1. 後端與資料庫
- **Decision**: 後端採用 **FastAPI**，以 **Uvicorn** 執行，資料庫使用 **PostgreSQL 16**。

## 2. 預約衝突防止
- **Decision**: 以 **PostgreSQL 16** 的 `EXCLUDE USING gist` 排除約束搭配 `tstzrange` 時段欄位，防止同一球場的預約時段重疊；後端在單一交易中寫入預約。
```

techstack.md 片段：

```markdown
| 後端 | FastAPI | — | HTTP API | research §1 |
| 後端 | Uvicorn | — | ASGI 伺服器 | research §1 |
| 資料儲存 | PostgreSQL | 16 | 預約與球場資料、時段重疊約束 | research §1、§2 |
```

## Bad Example

- 同一份 research.md，總覽多列了 research 沒有採用的 SQLAlchemy；把設計決策 `tstzrange` 時段欄位列成一列；PostgreSQL 拆成兩列。

```markdown
| 後端 | FastAPI | — | HTTP API | research §1 |
| 後端 | SQLAlchemy | 2.0 | ORM | research §1 |
| 資料儲存 | PostgreSQL | 16 | 預約與球場資料 | research §1 |
| 資料儲存 | PostgreSQL | 16 | 時段重疊約束 | research §2 |
| 資料儲存 | `tstzrange` 時段欄位 | — | 記錄預約時段 | research §2 |
```

# Rule 2 - 用途與版本欄只寫事實，不寫理由

- 用途欄必須只寫該技術在本次開發負責的功能。
- 用途欄不得寫採用理由，不得引用 FR／SC 編號，也不得出現「以符合」、「因為」等理由句。
- 版本欄必須只寫 research.md 明確指定的版本或版本下限，並照 research.md 的寫法。
- research.md 沒有指定版本時，版本欄必須寫 `—`，不得依查證結果或自行判斷補上版本。

## Good Example

- research.md 只指定了「PostgreSQL 16」與「Python 3.12 以上」；這兩列照原寫法填版本，FastAPI 沒有指定版本，寫 `—`；用途欄都只寫功能。

```markdown
| 執行環境 | Python | 3.12 以上 | 後端執行環境 | research §1 |
| 後端 | FastAPI | — | HTTP API | research §1 |
| 資料儲存 | PostgreSQL | 16 | 預約與球場資料 | research §1 |
```

## Bad Example

- 同一份 research.md，FastAPI 的版本寫成 research 沒有指定的 `0.115`；PostgreSQL 的用途欄寫成理由並引用 FR-003。

```markdown
| 執行環境 | Python | 3.12 以上 | 後端執行環境 | research §1 |
| 後端 | FastAPI | 0.115 | HTTP API | research §1 |
| 資料儲存 | PostgreSQL | 16 | 以排除約束滿足 FR-003 的防重複預約 | research §1 |
```

# Rule 3 - 分層依專案實際架構命名

- 分層名稱必須依本次專案實際具備的架構部分命名。
- 不得列出專案沒有的分層。
- 同一分層的列必須相鄰排列。

## Good Example

- 球場預約的每日對帳工具只是命令列程式，沒有畫面與 HTTP 伺服器；分層只有執行環境、命令列、資料儲存與品質與測試，同層的列相鄰。

```markdown
| 執行環境 | Python | 3.12 以上 | 對帳工具執行環境 | research §1 |
| 命令列 | `argparse` | — | 解析命令列參數 | research §1 |
| 命令列 | `csv` | — | 輸出對帳報表 | research §2 |
| 資料儲存 | PostgreSQL | 16 | 讀取當日預約紀錄 | research §3 |
| 品質與測試 | pytest | — | 單元測試 | research §4 |
```

## Bad Example

- 同一個對帳工具照抄 Web 專案的分層，列出專案沒有的「前端」與「後端」；兩個「命令列」的列被資料儲存隔開。

```markdown
| 執行環境 | Python | 3.12 以上 | 對帳工具執行環境 | research §1 |
| 前端 | — | — | 無 | — |
| 後端 | — | — | 無 | — |
| 命令列 | `argparse` | — | 解析命令列參數 | research §1 |
| 資料儲存 | PostgreSQL | 16 | 讀取當日預約紀錄 | research §3 |
| 命令列 | `csv` | — | 輸出對帳報表 | research §2 |
```

# Rule 4 - 不引入清單只列被捨棄的具名技術或方案

- 「本次開發不引入的技術」每一列都必須是 research.md 某主題 `Alternatives considered` 中被捨棄、且有名稱可辨識的技術或技術方案（套件、框架、服務、建置工具、儲存方式、演算法等）。
- 決策來源欄必須指向該替代方案所在的主題。
- 替代方案只是「不使用任何套件或工具、自行撰寫同樣功能」（例如自行解析檔案格式、不用建置工具）時，不得列入。
- 不引入原因必須只寫一句摘要，不得重述該主題的 `Rationale`。
- research.md 沒有任何可列的技術時，必須保留段落標題，並以一句「本次沒有被捨棄的技術。」取代表格。

## Good Example

### Example 1

- research.md §2 捨棄了 Redis 分散式鎖與自行撰寫時段比對函式，§1 捨棄了 Firebase；清單列出兩個具名方案，不列自行撰寫的函式，原因各一句。

research.md 片段：

```markdown
## 1. 後端與資料庫
- **Alternatives considered**:
  - **Firebase Realtime Database**：屬於雲端服務，違反使用者「不要用雲端服務」的限制。

## 2. 預約衝突防止
- **Alternatives considered**:
  - **Redis 分散式鎖**：需要多部署一個服務，且鎖逾時時仍可能重複預約，違反 FR-003。
  - **自行撰寫時段比對函式**：兩個請求同時通過比對時會重複預約，違反 FR-003。
```

techstack.md 片段：

```markdown
| 技術 | 不引入原因 | 決策來源 |
| ---- | ---------- | -------- |
| Firebase Realtime Database | 使用者指定不用雲端服務 | research §1 |
| Redis 分散式鎖 | 多一個服務且仍可能重複預約 | research §2 |
```

### Example 2

- 每日對帳工具的 research.md 只有「自行撰寫 CSV 字串拼接」這類自行撰寫的替代方案；段落保留標題，以一句話取代表格。

```markdown
## 本次開發不引入的技術

本次沒有被捨棄的技術。
```

## Bad Example

### Example 1

- 同一份球場預約 research.md，清單列入自行撰寫的時段比對函式，Redis 的原因重述整段 `Rationale`。

```markdown
| 技術 | 不引入原因 | 決策來源 |
| ---- | ---------- | -------- |
| Firebase Realtime Database | 使用者指定不用雲端服務 | research §1 |
| Redis 分散式鎖 | 需要多部署一個服務，且鎖逾時時仍可能重複預約，違反 FR-003；排除約束在資料庫層保證時段不重疊，預估 `< 20ms` | research §2 |
| 自行撰寫時段比對函式 | 同時請求會重複預約 | research §2 |
```

### Example 2

- 同一個每日對帳工具，沒有可列的技術時留下只有表頭的空表格。

```markdown
## 本次開發不引入的技術

| 技術 | 不引入原因 | 決策來源 |
| ---- | ---------- | -------- |
```
