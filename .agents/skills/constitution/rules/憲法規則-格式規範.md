# Rule 1 - Rule 必須從 1 連續編號

- 落點檔的 Rule 編號必須從 1 開始連續編號。
- 新增 Rule 後，新 Rule 的編號必須接在最後一條 Rule 之後。
- 修改既有 Rule 時，不得改變任何 Rule 的編號。

## Good Example

- 落點檔原有 Rule 1、Rule 2，新增的 Rule 編號為 3。

情境：

1. `skills/api-plan/openapi.md` 原有 `# Rule 1 - 分頁參數必須使用 page 與 pageSize`、`# Rule 2 - 訂單金額欄位必須以整數的最小貨幣單位表示`。
2. 使用者新增「商品價格必須標明幣別」。
3. 新 Rule 的標題為 `# Rule 3 - 商品價格必須標明幣別`。

## Bad Example

- 新 Rule 跳號，檔案內的編號不再連續。

情境：

1. `skills/api-plan/openapi.md` 原有 Rule 1、Rule 2。
2. 使用者新增「商品價格必須標明幣別」。
3. 新 Rule 的標題為 `# Rule 5 - 商品價格必須標明幣別`。

# Rule 2 - 強度必須使用固定用詞

- 規則說明必須只用「必須」、「不得」、「應」、「可以」表達強度。
- 硬性要求必須使用「必須」；禁止行為必須使用「不得」。
- 預設應遵守、但有具體理由時可以偏離的要求，必須使用「應」；不影響合規性的選項必須使用「可以」。
- 規則說明不得使用「盡量」、「最好」或「原則上」等未定義的用詞。

## Good Example

- 每項要求只用固定用詞表達強度。

```markdown
- 訂單的建立時間欄位必須使用 ISO 8601 的 UTC 字串。
- 訂單的建立時間欄位不得使用 Unix timestamp。
```

## Bad Example

- 使用「最好」，無法判斷是否必須遵守。

```markdown
- 訂單的建立時間欄位最好使用 ISO 8601 的 UTC 字串。
```

# Rule 3 - 規則只包含使用者提出的要求

- 規則只能包含使用者提出的要求與「澄清結果」。
- 不得加入使用者沒有提出、也不在「澄清結果」中的要求，例如欄位順序、數值上限、命名格式。
- 寫成規則必須的細節缺少時，必須列入「待澄清項目」，不得自行決定。

## Good Example

- 使用者只說「訂單編號必須使用 UUID」，規則只寫這項要求。

```markdown
# Rule 1 - 訂單編號必須使用 UUID

- 訂單編號欄位必須使用 UUID 字串。
```

## Bad Example

- 規則加入使用者沒有提出的 UUID 版本與欄位位置。

```markdown
# Rule 1 - 訂單編號必須使用 UUID

- 訂單編號欄位必須使用 UUID 第 4 版字串。
- 訂單編號欄位必須放在物件的第一個欄位。
```

# Rule 4 - 範例必須使用專案情境與產出物格式

- Good Example 與 Bad Example 必須使用專案的領域情境，情境取自 `specs/` 下的文件或使用者的描述。
- 範例的程式碼區塊必須使用該產出物的實際格式，例如 OpenAPI 與 AsyncAPI 使用 YAML、資料模型使用 DBML。
- 兩個範例必須針對同一個規則重點。

## Good Example

- 規則約束 `data-model.dbml`，範例使用專案的 `orders` 資料表與 DBML。

```dbml
Table orders {
  id uuid [pk]
  created_at timestamptz [not null]
}
```

## Bad Example

- 規則約束 `data-model.dbml`，範例卻使用與專案無關的情境，且格式為 SQL。

```sql
CREATE TABLE foo (
  id SERIAL PRIMARY KEY
);
```
