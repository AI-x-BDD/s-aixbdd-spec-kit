# Rule 1 - 規則必須寫入落點表指定的檔案

- 每條規則必須寫入下表指定的憲法檔，路徑相對於專案根目錄的 `.agents/constitution/`。

  | Skill | 產出物 | 憲法檔 |
  | --- | --- | --- |
  | 全部產出物共用 | — | `shared.md` |
  | `s-specify` | `spec.md` | `skills/s-specify/spec.md` |
  | `technical-research` | `research.md` | `skills/technical-research/research.md` |
  | `technical-research` | `techstack.md` | `skills/technical-research/techstack.md` |
  | `system-analysis` | `plan.md` | `skills/system-analysis/plan.md` |
  | `api-plan` | `contracts/openapi.yaml` | `skills/api-plan/openapi.md` |
  | `api-plan` | `contracts/asyncapi.yaml` | `skills/api-plan/asyncapi.md` |
  | `data-plan` | `data/data-model.dbml` | `skills/data-plan/data-model.md` |
  | `ui-plan` | `ui/plan.md` | `skills/ui-plan/ui-plan.md` |
  | `ui-plan` | `ui/*.html` | `skills/ui-plan/ui-page.md` |
  | `tasks` | `tasks.md` | `skills/tasks/tasks.md` |
  | `implement` | 程式碼 | `skills/implement/code.md` |

- 修改產出物的其他 Skill（例如 `clarify-over-specs` 修改 `spec.md`）必須使用產出該產出物之 Skill 的憲法檔。
- 需求的目標產出物不在表內時，不得寫入；必須列入「拒絕清單」，建議先以 `skill-engineering` 接入憲法機制。

## Good Example

- 需求約束資料模型，寫入表中 `data-plan` 的 `data-model.md`。

情境：

1. 使用者要求：「訂單資料表的金額欄位必須使用整數」。
2. 目標產出物是 `data/data-model.dbml`，對應的 Skill 是 `data-plan`。
3. 落點檔案為 `.agents/constitution/skills/data-plan/data-model.md`。

## Bad Example

- 需求的目標產出物不在表內，卻自行建立新檔案寫入。

情境：

1. 使用者要求：「商品類別圖提案裡每個類別都必須寫中文說明」。
2. 目標產出物是 `plan-with-class-diagram` 的類別圖提案，不在落點表。
3. 自行建立 `.agents/constitution/skills/plan-with-class-diagram/class-diagram.md` 並寫入規則。

# Rule 2 - 只有全部產出物適用的規則才寫入 shared.md

- 規則必須適用全部產出物，而且寫法不需依產出物改變，才可以寫入 `shared.md`。
- 規則只適用部分產出物時，必須分別寫入每個產出物的憲法檔，`shared.md` 不得變更。

## Good Example

- 時間欄位規則只適用 API 合約與資料模型，因此分別寫入各自的憲法檔。

情境：

1. 使用者要求：「訂單的建立時間在 API 合約一律用 ISO 8601 的 UTC 字串，在資料庫一律用 timestamptz」。
2. 規則只適用 `openapi.yaml`、`asyncapi.yaml` 與 `data-model.dbml`，且兩種格式的寫法不同。
3. 分別寫入 `skills/api-plan/openapi.md`、`skills/api-plan/asyncapi.md` 與 `skills/data-plan/data-model.md`；`shared.md` 不變。

## Bad Example

- 規則只適用部分產出物，卻寫入 `shared.md`。

情境：

1. 使用者要求：「訂單的金額欄位必須使用整數」。
2. 規則只適用 API 合約與資料模型，不適用 `spec.md` 與 `tasks.md`。
3. 規則寫入 `shared.md`。

# Rule 3 - 流程類需求不得寫入憲法

- 要求新增流程步驟、測試、改變 Skill 執行順序或處理方式的需求，不得寫入憲法。
- 這類需求必須列入「拒絕清單」，寫出原因，並建議以 `skill-engineering` 新增或修改 Skill。
- 約束產出物內容的需求可以寫入憲法。

## Good Example

- 需求要求先寫測試才能寫程式，改變了流程，因此列入「拒絕清單」。

情境：

1. 使用者要求：「結帳功能必須先寫自動化測試才能寫程式」。
2. 這項需求改變 `implement` 的執行順序，不是約束產出物內容。
3. 列入「拒絕清單」，建議以 `skill-engineering` 新增或修改 Skill；不建立或修改任何憲法檔。

## Bad Example

- 流程需求被改寫成憲法規則並寫入。

情境：

1. 使用者要求：「結帳功能必須先寫自動化測試才能寫程式」。
2. 在 `skills/implement/code.md` 新增 `# Rule 1 - 必須先寫測試`。

# Rule 4 - 同一面向已有 Rule 時必須修改該 Rule

- 需求和落點檔中既有 Rule 規範同一個面向時，必須修改該 Rule，不得新增 Rule。
- 修改時，其他 Rule 的原文必須不變。

## Good Example

- 既有 Rule 1 已規範商品清單的分頁上限，需求改變上限，因此修改 Rule 1。

情境：

1. `skills/api-plan/openapi.md` 的 Rule 1 規定商品清單 API 的 `pageSize` 上限為 100。
2. 使用者要求：「商品清單的 pageSize 上限改成 50」。
3. 修改 Rule 1 的上限為 50；Rule 2 以後的原文不變，Rule 數量不變。

## Bad Example

- 同一個面向新增了第二條 Rule，檔案中對 `pageSize` 上限有兩個來源。

情境：

1. `skills/api-plan/openapi.md` 的 Rule 1 規定商品清單 API 的 `pageSize` 上限為 100。
2. 使用者要求：「商品清單的 pageSize 上限改成 50」。
3. 新增 `# Rule 4 - pageSize 上限必須為 50`，Rule 1 保持不變。
