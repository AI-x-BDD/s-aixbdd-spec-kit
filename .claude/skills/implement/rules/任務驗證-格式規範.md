# Rule 1 - 驗證必須依任務類型實際執行任務要求的行為

- 每個任務必須依下表選擇驗證方式並實際執行；端點、資料庫、即時事件與畫面任務不得只以「檔案已建立」或「程式能編譯」作為驗證。

| 任務類型 | 必須執行的驗證 |
| -------- | -------------- |
| 專案初始化、套件與設定檔 | 安裝依賴成功；實際執行任務描述的 script 或工具命令，確認工具讀到該設定 |
| 資料庫 schema 與 migration | 以專案的資料庫工具驗證 schema 並套用 migration；查詢產生的 SQL 或資料庫結構，確認任務要求的資料表、欄位、約束與索引都存在 |
| 後端模組與服務 | 專案已有型別檢查或 lint 命令時執行；以臨時腳本呼叫任務描述的函式，涵蓋成功情況與任務列出的每個錯誤分支 |
| HTTP 端點 | 啟動伺服器，以 HTTP 客戶端實際呼叫，確認成功時的狀態碼與回應欄位，以及任務列出的每個錯誤碼與狀態碼 |
| 即時事件（WebSocket、Socket.IO 等） | 以實際的客戶端連線觸發事件，確認事件名稱、收到的對象與 payload 欄位 |
| 前端元件與畫面 | 型別檢查與建置成功；可由程式檢查的部分（例如狀態轉換函式、元件渲染結果）以臨時腳本確認；需要操作瀏覽器的部分留到 Phase Checkpoint |
| 文件 | 逐一執行文件中的命令，確認都能成功 |

- 本任務的行為需要後面任務的產物才能端到端執行時（例如路由在後面任務才掛上），必須驗證本任務可以獨立驗證的部分，並在進度回報寫出留給哪個任務或 Checkpoint 驗證。
- 進度回報必須寫出實際執行的命令與結果摘要：通過的檢查項目，或失敗時的錯誤訊息。

## Good Example

- 診所掛號系統的任務「實作 `POST /api/appointments`：時段已被預約回 `SLOT_TAKEN`（409）」，驗證實際打了成功與錯誤兩種請求，並核對狀態碼與錯誤碼。

```text
T014 驗證：
- npm run check → 通過（tsc、eslint 無錯誤）
- 啟動伺服器後 curl -X POST /api/appointments（slotId=s-0900）→ 201，回應含 appointmentId、slotId、status="booked"
- 再以相同 slotId 呼叫 → 409，回應 { "error": { "code": "SLOT_TAKEN" } }
- 伺服器已關閉
```

## Bad Example

- 同一個端點任務只跑型別檢查就打勾，沒有確認端點實際回傳的狀態碼與錯誤碼。

```text
T014 驗證：
- npx tsc --noEmit → 通過
```

# Rule 2 - Phase Checkpoint 必須驗證整個 Phase 的成果

- Setup 的 Checkpoint 必須確認：各端依賴已安裝，Setup 任務建立的檢查、測試與建置命令都能執行；因為還沒有原始碼而無法執行的命令，必須寫出留給哪個 Phase 驗證。
- Foundational 的 Checkpoint 必須確認：各端的型別檢查與 lint 通過、後端伺服器能啟動並回應請求、前端能完成建置。
- User Story 的 Checkpoint 必須把 Independent Test 的每個步驟轉成實際執行的驗證：後端行為以 HTTP 客戶端與即時事件客戶端腳本模擬 Independent Test 中的每位使用者，依步驟走完一次。
- Independent Test 中需要操作瀏覽器的步驟，有可用的瀏覽器自動化工具時必須實際操作；沒有時必須列入完成報告的「人工驗證項目」，寫出操作步驟與預期畫面。
- 本 Phase 修改了前面 Phase 建立的檔案時，必須重新執行前面 Phase Checkpoint 中涉及這些檔案的驗證。
- Polish 的 Checkpoint 必須重新執行各端完整的檢查命令（型別檢查、lint、建置），並確認 Polish 任務要求的量測都已實際執行。

## Good Example

- 診所掛號系統 US1 的 Independent Test 是「兩位病患搶同一時段，只有一位成功，另一位看到『這個時段已經有人預約』」；Checkpoint 以腳本模擬兩位病患，並把畫面步驟列為人工驗證項目。

```text
Phase 3（US1）Checkpoint：
- 腳本以病患 A、B 各自登入，同時呼叫 POST /api/appointments（slotId=s-0900）→ A 201、B 409 SLOT_TAKEN
- A 的 WebSocket 客戶端收到 slot:updated，status="booked"
- 人工驗證項目：以兩個瀏覽器分頁操作，B 送出後畫面顯示「這個時段已經有人預約」
```

## Bad Example

- 同一個 Checkpoint 只確認 Phase 內的任務都已打勾，沒有依 Independent Test 實際走過流程，也沒有列出需要人工確認的畫面步驟。

```text
Phase 3（US1）Checkpoint：T012–T018 皆已完成，通過。
```

# Rule 3 - 驗證不得在專案中留下痕跡

- 為驗證建立的臨時腳本與測試資料檔必須放在專案目錄以外的暫存目錄，或在驗證後刪除。
- 不得為驗證在專案中新增 tasks.md 沒有要求的測試檔。
- 驗證寫入資料庫的資料應在驗證後清除；無法清除時必須在進度回報說明留下哪些資料。
- 驗證時啟動的伺服器與其他背景程序必須在驗證後結束。
- 開發用的資料庫容器可以保持運行，並必須在完成報告說明。

## Good Example

- 臨時腳本放在系統暫存目錄，驗證後關閉伺服器並清除測試預約。

```text
- 腳本 /tmp/clinic-verify/book-twice.mjs（專案外）
- 驗證後 kill 伺服器 PID 48211；DELETE FROM appointments WHERE patient_id LIKE 'verify-%'
- git status 只顯示本任務修改的 backend/src/routes/appointmentsRouter.ts
```

## Bad Example

- 同一個驗證把臨時腳本寫進專案的測試目錄並留下，伺服器也沒有關閉。

```text
- 新增 backend/tests/book-twice.test.ts（tasks.md 沒有要求）
- 伺服器仍在背景監聽 3000 埠
```
