# Rule 1 - 一次只實作目前任務

- 必須一次只完成一個任務：目前任務的實作、驗證、打勾與進度回報都完成後，才可以開始下一個任務；標 `[P]` 的任務也必須逐一執行。
- 目前任務打勾前，不得建立或修改下一個任務的檔案。
- 不得在同一個命令中處理兩個以上任務的實作、驗證或打勾，也不得以迴圈一次打勾多個任務。
- 不得跳過任何任務的實作、驗證、打勾或回報步驟。
- 必須只建立或修改目前任務描述提到的檔案與內容；依專案衛生規則補齊 ignore 檔除外。
- 修改前面任務建立的檔案時，必須只改動本任務描述要求的部分。
- 不得提前實作後面任務描述的內容，即使知道後面任務會用到。
- 不得加入任務沒有要求的功能、測試、重構或套件。
- 不得修改 tasks.md。
- 不得執行 `git commit`、`git push`，或以其他命令改寫 git 歷史。

## Good Example

- 診所掛號系統的 T012 是「在 `appointmentService.ts` 實作 `createAppointment`」：取得 T012 後只動這個檔案，驗證、打勾、回報完成，才取得 T013；路由由 T013 負責，因此 T012 先以臨時腳本直接呼叫函式驗證。

```text
next → T012
修改：backend/src/services/appointmentService.ts（新增 createAppointment）
驗證：臨時腳本呼叫 createAppointment → 成功與 SLOT_TAKEN 兩種情況通過
check T012
T012 已通過，回寫後繼續下一個任務
next → T013
```

## Bad Example

- 同一批任務在一個命令中一起寫完 T012–T014 的檔案、整批驗證後以迴圈打勾，還順手加了任務沒要求的單元測試並建立 commit。

```text
cat > appointmentService.ts …; cat > appointmentsRouter.ts …; cat > AppointmentView.vue …
npm run check
for t in T012 T013 T014; do check $t; done
新增 backend/tests/unit/appointmentService.test.ts
git commit -m "feat: appointments"
```

# Rule 2 - 對外可見的識別字必須與上游逐字相同

- 下列識別字必須與任務描述或任務參考部位的寫法逐字相同，包含大小寫、標點與全半形：API 路徑與 HTTP 方法、錯誤碼、HTTP 狀態碼、事件名稱、請求與回應欄位、資料表與欄位名稱、Enum 值、畫面上的文字與提示。
- 只在程式內部使用的名稱（函式、區域變數、內部型別、檔案內的常數）可以自行命名。
- 任務描述與參考部位對同一識別字的寫法不同，或上游缺少需要的對外識別字時，必須依自主決策檢查清單決定並記錄，不得未經記錄自行命名。

## Good Example

- 合約寫 `SLOT_TAKEN`（409），ui/plan.md 寫「這個時段已經有人預約」，程式照抄；內部函式名稱自行命名。

```ts
// 內部名稱自取
function assertSlotAvailable(slot: Slot) {
  if (slot.status === "booked") throw new AppError("SLOT_TAKEN", 409);
}

export const zhTW = {
  SLOT_TAKEN: "這個時段已經有人預約",
};
```

## Bad Example

- 同一段程式把錯誤碼改成駝峰式、狀態碼改成 400，畫面文字也被改寫並加上驚嘆號。

```ts
function assertSlotAvailable(slot: Slot) {
  if (slot.status === "booked") throw new AppError("SlotTaken", 400);
}

export const zhTW = {
  SlotTaken: "時段已被預約！",
};
```

# Rule 3 - 只讀目前任務的參考部位

- 開始第一個任務前，必須只讀 `status` 輸出的 `context`；不得讀取 tasks.md 全文，也不得讀取 spec package 的其他文件。
- 任務內容必須只從 `next` 的輸出取得，不得自行讀取 tasks.md 中其他任務的內容。
- 讀取 Must Read 時，必須以部位的識別字（例如 operationId、`Table` 名稱、§ 編號）在檔案中定位，只讀該部位到下一個同層部位為止；不得讀取整份文件。
- 每一項 Must Read 都必須讀；只有以部位的識別字在檔案中搜尋不到時，才可以記為找不到，並寫出搜尋方式與結果；不得因判斷其他文件已涵蓋該部位而略過或記為找不到。
- 解決文件之間的矛盾時，可以讀取權威較高文件中與矛盾相關的部位，並必須在進度回報寫出讀取的部位與原因。

## Good Example

### Example 1

- 診所掛號系統的 T014 的 Must Read 是 `contracts/openapi.yaml` → `createAppointment` 與 `research.md` → §4；先以識別字找到行號，只讀這兩段。

```text
grep -n "operationId: createAppointment" contracts/openapi.yaml → 第 88 行；讀 80–131 行（到下一個 path）
grep -n "^## 4\." research.md → 第 61 行；讀 61–78 行（到 ## 5.）
T014 已通過，回寫後繼續下一個任務
- Must Read：openapi.yaml createAppointment（80–131 行）、research.md §4
```

### Example 2

- 同一個專案的 T020 有 3 項 Must Read，第 3 項 `ui/plan.md` → §6 以識別字搜尋不到；讀完前 2 項後，只把第 3 項記為找不到，並寫出搜尋方式與結果。

```text
grep -n "^## 6" ui/plan.md → 沒有結果，檔案只到 §5
check … --must-read 1,2 --not-found "3：grep -n '^## 6' ui/plan.md 沒有結果，檔案只到 §5"
```

## Bad Example

### Example 1

- 同一個專案在開始第一個任務前就把 research、plan、data-model 與兩份合約全文讀完，沒有以識別字定位部位。

```text
cat research.md plan.md data/data-model.dbml contracts/openapi.yaml contracts/asyncapi.yaml
（之後開始 T001）
```

### Example 2

- 同一個專案的 T021，Must Read 第 2 項是 `ui/booking.html` → 雛形狀態「時段已滿」，以識別字搜尋得到；執行者認為 `ui/plan.md` §4 已寫過這個狀態，沒有讀第 2 項，卻把它記為找不到。

```text
check … --must-read 1 --not-found "2：ui/plan.md §4 已涵蓋"
```
