# Rule 1 - 資料表必須歸屬負責介面並涵蓋 Key Entities

- 每張資料表的 `Note` 必須以「<介面編號>：」開頭，介面編號必須是「負責介面」之一。
- `Note` 在介面編號之後必須寫出需求依據：目標 spec 中存在的需求編號（US、FR、NFR、SC），或 Key Entities 項目名稱。
- 每個負責介面必須至少對應一張資料表。
- 不得為負責介面以外的介面設計資料表，也不得建立不屬於任何負責介面的資料表。
- 負責介面的需求依據引用的每個 Key Entities 項目，必須有對應的資料表；不單獨建表的項目，必須在併入的資料表 `Note` 說明併入該表。

## Good Example

- 圖書館借閱的負責介面為 D1 館藏資料存取與 D2 借閱紀錄持久化，需求依據引用 Key Entities 書目、館藏複本、讀者、借閱紀錄。每張表的 `Note` 以介面編號開頭並寫出需求依據；「讀者」由會員系統管理，只在 `loans` 保留讀者編號，並在 `Note` 說明併入。

```dbml
Table titles {
  id uuid [pk]
  isbn varchar(13) [not null, unique]
  Note: 'D1：Key Entities 書目；FR-001 依 ISBN 查詢館藏'
}

Table copies {
  id uuid [pk]
  title_id uuid [not null]
  barcode varchar(20) [not null, unique]
  Note: 'D1：Key Entities 館藏複本；FR-002 以條碼辨識每一本實體書'
}

Table loans {
  id uuid [pk]
  copy_id uuid [not null]
  reader_no varchar(12) [not null, note: '讀者由會員系統管理，只保存讀者編號']
  Note: 'D2：Key Entities 借閱紀錄，讀者併入此表的 reader_no；FR-004 借書、FR-005 還書'
}
```

## Bad Example

- 同一份需求中，`Note` 只寫表名，看不出屬於哪個介面與需求；Key Entities「館藏複本」沒有對應資料表，也沒有說明併入哪張表；另外多了一張不屬於任何負責介面的 `staff_accounts`。

```dbml
Table titles {
  id uuid [pk]
  isbn varchar(13) [not null, unique]
  Note: '書目表'
}

Table loans {
  id uuid [pk]
  title_id uuid [not null]
  reader_no varchar(12) [not null]
  Note: '借閱表'
}

Table staff_accounts {
  id uuid [pk]
  Note: '館員帳號'
}
```

# Rule 2 - 關聯與欄位約束必須反映需求

- 資料表之間的關聯必須以 `Ref` 表達，並以 `>`、`<` 或 `-` 標明基數；不得只在 `Note` 或欄位名稱暗示關聯。
- 每張資料表必須有主鍵。
- 需求中有固定狀態集合的欄位，必須以 `Enum` 定義，不得使用自由字串。
- 需求要求唯一的欄位或欄位組合，必須標 `unique` 或建立 `unique` 索引；需求要求必填的欄位，必須標 `not null`。
- 需求中的查詢條件或效能要求（例如 SC 的回應時間）所依賴的欄位，必須建立 `indexes`。
- 需求限制單一欄位的值（長度、數值範圍、格式、可接受的日期範圍），且只用該欄位的值（可加上目前時間）就能判斷時，必須寫在該欄位 `note` 的開頭：`驗證：<規則>（<依據>）；<規則>（<依據>）。`，之後才寫其他說明。`<依據>` 是 spec 存在的需求編號，或 `Key Entities <項目名稱>`、`Edge Cases <情境名稱>`。欄位型別與設定已表達的約束（`varchar(n)`、`not null`、`unique`、`Enum`、`default`）不得在「驗證」重寫。
- 需求限制同一列兩個以上欄位之間的關係時，必須寫在資料表 `Note` 的介面編號與需求依據之後：`跨欄位：<規則>（<table.column>、<table.column>；<依據>）。`；不得寫在其中一個欄位的 `note`。
- 「驗證」與「跨欄位」只寫需求規定的資料值限制：不得加入需求沒有的約束；要比對其他資料列或資料表的規則不得寫成這兩種寫法，改由 `unique`、索引或 `Ref` 表達，無法表達時不寫。

## Good Example

### Example 1

- 圖書館借閱需求寫明「同一本館藏複本同時只能有一筆未歸還的借閱」（FR-006）、借閱狀態分為借出中、已歸還、逾期（FR-007），以及「讀者查詢自己的借閱紀錄 1 秒內回應」（SC-002）。狀態用 `Enum`，關聯用 `Ref` 標明基數，查詢欄位建立索引；DBML 無法表達部分唯一索引，FR-006 改以 `active_copy_id` 欄位加 `unique` 表達，`active_copy_id` 和 `copy_id`、`status` 的關係寫成「跨欄位」。`status` 的狀態轉換由 Rule 3 示範，本例省略。

```dbml
Enum loan_status {
  on_loan
  returned
  overdue
}

Table loans {
  id uuid [pk]
  copy_id uuid [not null]
  active_copy_id uuid [unique, note: '以 unique 保證同一複本同時只有一筆未歸還的借閱']
  reader_no varchar(12) [not null]
  status loan_status [not null, default: 'on_loan']
  borrowed_at timestamptz [not null]

  indexes {
    (reader_no, borrowed_at) [name: 'idx_loans_reader_borrowed']
  }

  Note: 'D2：Key Entities 借閱紀錄；FR-004、FR-006、FR-007；SC-002。跨欄位：status 不是 returned 時 active_copy_id 等於 copy_id，status = returned 時為 null（loans.active_copy_id、loans.copy_id、loans.status；FR-006）。'
}

Ref: loans.copy_id > copies.id
```

### Example 2

- 同一圖書館借閱情境補充需求：讀者編號為 R 加 11 位數字（FR-003）；借閱期限為借出日起 1 到 30 天（FR-004）；歸還時記錄歸還時間（FR-005）。`reader_no` 的格式寫成「驗證」，長度由 `varchar(12)` 表達、不重寫；`due_date` 的範圍要比較 `borrowed_at`，寫成「跨欄位」；`status = returned` 與 `returned_at` 的關係也寫成「跨欄位」。`status` 的狀態轉換由 Rule 3 示範，本例省略。

```dbml
Table loans {
  id uuid [pk]
  copy_id uuid [not null]
  reader_no varchar(12) [not null, note: '驗證：R 加 11 位數字（FR-003）。讀者由會員系統管理，只保存讀者編號']
  status loan_status [not null, default: 'on_loan']
  borrowed_at timestamptz [not null]
  due_date date [not null]
  returned_at timestamptz

  Note: 'D2：Key Entities 借閱紀錄；FR-004 借書、FR-005 還書。跨欄位：due_date 為 borrowed_at 的日期之後 1 到 30 天（loans.due_date、loans.borrowed_at；FR-004）。跨欄位：status = returned 時 returned_at 不得為 null，其他狀態時為 null（loans.status、loans.returned_at；FR-005）。'
}
```

## Bad Example

### Example 1

- 同一份需求中，狀態用自由字串，FR-006 的「同時只能有一筆未歸還借閱」沒有任何唯一約束，與 `copies` 的關聯只寫在 `Note`，SC-002 依賴的讀者查詢也沒有索引。

```dbml
Table loans {
  id uuid [pk]
  copy_id uuid
  reader_no varchar(12)
  status varchar(20) [note: '借出中、已歸還或逾期']
  borrowed_at timestamptz

  Note: 'D2：借閱紀錄，copy_id 對應 copies.id'
}
```

### Example 2

- 同一情境中，格式規則混在說明句中；`reader_no` 重寫 `varchar(12)` 已表達的長度；`due_date` 和 `borrowed_at` 的關係只寫在 `due_date` 的 `note`；加入需求沒有的「`copy_id` 不得為零值 UUID」；把「同一讀者最多借 5 本」這種要比對其他資料列的規則寫成「驗證」。

```dbml
Table loans {
  id uuid [pk]
  copy_id uuid [not null, note: '驗證：不得為零值 UUID（FR-004）']
  reader_no varchar(12) [not null, note: '讀者編號，必須是 R 開頭加 11 位數字，最多 12 字元']
  due_date date [not null, note: '驗證：借出後 1 到 30 天內（FR-004）；同一讀者最多借 5 本（FR-006）']

  Note: 'D2：Key Entities 借閱紀錄；FR-004 借書'
}
```

# Rule 3 - 狀態轉換必須寫在狀態欄位的一處

- 需求規定狀態會改變的 `Enum` 欄位，必須在該欄位 `note` 的開頭寫「轉換」，放在「驗證」之前：`轉換：初始 <值>（<依據>）；<從> → <到>（<依據>）；…；終態 <值>、<值>。`，之後才寫其他說明。
- 「轉換」必須列出建立資料列時可用的每個初始值、需求允許的每個轉換與依據、每個終態；沒有列出的轉換表示不允許。`<依據>` 的寫法與 Rule 2 相同。
- 同一欄位的轉換只寫在這一處：`Enum` 值的 `note` 只寫該值的意思，資料表 `Note` 不得重述轉換。
- 需求沒有規定狀態改變的 `Enum` 欄位（例如角色）不得寫「轉換」，也不得加入需求沒有的轉換。

## Good Example

- 圖書館借閱情境：借出時建立 `on_loan`（FR-004）；超過期限未還改為 `overdue`（FR-007）；`on_loan`、`overdue` 都可以歸還（FR-005）。轉換只寫在 `loans.status`，`Enum` 值只寫意思。

```dbml
Enum loan_status {
  on_loan [note: '借出中']
  overdue [note: '逾期未還']
  returned [note: '已歸還']
}

Table loans {
  id uuid [pk]
  status loan_status [not null, default: 'on_loan', note: '轉換：初始 on_loan（FR-004）；on_loan → overdue（FR-007）；on_loan → returned（FR-005）；overdue → returned（FR-005）；終態 returned。借閱目前的狀態']
  Note: 'D2：Key Entities 借閱紀錄；FR-004、FR-005、FR-007'
}
```

## Bad Example

- 同一情境中，轉換分散在 `Enum` 值的 `note` 與資料表 `Note`；漏掉 `overdue → returned`；沒有寫終態；`reader_role` 的需求沒有狀態改變，卻寫了「轉換」。

```dbml
Enum loan_status {
  on_loan [note: '借出中，逾期時改為 overdue']
  overdue [note: '逾期未還']
  returned [note: '已歸還']
}

Table loans {
  id uuid [pk]
  status loan_status [not null, default: 'on_loan']
  reader_role reader_role [not null, note: '轉換：初始 student（FR-002）；student → teacher（FR-002）']
  Note: 'D2：Key Entities 借閱紀錄；on_loan 歸還時改為 returned（FR-005）'
}
```
