# Rule 1 - 回報中的每個識別字都必須搜尋

- 回報中的每個錯誤訊息、log 字串、route 名稱與元件識別字都必須搜尋。
- 每個識別字都必須記下命中位置或「沒有命中」。
- 一般用語（例如「維修」「狀態」）不算識別字，不得用來取代識別字的搜尋。

## Good Example

- 回報中的 route 名稱與元件識別字都有搜尋，每個都有搜尋結果；沒有命中的也寫「沒有命中」。

情境：

- 回報：設備維修頁把設備改為維修中時，`PATCH /api/equipment/:id/status` 回 409，頁面的 `equipment-status-badge` 仍顯示「可借用」。
- 搜尋：`/api/equipment/:id/status`，命中 `backend/src/routes/equipment.ts:42`。
- 搜尋：`409`，命中 `backend/src/routes/equipment.ts:58`。
- 搜尋：`equipment-status-badge`，沒有命中。

## Bad Example

- 只搜尋「維修」「狀態」等描述詞；回報中的 route 名稱與元件識別字沒有搜尋。

情境：

- 回報：設備維修頁把設備改為維修中時，`PATCH /api/equipment/:id/status` 回 409，頁面的 `equipment-status-badge` 仍顯示「可借用」。
- 搜尋：「維修」，命中 20 處。
- 搜尋：「狀態」，命中 63 處。

# Rule 2 - 必須追查使用同一筆資料或同一個前提的測試

- 必須追查使用同一筆 seed 資料、同一個時間假設或同一個 fixture 的其他測試。
- 每個找到的測試必須逐一寫出是否受影響與依據。
- 不得只看回報指出的那一個測試。

## Good Example

- 回報的測試依賴同一筆 seed 設備，找出所有使用該設備的測試並逐一判斷。

情境：

- 回報：測試依賴 seed 中設備 `EQ-003` 的「維修中」狀態，這個測試失敗。
- 搜尋 `EQ-003`，找到 3 個測試。
- `api.test.ts` 的借用測試：預期 `EQ-003` 不可借用，受影響，因為修法會改變維修中設備的回應。
- `equipment-loan.spec.ts` 的清單測試：只讀取 `EQ-003` 的名稱，不受影響。
- `seed.test.ts`：只檢查 seed 筆數，不受影響。

## Bad Example

- 只看回報指出的那一個測試，沒有追查同一筆 seed 資料的其他測試。

情境：

- 回報：測試依賴 seed 中設備 `EQ-003` 的「維修中」狀態，這個測試失敗。
- 追查：只檢查回報指出的 `api.test.ts` 借用測試。
