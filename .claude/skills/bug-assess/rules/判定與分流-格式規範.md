# Rule 1 - 判定只用四種值

- 判定必須只使用下表的四種值之一，每個值依「依據」欄的條件判斷。
- 判定為不成立或意圖改變時，修法的每一項（首選、替代做法、要改的檔案、要補的測試）必須寫「無」。
- 判定為不成立時，必須寫出下表 4 種理由之一，並寫出該理由的證據。
- 理由為重複回報時，必須指出症狀相同的 `specs/bugs/` 既有代號。
- 判定為意圖改變時，必須寫出每個要改的事所改變的已同意意圖。
- 回報要求已同意內容中沒有的新行為時，必須視為意圖改變，並在依據寫明「要求已同意內容中沒有的新行為」。

| 判定     | 依據                                                                 |
| -------- | -------------------------------------------------------------------- |
| 成立     | 證據顯示實作偏離已同意的意圖                                         |
| 待重現   | 只靠程式碼無法確認症狀                                               |
| 不成立   | 使用方式錯誤、行為符合已同意的意圖、重複回報、超出範圍，四種理由之一 |
| 意圖改變 | 全部要改的事都要改變已同意的意圖，或要求已同意內容中沒有的新行為     |

## Good Example

### Example 1

- 程式碼與雛形的證據足以確認實作偏離意圖，判定為成立，並列出修法。

情境：

- 回報：按「重新整理」時畫面抖動。
- 證據：載入提示列只在載入期間掛上，沒有預留高度，載入開始和結束各把下方內容推動一次（`OverdueNotificationsView.tsx:397-402`）。
- 判定：成立。
- 修法首選：載入提示列一直掛在 DOM 上並預留高度，只在載入期間顯示。

### Example 2

- 回報同時含缺陷與已同意內容中沒有的新行為；缺陷進修法，新行為列為意圖改變。

情境：

- 回報：「重新整理後通知清單的順序跑掉」，並且「希望通知清單可以匯出 CSV」。
- 證據：順序跑掉偏離 spec；spec 沒有匯出功能。
- 判定：成立。
- 修法首選：修正重新整理後的排序。
- 轉回 SDD 流程的項目：匯出 CSV，依據是要求已同意內容中沒有的新行為。

## Bad Example

### Example 1

- 沒有在瀏覽器實測就判定為不成立；程式碼已經顯示位移的原因，而且「沒有實測」不是行為符合意圖的證據。

情境：

- 回報：按「重新整理」時畫面抖動。
- 證據：載入提示列只在載入期間掛上，沒有預留高度（`OverdueNotificationsView.tsx:397-402`）。
- 判定：不成立，依據是「沒有實測，無法確認抖動」。
- 修法首選：無。

### Example 2

- 同一份回報中，已同意內容中沒有的新行為被放進修法，轉回段沒有列出。

情境：

- 回報：「重新整理後通知清單的順序跑掉」，並且「希望通知清單可以匯出 CSV」。
- 判定：成立。
- 修法首選：修正排序；新增匯出 CSV 的按鈕。
- 轉回 SDD 流程的項目：無。

# Rule 2 - 嚴重度只用四級並寫出理由

- 嚴重度必須只使用下表的四級之一。
- 嚴重度必須附上理由。
- 和回報者的認定不同時，必須寫出差異理由。

| 嚴重度     | 定義                             |
| ---------- | -------------------------------- |
| `critical` | 資料遺失、安全或主要流程無法使用 |
| `high`     | 主要功能錯誤且沒有替代操作       |
| `medium`   | 功能可用但結果或體驗錯誤         |
| `low`      | 外觀或文字問題                   |

## Good Example

- 評估和回報者不同，等級後面有理由，並說明差異。

情境：

- 回報者的認定：很嚴重。
- 評估：`medium`。
- 理由：
  - 使用者影響：每次重新整理都會位移，管理員會以為系統壞掉。
  - 波及範圍：只有這一頁。
  - 資料風險：不影響資料正確性、權限與通知送出。
  - 新的回歸或長期存在：長期存在，不是回歸。
  - 和回報者認定的差異：沒有主要功能錯誤，所以不到 `high`。

## Bad Example

- 只寫等級，沒有寫理由，也沒有說明和回報者認定的差異。

情境：

- 回報者的認定：很嚴重。
- 評估：`medium`。

# Rule 3 - 意圖改變的項目只列在轉回段

- 要改變已同意意圖的項目必須只列在「轉回 SDD 流程的項目」，並寫出處理 Skill。
- 要改變已同意意圖的項目不得出現在修法與要改的檔案。
- 每個轉回項目必須只對應一個處理 Skill。
- 轉回項目必須依上游到下游排序：`s-specify` → `ui-plan`／`data-plan` → `api-plan`。
- 沒有轉回項目時，「轉回 SDD 流程的項目」必須寫一列「無」。
- 全部要改的事都要改變已同意的意圖時，判定必須為意圖改變。

## Good Example

### Example 1

- 清除橫幅的時機和移除載入提示列都要改變 `ui/plan.md` 的規定，所以只列在轉回段，修法首選只留下缺陷的修正。

情境：

- 要改的事：預留載入提示列的高度（缺陷）。
- 要改的事：橫幅改成載入完成後才清除（`ui/plan.md` §4 規定先隱藏橫幅）。
- 要改的事：移除載入提示列（`ui/plan.md` §4 規定顯示載入提示）。
- 修法首選：預留載入提示列的高度。
- 轉回 SDD 流程的項目：I1 橫幅清除時機，處理 Skill 為 `ui-plan`；I2 移除載入提示列，處理 Skill 為 `ui-plan`。

### Example 2

- 4 個轉回項目各只對應一個處理 Skill，依上游到下游排序。

情境：

- I1：新增 Email 通知的需求，處理 Skill 為 `s-specify`。
- I2：Email 通知設定的畫面，處理 Skill 為 `ui-plan`。
- I3：通知偏好的資料表，處理 Skill 為 `data-plan`。
- I4：通知偏好的 API，處理 Skill 為 `api-plan`。

## Bad Example

### Example 1

- 「移除載入提示列」要改變已同意的意圖，卻放進修法首選，轉回段也沒有列出。

情境：

- 要改的事：預留載入提示列的高度（缺陷）。
- 要改的事：移除載入提示列（`ui/plan.md` §4 規定顯示載入提示）。
- 修法首選：預留載入提示列的高度；移除載入提示列。
- 轉回 SDD 流程的項目：無。

### Example 2

- 一項同時列 `s-specify` 與 `ui-plan`；順序也顛倒，`api-plan` 排在 `s-specify` 之前。

情境：

- I1：通知偏好的 API，處理 Skill 為 `api-plan`。
- I2：新增 Email 通知的需求與設定畫面，處理 Skill 為 `s-specify`、`ui-plan`。

# Rule 4 - 修法只能同步修改雛形

- 修法可以同步修改雛形，讓雛形和修正後的實作一致。
- 在 `spec.md`、`ui/plan.md` 等文件新增或改寫行為敘述時，必須視為意圖改變。

## Good Example

- 修法只修改雛形的版面，不動文件中的行為敘述。

情境：

- 修法首選：雛形 `ui/overdue-notifications.html` 同步預留載入提示列的高度。
- 要改的檔案：`ui/overdue-notifications.html`；`ui/plan.md` 不修改。

## Bad Example

- 修法直接在 `ui/plan.md` 新增行為敘述，等於改變已同意的意圖。

情境：

- 修法首選：在 `ui/plan.md` §4 補寫「重新整理與換頁期間版面不位移」。
- 要改的檔案：`ui/plan.md`。

# Rule 5 - 待確認問題的範圍

- 下列事項必須列為待確認問題：
  - 修法範圍有兩個以上可行選擇，而證據無法決定。
  - 回報用語和實際的頁面、元件或資料對不上。
  - 使用者的意圖無法從證據決定。
  - 根本原因中無法從證據確認的事項。
- 證據已能排出優劣的選擇必須列為替代做法，不得列為待確認問題。
- 不得猜測待確認問題的答案。

## Good Example

- 頁面名稱對不上，以及修法範圍的二選一證據無法決定，都列為待確認問題，由使用者回答。

情境：

- 回報：「申請紀錄頁」按重新整理時畫面抖動；實際頁面是「逾期通知紀錄」。
- 待確認問題：Q1 回報的「申請紀錄頁」是不是「逾期通知紀錄」頁？
- 修法範圍：「只修重新整理按鈕」或「換頁也一起修」，證據無法決定。
- 待確認問題：Q2 修法範圍是只修重新整理，還是換頁也一起修？

## Bad Example

- 同一個範圍選擇被寫成替代做法，執行者自己選了首選；頁面名稱由執行者推定。

情境：

- 回報：「申請紀錄頁」按重新整理時畫面抖動；實際頁面是「逾期通知紀錄」。
- 修法首選：只修重新整理按鈕。
- 替代做法：換頁也一起修。
- 待確認問題：無（頁面名稱推定為「逾期通知紀錄」）。

# Rule 6 - 核准段依判定寫入

- 核准狀態與核准段 4 欄（核准日期、核准的修法、核准執行的命令、不在本次修正範圍）的初稿必須依下表寫入。
- 判定不是成立時，轉回 SDD 流程的項目只列在轉回段，不得寫進「不在本次修正範圍」。
- 重新評估時，前次核准的內容必須保留在同一欄，前面標「（前次核准，<日期>）」；本次的值接在後面，前面標「本次：」。
- 同一欄不得混寫本次的值與說明句，例如「不適用（判定為待重現）。前次核准保留如下」。

| 判定                                               | 核准狀態   | 核准日期 | 核准的修法 | 核准執行的命令 | 不在本次修正範圍 |
| -------------------------------------------------- | ---------- | -------- | ---------- | -------------- | ---------------- |
| 成立                                               | 待核准     | 待核准   | 待核准     | 待核准         | 待核准           |
| 待重現，而且需要核准的命令不是「無」               | 待核准命令 | 待核准   | 不適用     | 待核准         | 不適用           |
| 其他（待重現沒有需要核准的命令、不成立、意圖改變） | 不適用     | 不適用   | 不適用     | 不適用         | 不適用           |

## Good Example

### Example 1

- 判定待重現，需要核准的命令會重設資料庫，所以核准狀態為「待核准命令」，這個命令才有辦法核准。

情境：

- 回報：每天 00:00 的逾期掃描有時重複寄通知。
- 判定：待重現；需要核准的命令：`npm run db:reset`。
- 核准狀態：待核准命令。
- 核准的修法：不適用。
- 核准執行的命令：待核准。

### Example 2

- 重新評估後仍是待重現，前次核准保留在同一欄，本次的值接在後面。

情境：

- 核准的修法：（前次核准，2026-11-03）首選修法第 1～2 項；本次：不適用

## Bad Example

### Example 1

- 判定待重現且有需要核准的命令，4 欄都寫「不適用」，`npm run db:reset` 因此沒有辦法核准。

情境：

- 回報：每天 00:00 的逾期掃描有時重複寄通知。
- 判定：待重現；需要核准的命令：`npm run db:reset`。
- 核准狀態、核准日期、核准的修法、核准執行的命令：都寫「不適用」。

### Example 2

- 判定為意圖改變，轉回項目被寫進「不在本次修正範圍」。

情境：

- 判定：意圖改變。
- 不在本次修正範圍：I1，轉回 `s-specify`。

### Example 3

- 重新評估為待重現，本次的值與說明句、前次核准混寫在同一句。

情境：

- 核准日期：不適用（判定為待重現）。前次核准保留如下
