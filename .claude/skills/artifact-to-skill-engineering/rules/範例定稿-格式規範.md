# Rule 1 - 範例必須是具體實例

- 範例必須是一份已填完內容的產出檔案，不得含有填位符號，例如 `{{DECISION}}`、`<負責人>`、`[日期]`、`TBD`。
- 範例不得含有寫給填寫者的抽象說明，例如「請在此填入待辦事項」、「描述本次決議」。
- 範例的內容必須取自單一具體情境，人名、日期、數量與事項都必須寫出實際值。
- 參考範例含有填位符號或抽象說明時，必須以同一個具體情境的實際內容取代，不得原樣保留。

## Good Example

- 決議與待辦都寫出實際的人名、日期與事項，讀者能看出這是一場真實會議的紀錄。

```markdown
# 2026-10-14 結帳流程改版週會

## 出席者

- 王小明（PM）、陳怡君（前端）、林志豪（後端）

## 決議

1. 結帳頁改為單頁式，移除第二步的地址確認頁。
2. 信用卡分期選項延到 11 月第二週上線。

## 待辦事項

- 陳怡君：10/21 前完成單頁式結帳的 UI 雛形。
- 林志豪：10/18 前確認金流商分期 API 的回應格式。
```

## Bad Example

- 決議保留填位符號，待辦只有寫給填寫者的說明，看不出實際會議內容。

```markdown
# {{MEETING_DATE}} {{MEETING_TITLE}}

## 出席者

- <出席者名單>

## 決議

1. {{DECISION}}

## 待辦事項

- 請在此填入待辦事項與負責人。
```

# Rule 2 - 客製化需求必須直接呈現在範例內容

- 客製化需求必須改寫範例本身的結構、段落或條目，讓範例直接呈現改變後的樣貌。
- 範例不得以註解、待辦標記或「此處改為⋯⋯」、「之後要調整」等說明文字表達尚未套用的修改。
- 使用者要求刪除的段落必須整段移除，不得保留空段落，也不得改寫成「本段已刪除」。

## Good Example

- 使用者要求「待辦改成表格並加上負責人欄」，範例的待辦事項段落就直接改成含負責人欄的表格。

```markdown
## 待辦事項

| 事項 | 負責人 | 期限 |
| ---- | ------ | ---- |
| 完成單頁式結帳的 UI 雛形 | 陳怡君 | 10/21 |
| 確認金流商分期 API 的回應格式 | 林志豪 | 10/18 |
```

## Bad Example

- 同一個需求，範例保留原本的條列，只在下方加註要改成表格，範例沒有呈現改變後的樣貌。

```markdown
## 待辦事項

- 陳怡君：10/21 前完成單頁式結帳的 UI 雛形。
- 林志豪：10/18 前確認金流商分期 API 的回應格式。

<!-- 此段之後改成表格，並加上負責人欄 -->
```

# Rule 3 - 修改後的範例必須維持同一情境且前後一致

- 修改後的整份範例必須仍描述同一個情境，不得在部分段落換成另一個情境的內容。
- 編號與交互引用必須前後一致：條目重新編號後，其他段落引用該編號的地方必須同步更新，不得引用已不存在的編號。
- 搬移、拆分或重組條目時，使用者沒有要求刪除的條目必須全部保留。

## Good Example

- 把「決議」拆成「已決議」與「待決議」後，原本 3 條決議都還在，待辦引用的決議編號也跟著更新。

修改前：

```markdown
## 決議

1. 結帳頁改為單頁式。
2. 分期選項延到 11 月上線。
3. 是否保留貨到付款，下次會議再決定。

## 待辦事項

- 林志豪：依決議 2 確認分期 API 格式。
```

修改後：

```markdown
## 已決議

1. 結帳頁改為單頁式。
2. 分期選項延到 11 月上線。

## 待決議

3. 是否保留貨到付款，下次會議再決定。

## 待辦事項

- 林志豪：依決議 2 確認分期 API 格式。
```

## Bad Example

- 同一個拆分，「是否保留貨到付款」在搬移時遺漏；已決議重新編號後，待辦仍引用舊編號 3，指向不存在的決議。

```markdown
## 已決議

1. 結帳頁改為單頁式。
2. 分期選項延到 11 月上線。

## 待辦事項

- 林志豪：依決議 3 確認分期 API 格式。
```
