# Rule 1 - 任務必須依 User Story 歸屬 Phase，並依技術端點分組

- 多個 User Story 都要用到的基礎設施（連線池、錯誤處理、共用版面、共用 API 呼叫）必須放在 Foundational；其餘工作必須放在第一個需要它的 User Story Phase。
- 不得依技術層（例如「全部資料表」「全部 API」）切分 Phase；同一個介面跨多個 User Story 時，必須依各 User Story 需要的功能拆到對應的 Phase。
- Foundational 與每個 User Story Phase 內，任務必須依 `plan.md`「系統介面盤點」的端點類型分組，順序為資料庫 → 後端 → 前端；盤點表中的其他端點類型（例如第三方服務、硬體）必須歸入呼叫它的那一組。
- 組標題必須寫成 `### <端點類型>（<介面編號>）`，括號列出該組任務實作的介面編號，連續編號可以寫成 `B1–B5`；Foundational 的組標題必須在編號後加「共用」。
- 某個端點類型在該 Phase 沒有任務時，不得列出空的組；省略的原因無法從前面的 Phase 看出時，必須在下一個組標題後以引言（`> `）說明。
- User Story Phase 的數量必須等於 spec.md 的 User Story 數，依 spec 的順序編號，Polish 的 Phase 編號接在最後一個 User Story 之後。

## Good Example

- 圖書館預約借書的 spec 有 US1 預約館藏、US2 到館取書兩個故事，plan.md 盤點 D1 館藏與預約資料、B1 預約 API、B2 取書 API、F1 預約畫面、F2 取書畫面、P1 簡訊通知服務。共用的連線池放 Foundational；簡訊通知由後端呼叫，歸入後端組；US2 沒有新資料表，以引言說明。

```markdown
## Phase 2: Foundational (Blocking Prerequisites)

### 資料庫（D1）
- [ ] T005 在 `server/db/schema.sql` 建立 `books`、`copies`……

### 後端（B1–B2 共用）
- [ ] T007 在 `server/db/pool.js` 建立連線池……

## Phase 3: User Story 1 - 預約館藏 (Priority: P1) 🎯 MVP

### 資料庫（D1）
- [ ] T010 [US1] 在 `server/db/schema.sql` 建立 `reservations`……

### 後端（B1、P1）
- [ ] T011 [US1] 在 `server/services/reservationService.js` 實作 `createReservation`……

### 前端（F1）
- [ ] T014 [US1] 在 `web/src/views/ReserveView.vue` 實作預約畫面……

## Phase 4: User Story 2 - 到館取書 (Priority: P2)

### 後端（B2）

> D1 的 `reservations` 已在 US1 建立，本故事沒有資料庫任務。

- [ ] T016 [US2] 在 `server/services/pickupService.js` 實作 `confirmPickup`……
```

## Bad Example

- 同一份需求依技術層切成「資料庫」「API」「畫面」三個 Phase，看不出每個 User Story 何時可以獨立驗證；組標題沒有介面編號，簡訊通知 P1 也沒有出現在任何組。

```markdown
## Phase 3: 資料庫

- [ ] T010 建立 `reservations`……

## Phase 4: API

### 後端
- [ ] T011 實作預約 API……
- [ ] T016 實作取書 API……
```

# Rule 2 - 任務描述必須可以直接動手實作

- 任務描述中的檔案路徑必須依 `plan.md` 的 Source Code 結構；結構沒有列出的檔案依 Rule 4 在 Notes 說明。
- 任務描述必須從上游文件原樣帶入實作需要的識別字，例如 operationId、HTTP 方法與路徑、錯誤碼與狀態碼、資料表與欄位名稱、Enum 值、畫面上的狀態名稱與提示文字；不得改寫成意思相近的其他名稱。
- 任務描述結尾必須以括號引用依據的需求編號，例如 `（FR-003、US1 情境 2、Edge Cases 預約已滿）`；只做專案設定、沒有對應需求的任務可以改引用技術研究的章節，例如 `（research §2）`。
- `[P]` 只能標在不依賴同 Phase 其他未完成任務結果的任務上。
- 同一個檔案由多個任務修改時，這些任務不得標 `[P]`，且必須依實作順序排列。
- `[USk]` 必須標在 User Story k 的 Phase 中每個任務上；Setup、Foundational、Polish 的任務不得帶 `[US…]`。

## Good Example

- 任務寫出檔案、operationId、錯誤碼與畫面文字，結尾引用需求編號；修改同一個 service 的兩個任務沒有標 `[P]`。

```markdown
- [ ] T011 [US1] 在 `server/services/reservationService.js` 實作 `createReservation(readerId, copyId)`：複本不存在拋出 `COPY_NOT_FOUND`（404）；同一讀者已預約 3 本時拋出 `RESERVATION_LIMIT`（409），訊息為「每位讀者最多預約 3 本」（FR-002、FR-004、Edge Cases 預約已滿）
- [ ] T012 [US1] 在 `server/services/reservationService.js` 實作 `cancelReservation(readerId, reservationId)`……（FR-005）
- [ ] T014 [P] [US1] 在 `web/src/views/ReserveView.vue` 實作預約畫面：預約成功顯示「已為你保留到 3 天後」……（FR-002、US1 情境 1）
```

## Bad Example

- 同一個任務沒有檔案路徑、沒有錯誤碼與需求編號，執行者必須自己回頭讀完整份合約；修改同一個檔案的兩個任務都標了 `[P]`。

```markdown
- [ ] T011 [P] [US1] 實作預約 API
- [ ] T012 [P] [US1] 實作取消預約
```

# Rule 3 - 每個任務必須綁定執行時要讀的文件部位

- 每個任務必須至少列出一項 Must Read。
- 任務實作的 operation、資料表、畫面狀態，以及限制做法的技術決策章節，必須列為 Must Read。
- 只在特定情況才需要的部位必須列為 Optional，Why 必須以「……時」寫出觸發的情況。
- Must Read 的 Why 必須寫出該部位決定任務的哪一部分，例如「累加數量的規則與各錯誤碼」；不得只寫「參考」「相關文件」。
- 部位使用的識別字必須在上游文件中實際存在，並與上游文件的寫法逐字相同。
- 不得只引用檔案而不指出部位；本檔較前面的任務建立的小型檔案（例如 `quickstart.md`）除外。
- 同一個部位決定任務的多個面向時，必須合併為一項參考，在 Why 中列出各面向。

## Good Example

- 預約任務的 Must Read 指向 operation、資料表與技術決策章節，Why 寫出各自決定的內容；Optional 寫出需要讀的情況。

```markdown
- [ ] T011 [US1] 在 `server/services/reservationService.js` 實作 `createReservation`……（FR-002、FR-004）
  - **Must Read**
    - `contracts/openapi.yaml` → `createReservation`（含 `Conflict`） — Why：預約上限與各錯誤碼
    - `data/data-model.dbml` → `Table reservations` 的 `expires_at` — Why：保留期限要寫入的欄位
    - `research.md` → §4 — Why：預約時以交易鎖定複本，避免同一本被兩人預約
  - **Optional**
    - `spec.md` → Edge Cases「預約已滿」 — Why：需要確認額滿時的提示文字時
```

## Bad Example

- 同一個任務只引用整份文件，Why 沒有說明讀什麼；Optional 沒有寫出何時需要讀。

```markdown
- [ ] T011 [US1] 在 `server/services/reservationService.js` 實作 `createReservation`……（FR-002、FR-004）
  - **Must Read**
    - `contracts/openapi.yaml` — Why：參考
    - `data/data-model.dbml` — Why：相關文件
  - **Optional**
    - `research.md` → §4 — Why：補充資料
```

# Rule 4 - 上游缺口必須寫成待確認，不得自行補齊

- `plan.md`「系統介面盤點」的介面在 contracts、data、ui 找不到對應的 operation、資料表或畫面時，必須記為上游缺口。
- 上游文件之間對同一件事的命名或內容不一致（例如資料表的 Enum 值與合約的狀態值不同、畫面需要的欄位合約沒有提供）時，必須記為上游缺口。
- 每個上游缺口必須在 Notes 寫成一項 `- 待確認 n：`，n 從 1 連續編號，內容必須寫出缺少或矛盾的部位、受影響的任務 ID，以及在補齊前的暫行做法。
- 受上游缺口影響的任務必須在描述中標出「見 Notes 待確認 n」，只寫可以依現有上游文件確定的部分。
- 不得為補齊缺口而在任務描述或參考中寫出上游沒有的 operationId、HTTP 路徑、資料表、欄位或錯誤碼。
- 任務需要建立 `plan.md` Source Code 沒有列出的檔案時，必須在 Notes 說明新增的檔案與原因。

## Good Example

- plan.md 盤點了 B3 借閱紀錄查詢 API，但 openapi.yaml 沒有對應 operation。任務只寫可確定的查詢內容，路徑與回應格式標為待確認。

```markdown
- [ ] T020 [US3] 在 `server/services/loanService.js` 實作 `listLoans(readerId)`：依 `idx_loans_reader_borrowed` 由新到舊查出借閱紀錄；回傳格式待 contracts 補上 B3 合約後再對齊（見 Notes 待確認 1）（FR-009）

## Notes

- 待確認 1：plan.md 盤點了 B3 借閱紀錄查詢 API，但 contracts/openapi.yaml 沒有 B3 的 operation；T020、T021 先依 data-model 實作查詢，路徑與回應格式等 api-plan 補上 B3 合約後再定案
```

## Bad Example

- 同一個缺口被自行補上 `GET /api/loans` 與 `listLoans` operationId，Notes 也沒有記錄，實作會與之後補上的合約不一致。

```markdown
- [ ] T020 [US3] 在 `server/routes/loanRouter.js` 實作 `GET /api/loans`（`listLoans`），回傳 `LoanList`（FR-009）
  - **Must Read**
    - `contracts/openapi.yaml` → `listLoans` — Why：路徑與回應格式
```

# Rule 5 - 測試任務必須依 spec 是否明確要求而定

- spec.md 明確要求撰寫自動化測試或採用 TDD 時，每個 User Story Phase 必須在實作任務之前加入該故事的測試任務。
- spec.md 沒有明確要求時，User Story Phase 不得產生測試任務，且 `**Tests**:` 必須說明 spec 沒有要求，以及 Setup 是否仍安裝測試工具。
- Success Criteria 中的量測要求（例如「以 100 組資料測試正確率達 100%」「1 秒內更新」）不視為要求撰寫測試；必須在 Polish 以驗證任務處理，任務描述寫出量測方式並引用該 SC 編號。

## Good Example

- spec 沒有要求測試，SC-002 要求「以 50 組預約資料測試，重複預約全部被拒絕」，Tests 說明不產生測試任務，量測放在 Polish。

```markdown
**Tests**: spec.md 沒有明確要求撰寫測試或 TDD，因此各使用者故事不產生測試任務。Setup 依 research §8 安裝測試工具，供之後需要時使用。

## Phase 5: Polish & Cross-Cutting Concerns

- [ ] T030 [P] 以 50 組預約資料呼叫 `createReservation`，確認同一讀者對同一複本的重複預約全部回 `DUPLICATE_RESERVATION`（SC-002）
```

## Bad Example

- 同一份 spec 因為 SC-002 出現「測試」兩字，就在每個 User Story 加入單元測試任務，Tests 欄也沒有說明依據。

```markdown
**Tests**: 包含測試。

## Phase 3: User Story 1 - 預約館藏 (Priority: P1) 🎯 MVP

- [ ] T010 [P] [US1] 在 `server/tests/reservationService.test.js` 撰寫 `createReservation` 的單元測試（SC-002）
```
