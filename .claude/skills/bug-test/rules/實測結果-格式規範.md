# Rule 1 - 每項檢查的結果值必須依證據判定

- 每項檢查的結果值必須只使用通過、不通過、略過、無法執行。
- 需要說明時，必須在結果值後加全形括號註記，註記只能使用下表的值。
- 修正後不通過的檢查，必須在修正前版本執行；修正前同樣不通過時，才可以註記「既有、無關」。
- 「既有、無關」只能用在不屬於任何完整預期行為通過標準的檢查。
- 屬於某項完整預期行為通過標準的檢查，修正前同樣不通過時，修正後的結果必須寫「不通過」，不得註記「既有、無關」，該項完整預期行為必須判為不通過。
- 修正前版本通過、修正後不通過的檢查是本次修正造成的回歸，不得註記「既有、無關」。
- 轉回 SDD 流程的項目必須寫「仍會發生（轉回項目）」，不得列入結果判定。
- 同一個版本第 1 次不通過、重跑 1 次通過，而且失敗原因和本錯誤無關時，可以註記「偶發、重跑通過」；使用時，必須另加一列記錄重跑結果。

| 註記           | 使用時機                                                     |
| -------------- | ------------------------------------------------------------ |
| 成功重現       | 修正前實測，或修正前版本，量到評估報告描述的錯誤，結果為不通過 |
| 符合預期       | 要補的測試在修正前版本不通過                                 |
| 既有、無關     | 不屬於任何完整預期行為通過標準的檢查，修正後不通過，修正前版本同樣不通過 |
| 同樣失敗       | 在修正前版本重跑修正後不通過的檢查，結果同樣不通過           |
| 偶發、重跑通過 | 同一個版本第 1 次不通過，重跑 1 次通過，而且失敗原因（例如逾時）和本錯誤無關 |

## Good Example

### Example 1

- 完整 e2e 修正後不通過，先在修正前版本重跑；修正前同樣不通過，而且它不屬於任何完整預期行為的通過標準，所以修正後註記「既有、無關」。

情境：

| 檢查                  | 命令                                          | 版本   | 結果                 |
| --------------------- | --------------------------------------------- | ------ | -------------------- |
| 完整 e2e              | `npm run test:e2e`                            | 修正後 | 不通過（既有、無關） |
| 完整 e2e 失敗項       | `npx playwright test e2e/equipment-loan.spec.ts` | 修正前 | 不通過（同樣失敗）   |

### Example 2

- E2 的通過標準是「`npm run test:frontend` 全部通過」，`formatDate.test.ts` 修正前、修正後都不通過；它屬於 E2 的通過標準，所以修正後寫「不通過」，E2 判為不通過。

情境：

| 檢查                                 | 命令                                | 版本   | 結果                 |
| ------------------------------------ | ----------------------------------- | ------ | -------------------- |
| E2：`formatDate.test.ts`             | `npm run test:frontend`             | 修正前 | 不通過（同樣失敗）   |
| E2：`formatDate.test.ts`             | `npm run test:frontend`             | 修正後 | 不通過               |
| E2：完整預期行為                     | `npm run test:frontend`             | 修正後 | 不通過               |

## Bad Example

### Example 1

- 完整 e2e 修正後不通過，沒有在修正前版本執行，就直接註記「既有、無關」；沒有證據顯示它不是本次修正造成的回歸。

情境：

| 檢查     | 命令               | 版本   | 結果                 |
| -------- | ------------------ | ------ | -------------------- |
| 完整 e2e | `npm run test:e2e` | 修正後 | 不通過（既有、無關） |

### Example 2

- `formatDate.test.ts` 屬於 E2 的通過標準，卻被註記「既有、無關」，E2 因此被判為通過。

情境：

| 檢查                                 | 命令                                | 版本   | 結果                 |
| ------------------------------------ | ----------------------------------- | ------ | -------------------- |
| E2：`formatDate.test.ts`             | `npm run test:frontend`             | 修正前 | 不通過（同樣失敗）   |
| E2：`formatDate.test.ts`             | `npm run test:frontend`             | 修正後 | 不通過（既有、無關） |
| E2：完整預期行為                     | `npm run test:frontend`             | 修正後 | 通過                 |

# Rule 2 - 修正後實測的結果必須依三種值的條件判定

- 修正後實測的結果必須只使用下表的三種值之一，每個值依「條件」欄判斷。
- 既有、無關的不通過與轉回項目不得降低結果。
- 評估報告沒有要求的情境必須寫在剩餘風險，不得降低結果。

| 結果         | 條件                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 待使用者驗證 | 修正前版本至少一項完整預期行為不通過、修正後每項完整預期行為通過、要補的測試修正前不通過而修正後通過，而且沒有回歸                     |
| 部分         | 修正後沒有完整預期行為不通過，也沒有回歸，但有檢查略過、無法執行，或修正前版本沒有重現錯誤，或要補的測試在修正前版本沒有不通過           |
| 失敗         | 修正後任一項完整預期行為不通過，或有回歸                                                                                             |

## Good Example

- 修正前版本重現了錯誤，修正後 E1～E4 都通過，新測試修正前不通過而修正後通過；回歸檢查的 2 項不通過在修正前同樣不通過，I1 是轉回項目，換頁情境沒有量到，寫在剩餘風險；所以結果為「待使用者驗證」。

情境：

- 修正前版本：E2、E3 不通過（成功重現）。
- 修正後版本：E1～E4 通過。
- 新 e2e：修正前不通過（符合預期），修正後通過。
- 回歸檢查：2 項修正後不通過（既有、無關）。
- I1：仍會發生（轉回項目）。
- 換頁中的情境沒有量到，寫在剩餘風險。
- 結果：待使用者驗證。

## Bad Example

- 修正前版本沒有重現錯誤，只能證明修正後沒有出問題，不能證明修法有效；結果應為「部分」，卻寫成「待使用者驗證」。

情境：

- 修正前版本：E1～E4 都通過（沒有量到位移）。
- 修正後版本：E1～E4 通過。
- 新 e2e：修正前通過，修正後通過。
- 結果：待使用者驗證。

# Rule 3 - 修正前實測的結果必須依評估報告的症狀判定

- 修正前實測的結果必須只使用「已重現」、「未重現」或「部分」。
- 任一項完整預期行為或重現步驟，依評估報告的量測方式量到評估報告描述的症狀時，必須寫「已重現」。
- 能觀察症狀的重現步驟或量測沒有執行（例如需要對外網路或瀏覽器），而且其他項目都沒有量到症狀時，必須寫「部分」，不得寫「未重現」。
- 寫「部分」時，必須在說明欄寫出略過的步驟、原因與補齊條件。
- 所有能觀察症狀的步驟都已執行，而且都沒有量到症狀時，必須寫「未重現」，並在說明欄寫出依評估報告的哪個量測方式、量到什麼數值。
- 「修正後」欄必須寫「不適用」。

## Good Example

### Example 1

- 依評估報告的量測方式量到位移，結果為「已重現」，「修正後」欄寫「不適用」。

情境：

| # | 預期行為 | 修正前                                   | 修正後 | 結果   |
| - | -------- | ---------------------------------------- | ------ | ------ |
| E2 | 不位移  | 不通過：載入中清單下移 28px              | 不適用 | 已重現 |

### Example 2

- 重現需要送到實際的 Discord Webhook，該步驟被略過，其他項目沒有量到症狀；結果寫「部分」，說明欄寫出略過的步驟、原因與補齊條件。

情境：

| # | 預期行為             | 修正前                                                                 | 修正後 | 結果 |
| - | -------------------- | ---------------------------------------------------------------------- | ------ | ---- |
| E1 | 逾期通知送到 Webhook | 略過：需要對外網路，沒有執行；補齊條件：提供可用的測試 Webhook 後重跑 | 不適用 | 部分 |

## Bad Example

### Example 1

- 實測沒有照評估報告的量測方式，也沒有量到症狀，就寫「未重現」，說明欄沒有量到的數值，讀者無法判斷錯誤是否真的不存在。

情境：

| # | 預期行為 | 修正前                   | 修正後 | 結果   |
| - | -------- | ------------------------ | ------ | ------ |
| E2 | 不位移  | 通過：看起來沒有位移     | 不適用 | 未重現 |

### Example 2

- 重現需要送到實際的 Discord Webhook，該步驟被略過，卻寫「未重現」；沒有執行就沒有證據證明錯誤不存在。

情境：

| # | 預期行為             | 修正前               | 修正後 | 結果   |
| - | -------------------- | -------------------- | ------ | ------ |
| E1 | 逾期通知送到 Webhook | 略過：需要對外網路 | 不適用 | 未重現 |

# Rule 4 - 使用者驗證項目必須依症狀的觀察方式選擇操作

- 每個驗證項目必須對應完整預期行為的編號。
- 最後一項驗證項目必須確認使用者原本回報的現象已消失。
- 驗證項目不得列轉回 SDD 流程的項目。
- 症狀在畫面上可以看到時，操作必須是一般使用者不用工具就能做的動作，通過標準必須是用眼睛就能判斷的條件。
- 症狀只能用命令觀察時（例如測試結果），操作必須是使用者在終端機執行的命令，通過標準必須是可以從命令輸出判斷的條件。
- 症狀取決於時刻時，操作必須使用模擬時刻的命令。
- 驗證項目不得列出需要等待實際時間才能做的操作。

## Good Example

- 月底報表的測試只在月底失敗；U1 用模擬時刻的終端機命令，通過標準可以從輸出判斷，不需要等待。

情境：

| # | 對應 | 操作                                              | 通過標準   |
| - | ---- | ------------------------------------------------- | ---------- |
| U1 | E1  | `FAKE_NOW=2026-02-28T23:59 npm test -- report`    | 輸出 0 failed |

## Bad Example

- U1 要使用者等到 2 月 28 日晚上才能操作，需要等待數天；同一症狀也沒有改用模擬時刻的命令。

情境：

| # | 對應 | 操作                                                  | 通過標準   |
| - | ---- | ----------------------------------------------------- | ---------- |
| U1 | E1  | 等到 2 月 28 日晚上再執行 `npm test -- report`        | 輸出 0 failed |
