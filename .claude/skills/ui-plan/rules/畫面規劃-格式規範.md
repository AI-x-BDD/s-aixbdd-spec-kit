# Rule 1 - 頁面必須依功能流程切分並以 index.html 為入口

- 在同一段流程中相鄰、且共用主要內容的畫面，例如表單與送出後的結果，必須放在同一頁，以畫面狀態切換。
- 主要內容不同的畫面才拆成不同頁；不得為同一個畫面的成功、失敗或錯誤狀態各開一頁。
- 頁面檔名必須使用英文小寫與連字號，副檔名為 `.html`。
- 頁面清單第一列必須是流程的第一個畫面，檔名必須為 `index.html`。
- 每個負責介面必須至少對應一頁；一頁可以對應多個負責介面。

## Good Example

- 餐廳訂位的負責介面為 F1 時段選擇介面、F2 訂位填寫與結果介面、F3 我的訂位介面。填寫訂位資料、送出中與訂位成功共用同一筆訂位內容，放在 `booking.html` 以狀態切換；流程第一個畫面是時段選擇，命名為 `index.html`。

| 檔案 | 畫面 | 介面 | 進入方式 |
| ---- | ---- | ---- | -------- |
| `index.html` | 時段選擇 | F1 | 雛形入口；頁首「選擇時段」 |
| `booking.html` | 訂位填寫與結果 | F2 | 時段選擇的「訂這個時段」 |
| `my-bookings.html` | 我的訂位 | F3 | 頁首「我的訂位」；訂位成功的「查看我的訂位」 |

## Bad Example

- 同一組介面，第一頁命名為 `home.html`；訂位的填寫、成功與額滿各開一頁；F3 我的訂位沒有對應的頁面。

| 檔案 | 畫面 | 介面 | 進入方式 |
| ---- | ---- | ---- | -------- |
| `home.html` | 時段選擇 | F1 | 雛形入口 |
| `booking-form.html` | 填寫訂位資料 | F2 | 時段選擇的「訂這個時段」 |
| `booking-success.html` | 訂位成功 | F2 | 送出訂位後 |
| `booking-full.html` | 時段已額滿 | F2 | 送出訂位後 |

# Rule 2 - 每列必須追溯到需求且只涵蓋負責介面

- 第 1 節每列的需求依據，必須在每個需求編號後寫出對應的需求內容。
- 第 3.3、4、5 節每列的需求依據，必須至少引用一個目標 spec 中存在的需求編號（US、FR、NFR、SC）或 Edge Cases 項目名稱，可以只寫編號或名稱。
- 需求依據不得只寫「依需求」、「依 spec」，也不得留空。
- 第 1 節與第 3.1 節的介面欄只能出現負責介面；不得把後端、資料庫或第三方介面列成畫面。
- 「不在範疇」可以引用其他介面的編號與名稱，說明該功能由哪個介面負責。
- 第 3.2 節流程圖的節點代號不得與 `plan.md` 盤點表中的介面編號相同，例如不得以 `B1`、`F2` 當節點代號。
- spec 沒有涵蓋、但使用者可能預期的畫面，必須列在「不在範疇」並說明原因，不得列成畫面。

## Good Example

- 餐廳訂位的第 1 節寫出每個編號的需求內容；第 3.3 節只引用編號；spec 沒有涵蓋的會員中心列在「不在範疇」，由簡訊服務負責的訂位通知引用其介面編號；流程圖的節點代號用 `A`、`B`、`C`，不與盤點表的 `B1` 訂位 API 撞名。

| 介面 | 畫面 | 需求依據 |
| ---- | ---- | -------- |
| F1 時段選擇介面 | 時段選擇 | US1；FR-001 依日期與人數顯示可訂時段；Edge Cases 人數超過單桌上限 |
| F2 訂位填寫與結果介面 | 訂位填寫與結果 | US1；FR-002 填寫訂位人姓名與手機；FR-003 時段額滿時拒絕並提示；Edge Cases 時段已額滿 |

| 編號 | 畫面 | 操作 | 需求依據 |
| ---- | ---- | ---- | -------- |
| A1 | `index.html` | 選擇日期與人數，查看可訂時段 | FR-001 |
| A2 | `booking.html` | 填寫訂位人姓名與手機並送出訂位 | FR-002、FR-003 |

不在範疇：

- 會員中心與點數：spec 沒有涵蓋，雛形假設訂位人以手機號碼辨識。
- 訂位成功簡訊：由 P1 簡訊通知服務負責，雛形只在訂位成功畫面顯示「已傳送簡訊至 0921556118」。

```mermaid
  A["index.html<br>時段選擇"] -->|訂這個時段| B["booking.html<br>填寫訂位資料"]
  B -->|送出訂位| C["booking.html<br>訂位成功"]
```

## Bad Example

- 同一份 spec，第 1 節的需求依據只寫「依需求」；把後端的 B1 訂位 API 列成畫面；spec 沒有的會員中心被列成畫面；第 3.3 節 A2 的需求依據留空；流程圖以 `B1`、`B2` 當節點代號，與盤點表的 `B1` 訂位 API 撞名。

| 介面 | 畫面 | 需求依據 |
| ---- | ---- | -------- |
| F1 時段選擇介面 | 時段選擇 | 依需求 |
| B1 訂位 API | 訂位 API 呼叫 | FR-002 |
| F3 我的訂位介面 | 會員中心 | 依 spec |

| 編號 | 畫面 | 操作 | 需求依據 |
| ---- | ---- | ---- | -------- |
| A2 | `booking.html` | 送出訂位 | |

# Rule 3 - 狀態與錯誤回饋必須涵蓋 Edge Cases 並寫出實際文字

- 第 4 節必須為每頁列出畫面會經過的狀態；有適用時，必須包含載入中、空狀態、等待外部結果與成功狀態。
- 第 5 節必須涵蓋負責介面需求依據中的每個 Edge Case 與驗證規則，每個 Edge Case 或驗證規則至少一列。
- 第 5 節的觸發條件必須寫出具體值，例如人數 9 位、手機少於 10 碼。
- 第 5 節的畫面回饋必須寫出畫面實際顯示的文字與位置，不得只寫「顯示錯誤訊息」。

## Good Example

- 餐廳訂位的 `booking.html` 列出送出中與成功狀態，`my-bookings.html` 列出載入中與空狀態；第 5 節涵蓋兩個 Edge Cases 與手機格式驗證，回饋寫出實際文字。

| 畫面 | 狀態 | 呈現方式 | 需求依據 |
| ---- | ---- | -------- | -------- |
| `booking.html` | 填寫訂位資料 | 上方顯示 2026-11-08（六）18:30、4 位，下方為訂位人表單 | FR-002 |
| `booking.html` | 送出訂位中 | 送出按鈕改為「訂位中…」並停用 | FR-002 |
| `booking.html` | 訂位成功 | 顯示「訂位成功」與訂位編號 RS20261108017 | FR-002 |
| `my-bookings.html` | 載入中 | 訂位卡以灰色骨架顯示 | FR-004 |
| `my-bookings.html` | 沒有訂位 | 顯示「還沒有訂位」與「選擇時段」 | FR-004 |

| 畫面 | 情境 | 觸發條件 | 畫面回饋 | 需求依據 |
| ---- | ---- | -------- | -------- | -------- |
| `index.html` | 人數超過單桌上限 | 人數選 9 位 | 人數欄下方顯示「單桌最多 8 位，9 位以上請來電 02-2771-5566」，時段按鈕停用 | Edge Cases 人數超過單桌上限 |
| `booking.html` | 手機號碼格式錯誤 | 去掉「-」後不是 09 開頭的 10 碼數字 | 欄位紅框與「請輸入 09 開頭的 10 碼手機號碼」 | FR-002 |
| `booking.html` | 時段已額滿 | 送出時 18:30 已被訂滿 | 頁頂提示「18:30 已額滿，請改選其他時段」與「回到時段選擇」 | FR-003；Edge Cases 時段已額滿 |

## Bad Example

- 同一組畫面，第 4 節每頁只有「正常」；第 5 節的回饋只寫「顯示錯誤訊息」，觸發條件沒有具體值；Edge Case「人數超過單桌上限」沒有出現。

| 畫面 | 狀態 | 呈現方式 | 需求依據 |
| ---- | ---- | -------- | -------- |
| `booking.html` | 正常 | 顯示訂位表單 | FR-002 |
| `my-bookings.html` | 正常 | 顯示訂位列表 | FR-004 |

| 畫面 | 情境 | 觸發條件 | 畫面回饋 | 需求依據 |
| ---- | ---- | -------- | -------- | -------- |
| `booking.html` | 輸入錯誤 | 輸入不正確 | 顯示錯誤訊息 | FR-002 |
| `booking.html` | 時段已額滿 | 時段滿了 | 顯示錯誤訊息 | FR-003 |
