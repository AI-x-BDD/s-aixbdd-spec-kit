# Rule 1 - 負責介面必須依端點類型與職責判定

- `plan.md`「系統介面盤點」中端點類型不是前端、後端、資料庫，且負責通知觸發、送出、重試或結果追蹤的介面，必須列為負責介面。
- 端點類型不是前端、後端、資料庫，但不負責上述工作的介面，必須列在「不在範疇」，理由必須寫出端點類型與它不負責通知的原因。
- 端點類型是前端、後端或資料庫的介面不得列為負責介面，也不必列在「不在範疇」；即使它與通知有關（例如重送 API、通知紀錄資料表），也只能在介面規格與轉換表中引用。

## Good Example

- 排程、Email 服務與它的本機替身列為負責介面；條碼掃描器是硬體端點、不負責通知，列在「不在範疇」並寫出理由；重送 API B3 是後端介面，沒有列入。

| 介面 | 端點類型 | 判定 | 理由 |
| ---- | -------- | ---- | ---- |
| S1 到館通知排程 | 排程 | 負責介面 | 觸發並送出通知、處理自動重試 |
| E1 Email 服務送出 | 通知服務 | 負責介面 | 送出通知並取得回應 |
| E2 本機 Email 服務替身 | 通知服務 | 負責介面 | 重現 E1 的各類回應 |
| M1 條碼掃描器 | 硬體 | 不在範疇 | 硬體端點，只登記書籍到館，不觸發或追蹤通知 |

## Bad Example

- 後端的重送 API B3 被列為負責介面；條碼掃描器 M1 沒有出現在任何一張表，讀者無法判斷它是被遺漏還是被排除。

| 介面 | 端點類型 | 判定 | 理由 |
| ---- | -------- | ---- | ---- |
| S1 到館通知排程 | 排程 | 負責介面 | 觸發並送出通知 |
| E1 Email 服務送出 | 通知服務 | 負責介面 | 送出通知 |
| B3 通知重送 API | 後端 | 負責介面 | 與通知有關 |

# Rule 2 - 識別字必須沿用上游，缺口必須列為上游衝突

- 狀態值、失敗原因值、資料表與欄位名稱、`operationId` 與 API 路徑必須逐字沿用 `data/`、`contracts/` 或 `research.md`。
- 需要的識別字在上游不存在，或兩份上游互相矛盾時，必須在「上游衝突」寫出位置、問題與處理 Skill（`api-plan`、`data-plan`、`ui-plan` 或 `technical-research`）。
- 不得自創上游沒有的欄位、Enum 值或 `operationId`，也不得修改上游檔案。

## Good Example

- 合約的狀態 `enum` 少了資料模型已有的 `uncertain`；轉換表沿用資料模型的值，差異列為上游衝突並交給 `api-plan`。

| 編號 | 位置 | 問題 | 處理 Skill |
| ---- | ---- | ---- | ---------- |
| UC1 | `contracts/openapi.yaml` `HoldNotification.status` | `enum` 缺少 `uncertain`，與 `data/data-model.dbml` 的 `Enum hold_notification_status` 不一致 | `api-plan` |

## Bad Example

- 同一情境中，轉換表自創上游沒有的 `unknown_result` 狀態，也沒有列出合約與資料模型的不一致。

| 從 | 事件 | 到 | 觸發介面 | 寫入欄位 | 需求 |
| -- | ---- | -- | -------- | -------- | ---- |
| `sending` | 15 秒沒有回應 | `unknown_result` | E1 | `status` | FR-007 |

# Rule 3 - 狀態轉換必須完整且可追溯

- 狀態表必須列出上游狀態 Enum 的每一個值，並標出是否為終態。
- 每個轉換必須寫出觸發介面、寫入的欄位與需求編號。
- 每個非終態都必須寫出系統停止運作後恢復時的處理。

## Good Example

- `Enum hold_notification_status` 的 5 個值都在狀態表；`queued`、`sending` 兩個非終態都寫出恢復處理。

| 停止時的狀態 | 恢復後的處理 | 觸發介面 | 需求 |
| ------------ | ------------ | -------- | ---- |
| `queued` | 第一次排程繼續送出，`attempt_count` 沿用 | S1 | FR-005、FR-008 |
| `sending` | 第一次排程改成 `uncertain`，`failure_reason = connection_lost` | S1 | FR-007、FR-008 |

## Bad Example

- 同一 Enum 只列了 4 個值，漏掉 `uncertain`；`sending` 停止後恢復時怎麼處理沒有寫出，轉換也沒有寫入欄位。

| 從 | 事件 | 到 | 觸發介面 | 寫入欄位 | 需求 |
| -- | ---- | -- | -------- | -------- | ---- |
| `queued` | 送出請求 | `sending` | S1 | — | FR-003 |
| `sending` | 回應 202 | `delivered` | E1 | — | FR-004 |

# Rule 4 - 失敗分類、重試界線與重複處理必須區分是否已收到

- 外部服務的每一類回應（成功、每個錯誤狀態碼、逾時、送出前連線失敗、送出後連線中斷）都必須有一列分類。
- 每一列必須寫出「確定沒收到」、「是」或「不確定」其中一種對方收到情況。
- 只有「確定沒收到」且會自己恢復的失敗可以自動重試；「不確定」的回應不得自動重試。
- 重試次數與等待上限必須取自 spec 或 `research.md`；兩者都沒有時必須列入業務規則缺口。
- 重複處理必須列出每個可能造成重複通知的來源、對應的防護與殘留風險；沒有殘留風險時寫「無」。
- 不得寫「保證不重複」或同義的絕對保證。

## Good Example

- 逾時與送出後中斷標為「不確定」且不自動重試；重複處理寫出重試與手動重送的殘留風險。

| 回應 | 分類 | 對方是否收到 | 自動重試 | 等待與上限 | 最終狀態與原因 | 需求 |
| ---- | ---- | ------------ | -------- | ---------- | -------------- | ---- |
| 503 | 暫時失敗 | 確定沒收到 | 是 | 固定 30 秒；總共最多 3 次 | `failed`／`provider_error` | FR-005 |
| 15 秒沒有回應 | 結果不明 | 不確定 | 否 | — | `uncertain`／`timeout` | FR-007 |

| 來源 | 防護 | 殘留風險 |
| ---- | ---- | -------- |
| 館員手動重送 `uncertain` 通知 | 重送前顯示確認視窗 | 前一次其實已寄出時，會員會收到兩封 |

## Bad Example

- 同一情境中，逾時被歸為暫時失敗並自動重試；重複處理只寫「保證不重複」，沒有來源與殘留風險。

| 回應 | 分類 | 對方是否收到 | 自動重試 | 等待與上限 | 最終狀態與原因 | 需求 |
| ---- | ---- | ------------ | -------- | ---------- | -------------- | ---- |
| 15 秒沒有回應 | 暫時失敗 | 確定沒收到 | 是 | 30 秒 | `failed`／`timeout` | FR-007 |

```text
重複處理：以唯一約束保證不重複。
```

# Rule 5 - 介面規格必須寫出該類型的必寫項

- 排程介面必須寫出觸發時機、時間來源、讀取的資料、寫入的資料、重疊執行時的處理與系統恢復時的處理。
- 外部通知服務介面必須寫出請求（方法、路徑或位址、主要標頭、逾時）、回應對照，以及通知內容的逐行版面與一個填好值的範例。
- 通知內容的逐行版面必須寫出每一行的固定文字與資料來源欄位。
- 本機替身介面必須寫出每個控制操作的請求、回應與錯誤回應，並列出每個模式對應重現的回應。

## Good Example

- 本機替身列出控制操作、錯誤回應與每個模式重現的回應。

| 操作 | 請求 | 回應 | 錯誤回應 |
| ---- | ---- | ---- | -------- |
| 設定模式 | `PUT /__mock/mode`，body `{"mode": "<模式>"}` | 204 | 模式不存在：400 `{"error": "unknown mode"}` |
| 查詢收到的郵件 | `GET /__mock/messages` | 200，郵件陣列 | — |

- 模式：`accept`（202）、`unavailable`（503）、`hang`（不回應）、`drop_after_send`（記錄郵件後中斷連線）。

## Bad Example

- 同一替身只寫一句說明，沒有控制操作的請求與錯誤回應，也沒有模式對照，`tasks` 無法據此排出實作任務。

```text
E2：本機 Email 替身，可以切換各種回應。
```

# Rule 6 - 驗收情境必須涵蓋每類失敗，業務規則缺口必須交給使用者決定

- 每個驗收情境必須使用 Given／When／Then，並標出介面與需求編號。
- 失敗分類表的每一種分類必須至少有一個驗收情境。
- 必須至少有一個「對方可能已收到、本機沒收到回應」的驗收情境，Then 必須寫出不自動重送。
- spec 沒有決定、且不同做法會產生不同可觀察行為的業務規則，必須列入業務規則缺口，經使用者決定後寫入「使用者決定」；不得自行推定。
- 只影響實作方式、不改變可觀察行為的選擇不得列入業務規則缺口。

## Good Example

- 送出後中斷的情境寫出對方可能已收到，且不自動重送；日期是否顯示星期會改變會員看到的內容，交給使用者決定。

- NS4 對方可能已收到、本機沒收到回應：Given E2 模式為 `drop_after_send`；When 排程執行；Then 通知為 `uncertain`／`connection_lost`，E2 有 1 封郵件，之後的排程不自動重送。

| 編號 | 問題 | 決定 | 影響段落 |
| ---- | ---- | ---- | -------- |
| UD1 | 「保留至」日期是否顯示星期？ | 不顯示，只寫 YYYY-MM-DD | 第 5.2 節 |

## Bad Example

- 同一情境中，驗收情境只有成功一種；日期格式由執行者自行決定為顯示星期，沒有交給使用者；排程套件的選擇不影響可觀察行為，卻被列為業務規則缺口。

- NS1 送出成功：Given 預約可取書；When 排程執行；Then 通知為 `delivered`。

| 編號 | 問題 | 決定 | 影響段落 |
| ---- | ---- | ---- | -------- |
| UD1 | 排程用 `setInterval` 還是 `node-cron`？ | `node-cron` | 第 5.1 節 |
