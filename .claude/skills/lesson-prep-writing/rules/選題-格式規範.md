# Rule 1 - 方向必須延伸自使用者的想法與素材

- 每個方向必須延伸自已載入構想及來源版本的想法或素材。
- 不得另找與已載入想法和素材都無關的新主題。

## Good Example

- 想法是「GitHub Actions 跑太慢」，方向從使用者記錄的 workflow 設定延伸。

| `00-idea.md` 的想法    | `00-idea.md` 的素材                      | 方向                                      |
| ---------------------- | ---------------------------------------- | ----------------------------------------- |
| GitHub Actions 跑太慢 | `ci.yml`，每次執行都花 6 分鐘裝 npm 依賴 | 用 `actions/cache` 快取 npm 依賴          |

## Bad Example

- 同一個想法，方向換成使用者沒有提到的另一套工具。

| `00-idea.md` 的想法    | `00-idea.md` 的素材                      | 方向                                      |
| ---------------------- | ---------------------------------------- | ----------------------------------------- |
| GitHub Actions 跑太慢 | `ci.yml`，每次執行都花 6 分鐘裝 npm 依賴 | 從零開始架設 Jenkins                      |

# Rule 2 - 三個角度必須回答各自的問題

- 高度必須寫出讀者真正想達成的目標，而不是文章主題本身。
- 深度必須列出實際問題、原始資料或測試。
- 廣度必須列出可以借用的其他角度。

## Good Example

- 三個角度各自回答不同的問題。

- 高度：讀者想要的是推完 commit 後 2 分鐘內知道有沒有壞，而不是「設定快取」。
- 深度：`ci.yml` 中 `npm ci` 佔掉 6 分鐘裡的 4 分鐘；可以比較加上快取前後的執行時間。
- 廣度：可以借用建置系統的角度（只重跑有變動的套件），或測試的角度（先跑最快失敗的測試）。

## Bad Example

- 同一個主題，三個角度都只是重複主題，沒有回答各自的問題。

- 高度：介紹 GitHub Actions 快取。
- 深度：深入介紹 GitHub Actions 快取。
- 廣度：更多 GitHub Actions 快取的用法。

# Rule 3 - 讀完後能做到什麼必須是可觀察的行動

- 「讀完後能做到什麼」必須是可觀察的行動或產出。
- 不得只寫「了解」「認識」「掌握」等無法觀察的結果。

## Good Example

- 結果可以由讀者的 workflow 執行紀錄判斷。

- 讀完後能做到什麼：在 `ci.yml` 加上 `actions/cache`，讓第二次執行的 `npm ci` 步驟少於 1 分鐘。

## Bad Example

- 同一個方向只寫「了解」，無法判斷讀者是否做到。

- 讀完後能做到什麼：了解 GitHub Actions 快取的原理。

# Rule 4 - 素材必須標示已有或待準備

- 需要準備的素材必須逐項標示「已有」或「待準備」。
- 標示必須依已載入的構想、來源版本及補充素材判斷；未取得的素材不得標成「已有」。

## Good Example

- `00-idea.md` 只記錄了 `ci.yml`，其餘素材標示為待準備。

- 需要準備的素材：
  - 目前的 `ci.yml`（已有）
  - 加上快取前後的執行時間截圖（待準備）

## Bad Example

- 同一份 `00-idea.md`，沒有記錄的執行時間截圖被標成已有，`ci.yml` 也沒有標示。

- 需要準備的素材：
  - 目前的 `ci.yml`
  - 加上快取前後的執行時間截圖（已有）

# Rule 5 - 第一版不寫什麼必須列出具體內容

- 「第一版不寫什麼」必須列出至少一項具體的主題或步驟。
- 不得只寫「進階內容」「其他細節」等無法判斷範圍的描述。

## Good Example

- 列出的項目可以直接判斷某段內容是否超出範圍。

- 第一版不寫什麼：Docker layer 快取、self-hosted runner、矩陣建置

## Bad Example

- 同一個方向只寫籠統的描述，無法判斷哪些內容不該寫。

- 第一版不寫什麼：進階內容

# Rule 6 - 研究證據必須可追溯並區分用途

- 讀者研究必須先提出3～5群候選讀者與驗證條件，再核對真實發文；每群必須規劃中文2組、英文1組查詢，近12個月不足時可以放寬至24個月。
- 每群應以10～20則為採樣目標；不足必須記錄缺口，未滿研究計畫驗證條件的群不得作確定推薦。
- 研究必須保留查詢日期、發文日期、網址、短原話、排除理由及缺口；必須排除廣告與無具體工作情境的內容，個人資料必須匿名化。
- 讀者卡必須依工作分群，分析卡點、素材能及不能回答的範圍、代表原話、詞彙與案例選取理由。
- 搜尋導向研究必須分別保存SERP、搜尋量、競爭及作者資料的來源。SERP必須記查詢詞、日期、地區、語言、實際排名網址及意圖判讀；搜尋量必須記工具、估計值或區間、地區、語言及資料期間。
- 競爭判斷必須依已讀排名頁的涵蓋與可補足處；作者資料必須包含網站現況、能力、可投入資源與取得日期。
- 每題必須對回課程來源、可回答範圍及待補工作。SERP結果數、發文則數及互動數不得替代搜尋量；採樣目標不得作為搜尋量或競爭門檻。
- 自製研究測試資料必須明示虛構，不得寫成真實研究。

## Good Example

- 自製書目例分開保存問題證據與未知的量資料。

- 讀者：有同名書去重工作的館員；測試資料僅2則，驗證條件未滿，推薦暫定。
- 原話：「同名卻不同作者怎麼辦？」；來源為自製測試紀錄，無真實網址。
- 搜尋量：工具未提供，待補；競爭：尚未讀排名頁。
- 課程支持：書目示例v1第2段能回答先比作者；網站與投入資源待補。

## Bad Example

- 同一份虛構資料被冒充為真實調查，並拿則數代替量。

- 推薦館員：已查2則真實發文，因此每月搜尋量為2，競爭低，適合立刻投入。

# Rule 7 - 候選優先序必須共同對照四項證據

- 每題的優先序與理由必須共同對照搜尋需求、排名競爭、作者目前資源及課程支持程度。
- 缺項時必須標為暫定，指出該缺項可能如何改變排序；不得自行設定固定量門檻或只按量排序。
- 低需求或高量題的投入價值必須依本次作者條件判斷，高量不得直接推定高競爭或不可競爭。

## Good Example

- 自製書目例的排序保留缺資料的影響。

- 「同名書辨識」暫列優先：素材已有作者比對，作者能提供案例；量與排名頁待補，取得後可能改變排序。
- 「自動建立全館目錄」暫緩：素材未涵蓋，超出目前投入資源；需求大小尚待研究。

## Bad Example

- 相同兩題只按虛構量值排名。

- 自動建立全館目錄有一萬次搜尋，必須排第一；少於一千次都不寫，不必查排名或作者資源。
