# Rule 1 - 每個角色都必須預設大綱有問題並提出實際修改

- 每項修改必須以「<角色>-<N>」編號，並寫出位置、原文、修改後與理由。
- 不得只給評論、修改方向或模仿角色的語氣，而沒有修改後的文字。
- 每個角色必須預設大綱在自己的職責範圍內有問題，並逐節檢查。
- 角色沒有提出修改時，必須逐節寫出檢查了什麼與不需修改的理由；不得只寫「沒有問題」或「整體不錯」。

## Good Example

### Example 1

- 修改有編號、位置、原文、修改後與理由，使用者可以直接比對並決定是否採用。

- 講師-1
  - 位置：「## 5. 循序練習大綱」第 3 段「3. 把 build 與 runtime 拆成兩個 stage」的讀者的小練習
  - 原文：寫出兩個 stage 的 Dockerfile，再改用 distroless 或自己編譯 musl 版本
  - 修改後：寫出兩個 stage 的 Dockerfile，runtime stage 只複製 build stage 產出的執行檔
  - 理由：動詞版定義只讓讀者用 multi-stage build 縮小映像檔，distroless 與 musl 已列在範圍外，留在練習中會超出「從 1 走到 3」的範圍。

### Example 2

- 編輯沒有提出修改，但逐一寫出職責範圍內每個練習段落檢查了什麼與不需修改的理由。

- 編輯：沒有修改
  - 「## 5. 循序練習大綱」第 1 段「1. 量出目前的映像檔大小」：標題是讀者要做的動作，只對應 SOP 第 1 步，不需刪減。
  - 第 2 段「2. 找出最大的 layer」：與第 1 段各自對應一個 SOP 步驟，沒有重複。
  - 第 3 段「3. 把 build 與 runtime 拆成兩個 stage」：標題說出做法，只看三個段落標題就能讀出「量出大小、找出原因、拆開 stage」這條主線，順序不需調整。

## Bad Example

### Example 1

- 同一段只有評論，沒有原文與修改後的文字，使用者無法決定要採用什麼。

- 講師：第 3 段有點離題，建議精簡，讓大綱更聚焦。

### Example 2

- 同一情境中，編輯只寫結論，看不出檢查了哪些段落。

- 編輯：沒有問題，整體不錯。

# Rule 2 - 各角色必須依職責修改大綱

- 每個角色的修改必須屬於下表該角色的職責。
- 各角色必須依職責完成下表的檢查。

| 角色     | 職責                                                                                         |
| -------- | -------------------------------------------------------------------------------------------- |
| 講師     | 依已載入備課Rule 5、6、8檢查成果、教學增益與檢核對應，修改超出本篇動詞版定義的內容 |
| 目標讀者 | 依大綱的詞彙表、SOP 與練習，標出讀者可能看不懂的詞、缺少的前提或無法銜接的步驟，並改寫       |
| 編輯     | 依備課Rule 6核對新增內容及重複位置，提出有理由的保留／縮短／合併／刪除修改；調整順序及標題，保留成果所需解說 |
| 紅隊     | 檢查大綱的假設與預定論點，找出反例、可能誇大的說法與缺少證據的地方，並改寫或刪除             |
| 文件類型編輯（交接指定時） | 依成果判斷文類，引用備課Rule 5、6、8檢查逐節內容；不得只因屬於另一文類而刪除必要前提、推理或對照例 |

## Good Example

- 編輯對自製書目教材的重述提出可直接套用的刪改，講師保留必要對照例。

- 編輯-1
  - 位置：同名書比較表後一句
  - 原文：第一本作者是甲，第二本作者是乙。
  - 修改後：刪除此句。
  - 理由：依備課Rule 6，比較表已列同一資訊，此句無新增用途；保留下一句作者不同所以暫不合併的推理。
- 講師：缺作者對照例補足證據不足時的判斷，沿用整合檢核；依備課Rule 5、6、8保留。

## Bad Example

- 同一書目教材只修語氣，未檢查重述與理解收益。

- 編輯-1
  - 位置：同名書比較表後一句
  - 原文：第一本作者是甲，第二本作者是乙。
  - 修改後：請注意，第一本作者是甲，第二本作者是乙喔！
  - 理由：更親切，所有案例預設保留。

# Rule 3 - 修改後的完整大綱必須套用所有修改

- 候選完整大綱必須套用本次角色集合列出的每一項建議，狀態必須標為「候選，待作者採用」。
- 候選必須保留各段成果、必要解說、對應檢核及證據；證據缺項必須依證據檢查清單標示，不得留空。
- 原受檢版本與候選必須可區分；候選狀態不得寫成作者已採用或已確認。

## Good Example

- 紅隊-1 把誇大的說法改掉，完整大綱第 1 段的一句重點是修改後的句子，使用的證據欄寫出缺少的證據標記。

| 修改   | 原文                             | 完整大綱第 1 段的一句重點                          | 完整大綱第 1 段的使用的證據                            |
| ------ | -------------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| 紅隊-1 | 每個專案的映像檔都能縮小一半以上 | 先記下目前映像檔的大小，之後才能比較拆分前後的差異 | （待補證據：目前專案執行 `docker images` 的輸出） |

## Bad Example

### Example 1

- 同一項修改已列出，但完整大綱第 1 段的一句重點仍保留原文。

| 修改   | 原文                             | 完整大綱第 1 段的一句重點        | 完整大綱第 1 段的使用的證據                            |
| ------ | -------------------------------- | -------------------------------- | ------------------------------------------------------ |
| 紅隊-1 | 每個專案的映像檔都能縮小一半以上 | 每個專案的映像檔都能縮小一半以上 | （待補證據：目前專案執行 `docker images` 的輸出） |

### Example 2

- 同一項修改已套用，但第 1 段沒有證據，使用的證據欄卻留空。

| 修改   | 原文                             | 完整大綱第 1 段的一句重點                          | 完整大綱第 1 段的使用的證據 |
| ------ | -------------------------------- | -------------------------------------------------- | --------------------------- |
| 紅隊-1 | 每個專案的映像檔都能縮小一半以上 | 先記下目前映像檔的大小，之後才能比較拆分前後的差異 |                             |

# Rule 4 - 外部標準檢查必須給出明確判定與驗證方式

- 判定、缺口與驗證方式必須只針對具名受檢版本，不得以尚未採用的建議已套用為前提。
- 品質及三用途判準必須使用已載入的備課Rule 8；結果必須附具名受檢版本、證據位置、未解項及後續驗證方式。
- 作者採用後必須只重驗受影響項，依實際採用版本記錄品質；作者保留的缺口必須保留原判定。
- 讀者驗證方式必須說明請何種讀者完成何種解釋、判斷或操作，以及觀察何種結果。
- 採用後新版本的結果必須指出受影響項的重驗依據；沿用項必須連回同版有效證據。全部不採用時可以沿用原版本證據。

## Good Example

- 判定針對受檢版本及實際採用結果，保留未解品質缺口。

- 自製書目outline-v2只採用補缺作者解說，作者保留表後重述。依備課Rule 8，內容必要性及整體內容品質仍未通過，證據為v2比較表後一句；使用者驗證未執行。
- 以下操作文例指出缺少的資訊、應補位置及後續驗證方式。

- 大綱是否規劃了讀者完成第一步所需的資訊：否
- 仍缺少的資訊：大綱沒有說明要看 `docker images` 輸出的哪一欄，也沒有說明映像檔名稱從哪裡找，應補在「## 6. 全貌筆記」的「### 今天就能做的第一步」。
- 之後的驗證方式：請一位會寫 Dockerfile、但沒用過 multi-stage build 的後端工程師，只看「### 今天就能做的第一步」，對自己的專案執行 `docker images`，觀察對方能否記下目前映像檔的 `SIZE`。

## Bad Example

### Example 1

- 自製書目outline-v2仍保留表後重述，卻因作者已採用其他修改便把整體內容品質列通過。
- 以下操作文例只寫「大致可以」，缺少位置及驗證方式。

- 大綱是否規劃了讀者完成第一步所需的資訊：大致可以
- 仍缺少的資訊：可能還有一些細節
- 之後的驗證方式：之後再測試

### Example 2

- 同一份大綱的「### 今天就能做的第一步」沒有說明要看哪一欄，判定卻以尚未決定是否採用的目標讀者-2 為前提寫成「是」；使用者沒有採用目標讀者-2 時，判定與受檢查的大綱不符。

- 大綱是否規劃了讀者完成第一步所需的資訊：是
- 仍缺少的資訊：無（以採用目標讀者-2 後的「### 今天就能做的第一步」為準）
- 之後的驗證方式：請一位會寫 Dockerfile、但沒用過 multi-stage build 的後端工程師，只看「### 今天就能做的第一步」，對自己的專案執行 `docker images`，觀察對方能否記下目前映像檔的 `SIZE`。

# Rule 5 - 紅隊風險必須指向大綱的具體位置

- 每個風險必須指出大綱中的位置，例如節名或練習段落標題。
- 每個風險必須說明風險原因。

## Good Example

- 風險指出練習段落標題，並說明讀者可能遇到的失敗。

1. 「## 5. 循序練習大綱」第 3 段「3. 把 build 與 runtime 拆成兩個 stage」只規劃了 Go 程式的練習；用 Node.js 的讀者照這一段寫 Dockerfile，可能漏複製 `node_modules`，容器一啟動就失敗。

## Bad Example

- 同一個風險沒有指出大綱中的位置，也沒有說明原因。

1. 大綱對部分讀者可能不夠友善。

# Rule 6 - 每項修改必須能單獨採用

- 每項修改的原文必須逐字取自本次具名受檢大綱版本。
- 不同修改的原文不得重疊。
- 每項修改的修改後必須能單獨套用到本次具名受檢大綱版本，不得依賴其他修改是否被採用。
- 兩個角色要修改同一處時，必須合併成一項修改，由其中一個角色提出，理由必須寫出兩個角色的考量。
- 合併的修改必須在編號後標明含哪些其他角色的考量，格式為「<角色>-<N>（含<其他角色>的考量）」。
- 同一個問題需要修改大綱中多處時，不論是否屬於同一個角色，每項相關修改的理由必須列出其他相關修改的編號，並說明要一起採用。

## Good Example

### Example 1

- 講師與紅隊都要修改同一句一句重點，合併成一項修改，編號標明含講師的考量；使用者只採用紅隊時，「runtime stage 改用 `alpine`」仍留在大綱中。

- 紅隊-2（含講師的考量）
  - 位置：「## 5. 循序練習大綱」第 3 段「3. 把 build 與 runtime 拆成兩個 stage」的一句重點
  - 原文：runtime stage 改用 `alpine`，一定不會出問題，映像檔還能縮小 80%
  - 修改後：runtime stage 改用 `alpine`，映像檔從 900 MB 降到 150 MB（待補證據：`docker images` 的輸出）
  - 理由：紅隊的考量是「一定不會出問題」與「80%」都沒有證據；講師的考量是這句同時講相容性與大小兩個重點，只保留大小。

### Example 2

- 大綱在「## 4. SOP」第 3 步與練習第 3 段都寫了已列在範圍外的 distroless，講師分成兩項修改，兩項的理由都列出另一項的編號，使用者看得出要一起採用。

- 講師-1
  - 位置：「## 5. 循序練習大綱」第 3 段「3. 把 build 與 runtime 拆成兩個 stage」的讀者的小練習
  - 原文：寫出兩個 stage 的 Dockerfile，再改用 distroless 或自己編譯 musl 版本
  - 修改後：寫出兩個 stage 的 Dockerfile，runtime stage 只複製 build stage 產出的執行檔
  - 理由：distroless 與 musl 已列在範圍外，超出「從 1 走到 3」的範圍；「## 4. SOP」第 3 步也寫了 distroless，由講師-3 修改，要與講師-3 一起採用。
- 講師-3
  - 位置：「## 4. SOP」第 3 步
  - 原文：把 Dockerfile 拆成 build 與 runtime 兩個 stage，runtime stage 改用 distroless。
  - 修改後：把 Dockerfile 拆成 build 與 runtime 兩個 stage，runtime stage 只複製 build stage 產出的執行檔。
  - 理由：distroless 已列在範圍外；練習第 3 段也寫了 distroless，由講師-1 修改，要與講師-1 一起採用。
