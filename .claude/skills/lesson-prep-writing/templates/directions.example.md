# 文章方向：把 Spring Boot 預約系統部署到 AWS

- 狀態：待選定

## 三個角度

- 高度：讀者想要的不是「部署成功」，而是確定上線後預約資料不會出錯，敢把系統交給真實使用者。
- 深度：預約系統最怕最後一個名額被兩個人同時搶到；可以用兩個執行緒同時呼叫 `reserve()` 的測試重現（待補證據：`ConcurrentReserveTest` 的輸出）。部署筆記中記下的 Elastic Beanstalk 環境設定與 RDS 連線字串，也是原始資料。
- 廣度：可以借用資料庫交易的角度（樂觀鎖與悲觀鎖），或維運的角度（上線後怎麼從 CloudWatch 看出問題）。

## 普通模糊選題的三方向

### 方向 1：用併發測試證明預約名額不會被搶兩次

- 適合誰看：會用 Spring Data JPA 寫 CRUD、還沒處理過同時寫入的後端工程師
- 讀完後能做到什麼：寫出一個用 `CountDownLatch` 讓兩個執行緒同時預約的測試，並用 `@Version` 讓測試只剩一個成功
- 需要準備的素材：
  - 預約系統的 `SlotService` 原始碼（已有）
  - 未加 `@Version` 時的併發測試輸出（待準備）
  - 加上 `@Version` 後重跑的測試輸出（待準備）
- 第一版不寫什麼：Redis 分散式鎖、悲觀鎖、部署到 AWS 的步驟

### 方向 2：第一次把 Spring Boot 部署到 Elastic Beanstalk

- 適合誰看：只在本機跑過 Spring Boot、還沒部署過雲端的後端工程師
- 讀完後能做到什麼：用 `eb deploy` 把專案部署上線，並從瀏覽器打開健康檢查網址看到 `UP`
- 需要準備的素材：
  - 部署到 AWS 時的筆記（已有）
  - `eb deploy` 的完整輸出（待準備）
  - Elastic Beanstalk 主控台的環境健康狀態截圖（待準備）
- 第一版不寫什麼：RDS 的建立與連線、自訂網域與 HTTPS、CI 自動部署

### 方向 3：上線後從 CloudWatch 找出最慢的預約 API

- 適合誰看：系統已部署到 AWS、但上線後只會看應用程式 log 的後端工程師
- 讀完後能做到什麼：在 CloudWatch Logs Insights 寫一條查詢，列出回應時間最長的 5 個 API
- 需要準備的素材：
  - 部署到 AWS 時的筆記（已有）
  - 預約 API 的存取 log 範例（待準備）
  - Logs Insights 查詢與查詢結果（待準備）
- 第一版不寫什麼：CloudWatch 告警設定、X-Ray 分散式追蹤、效能調校
