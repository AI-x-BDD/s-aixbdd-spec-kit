# Rule 1 - 使用者故事必須是可獨立交付與驗證的使用者價值

- 每個使用者故事必須從使用者角度描述一段使用者能得到的成果，不得以技術工作或內部步驟（例如「建立資料表」、「實作 API」）作為故事。
- 只實作該故事時，必須仍能展示並驗證其價值。
- `Independent Test` 必須描述只實作該故事時的驗證方式，以及預期觀察到的結果。

## Good Example

- 故事描述使用者得到的瀏覽成果，獨立測試只需要這個故事就能執行並觀察結果。

```markdown
### User Story 2 - 相簿內照片平鋪式預覽 (Priority: P2)

使用者在主頁面檢視任一相簿時，相簿內的照片以平鋪式網格呈現縮圖，不需逐一點開即可瀏覽。

**Independent Test**: 開啟一個包含多張照片的相簿；驗證照片以整齊的網格排列，且會依視窗寬度調整每列張數。
```

## Bad Example

- 故事是技術工作，使用者得不到可展示的成果；獨立測試也依賴其他故事。

```markdown
### User Story 2 - 建立相簿資料表與查詢 API (Priority: P2)

建立 albums 與 photos 資料表，並提供查詢相簿照片的 API。

**Independent Test**: 等其他故事完成後一起測試。
```

# Rule 2 - 優先級必須依使用者價值與交付順序排列並寫出理由

- `P1` 必須代表最先需要被證明的核心價值；建立在其他故事成果之上的故事，必須排在該故事之後。
- 優先級不得只依需求描述中出現的順序決定。
- 每個故事的 `Why this priority` 必須說明排序理由，不得只重述優先級。

## Good Example

- 相簿分組是其他故事的基礎，排為 P1；拖放整理需要已分組的相簿，排在其後，理由都指出依賴與價值。

| 故事 | 優先級 | Why this priority |
| ---- | ------ | ----------------- |
| 將照片整理至依日期分組的單層相簿 | P1 | 核心資訊架構；沒有相簿與分組，預覽與拖放都無從運作 |
| 在主頁面上透過拖放重新排列與整理照片 | P3 | 需要已分組的相簿與預覽成立後，才能微調排列順序 |

## Bad Example

- 拖放整理依賴相簿分組卻排在最前面，理由只重述優先級。

| 故事 | 優先級 | Why this priority |
| ---- | ------ | ----------------- |
| 在主頁面上透過拖放重新排列與整理照片 | P1 | 這是 P1 |
| 將照片整理至依日期分組的單層相簿 | P2 | 這是 P2 |

# Rule 3 - 驗收情境必須以 Given／When／Then 描述可觀察結果

- 每條驗收情境必須包含 `Given`、`When` 與 `Then`，且 `Then` 必須描述使用者或系統可觀察的結果。
- 每條驗收情境必須只驗證一個結果。
- 每個故事的驗收情境必須涵蓋主要成功路徑，並至少包含一個例外或邊界情況。

## Good Example

- 兩條情境各驗證一個可觀察結果，第二條涵蓋相簿沒有照片的邊界情況。

```markdown
1. **Given** 某相簿內已包含多張照片，**When** 使用者檢視該相簿內容，**Then** 所有照片皆以平鋪式介面呈現清晰縮圖。
2. **Given** 某相簿內尚無任何照片，**When** 使用者檢視該相簿，**Then** 系統顯示繁體中文空白狀態提示，引導使用者新增照片。
```

## Bad Example

- 只有一條情境，同時驗證多個結果，`Then` 也無法觀察，且沒有例外或邊界情況。

```markdown
1. **Given** 使用者有相簿，**When** 使用者瀏覽、調整視窗並新增照片，**Then** 系統運作正常。
```
