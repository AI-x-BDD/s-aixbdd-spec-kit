# Rule 1 - 只把會改變規格骨架、沒有業界預設的項目列為需求缺口

- 需求缺口必須是會改變使用者故事切分、需求歸戶、主要流程或正式驗收標準的缺漏、矛盾或歧義，或和「憲法檢查清單」必須／不得規則無法同時滿足的需求。
- 資料保存期、效能目標、錯誤處理方式、登入方式、整合方式有業界預設可採用時，不得列入需求缺口，必須列入「業界預設項目」並寫出採用的預設內容。
- 需求輸入對上述 5 類的說法互相矛盾，或涉及法規、金錢等重大後果時，仍必須列入需求缺口。
- 需求輸入已指定的做法不是缺口。

## Good Example

- 情境：社團活動報名，社員登入後報名活動，額滿時候補。「額滿後是否自動遞補」會改變主要流程，列為缺口；「報名資料保存期」「頁面回應速度」有業界預設，列為業界預設項目並寫出預設；登入方式沿用需求輸入。

```markdown
需求缺口：
- 額滿後是否自動遞補

業界預設項目：
- 報名資料保存期：活動結束後保存 1 年
- 頁面回應速度：一般網頁操作在 2 秒內回應
- 登入方式：沿用需求輸入的社員登入
```

## Bad Example

- 同一情境把有業界預設的項目列為提問，浪費使用者的回答次數。

```markdown
需求缺口：
- 報名資料要保存多久？
- 頁面多久要載入完成？
```

# Rule 2 - 需求缺口必須依範圍 > 安全／隱私 > 使用者體驗 > 技術細節排序

- 每個缺口必須歸入範圍、安全／隱私、使用者體驗、技術細節其中一類，依此順序排列；同類內影響較大的在前。

## Good Example

- 情境：社團活動報名。「候補是否開放給非社員」屬於範圍，排在最前；「其他社員能否看到報名名單」屬於安全／隱私，排第二；「候補遞補時如何通知」屬於使用者體驗，排第三。

```markdown
需求缺口（已排序）：
1. 候補是否開放給非社員（範圍）
2. 其他社員能否看到報名名單（安全／隱私）
3. 候補遞補時如何通知（使用者體驗）
```

## Bad Example

- 同一情境先問通知方式，再問範圍，順序顛倒。

```markdown
需求缺口（已排序）：
1. 候補遞補時如何通知（使用者體驗）
2. 候補是否開放給非社員（範圍）
```
