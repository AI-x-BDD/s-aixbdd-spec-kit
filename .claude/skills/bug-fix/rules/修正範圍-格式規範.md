# Rule 1 - 只執行核准的修法項目

- 只實作評估報告核准段「核准的修法」列出的項目。
- 替代做法、「不在本次修正範圍」與「轉回 SDD 流程的項目」不得實作，必須在修正報告列為未執行並寫出原因。
- 評估報告的核准狀態或修法首選標為前次已套用的項目，不得重新實作。
- 前次已套用的項目，必須在修正報告「執行的修法」各寫一列，結果寫「保留（前次已套用）」。

## Good Example

### Example 1

- 核准的修法是首選修法第 1～4 項；I1 屬於轉回 SDD 流程的項目，橫幅清除時機維持原狀並列為未執行。

情境：

1. 評估報告核准首選修法第 1～4 項，I1（頁頂橫幅改成載入完成後才清除）轉回 `ui-plan`。
2. 實作只涵蓋第 1～4 項，`handleRefresh()` 的 `setBanner(null)` 沒有修改。
3. 修正報告在「未執行的項目」列出 I1，原因是轉回 SDD 流程，由 `ui-plan` 處理。

### Example 2

- 重新評估後只核准第 6～8 項，只實作第 6～8 項，並把前次已套用的第 1～5 項列為保留。

情境：

1. 重新評估後，評估報告核准首選修法第 6～8 項，第 1～5 項標為前次已套用。
2. 實作只涵蓋第 6～8 項，第 1～5 項的程式沒有修改。
3. 修正報告「執行的修法」列出第 6～8 項的結果，另外各寫一列第 1～5 項，結果寫「保留（前次已套用）」。

## Bad Example

### Example 1

- 實作第 3 項時順手實作 I1；I1 沒有被核准，而且要改變已同意的意圖。

情境：

1. 評估報告核准首選修法第 1～4 項，I1 轉回 `ui-plan`。
2. 實作第 3 項時，順手把頁頂橫幅改成載入完成後才清除。
3. 修正報告沒有列出 I1。

### Example 2

- 重新實作前次已套用的第 1～5 項，或沒有在「執行的修法」列出它們。

情境：

1. 重新評估後，評估報告核准首選修法第 6～8 項，第 1～5 項標為前次已套用。
2. 實作時重新實作第 1～5 項，再實作第 6～8 項。
3. 修正報告「執行的修法」只列出第 6～8 項，沒有列出第 1～5 項為保留。

# Rule 2 - 只修改列出的檔案

- 只能修改評估報告「要改的檔案」與「要補的測試」列出的檔案；列的是目錄或描述時，只能在該範圍內新增或修改檔案。
- 不得修改 `assessment.md`、`spec.md`、`ui/plan.md`、`tasks.md`。
- 雛形只在核准的修法項目包含時才能修改。
- 不得重構和核准項目無關的程式，不得加入評估報告沒有提到的依賴，不得刪除評估報告沒有要求刪除的檔案。

## Good Example

- 「要補的測試」列出 `e2e/overdue-notifications-refresh.spec.ts`（新增），新檔位於列出的 `e2e/` 範圍內。

情境：

1. 評估報告「要改的檔案」列出 `OverdueNotificationsView.tsx` 與雛形 `ui/overdue-notifications.html`，「要補的測試」列出 `e2e/overdue-notifications-refresh.spec.ts`（新增）。
2. 實作只修改這三個檔案。
3. 雛形在核准的第 4 項包含時才修改。

## Bad Example

- 為了讓「版面不位移」有文件依據，順手修改 `ui/plan.md`；`ui/plan.md` 不得修改，I2 屬於轉回 SDD 流程的項目。

情境：

1. 評估報告核准首選修法第 1～4 項，I2（`ui/plan.md` 補寫版面不位移）轉回 `ui-plan`。
2. 實作完成後，順手在 `ui/plan.md` §4 補一句「重新整理與換頁期間版面不位移」。

# Rule 3 - 偏離分為補充與判斷錯誤

- 補充是為了完成核准的項目必須加入、評估報告沒寫到、而且仍在 Rule 1、Rule 2 範圍內的實作細節；必須記錄內容與理由後繼續。
- 判斷錯誤是下列任一情況：修法無法達成評估報告的預期行為、根本原因在別處、需要修改 Rule 2 以外的檔案、需要實作未核准的項目。
- 判斷錯誤必須記錄新發現、停止修改程式，並建議重新執行 `bug-assess`。
- 無法確定屬於補充或判斷錯誤時，必須視為判斷錯誤。

## Good Example

- 新增 `loadedFilter` 狀態是完成第 3 項必須加入的細節，仍在列出的檔案內，記為補充後繼續。

情境：

1. 評估報告第 3 項寫「空狀態依 `items.length` 判斷，不看 `loading`」。
2. 實作時發現只拿掉 `!loading`，從「送出中」切回「全部」的載入期間會先錯誤顯示「目前沒有逾期通知」。
3. 在 `OverdueNotificationsView.tsx` 內新增 `loadedFilter` 狀態，記入偏離：等級為補充，並寫出理由，然後繼續。

## Bad Example

- 需要修改未列出的後端 API 檔才能修好，卻記為補充並繼續修改；這屬於判斷錯誤。

情境：

1. 實作第 3 項時發現，要修改後端 `api/` 底下未列出的檔案才能讓空狀態的資料正確。
2. 把它記為補充，繼續修改後端檔案。
