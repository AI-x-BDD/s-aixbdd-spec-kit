# Rule 1 - 總覽每一列代表一個系統角色

- 「技術堆疊總覽」每一列必須代表本次系統中的一個角色，也就是系統負責的一塊工作（例如 HTTP API、資料庫、端對端測試）。
- 同一角色用到的技術必須寫在同一格，以「、」分隔；同一角色不得拆成多列。
- 採用技術格中的每個技術都必須出現在 research.md 某個主題的 `Decision` 中。
- 決策來源欄必須以 `research §<主題編號>` 列出該列所有技術出自的主題，多個主題以「、」並列（例如 `research §1、§2`）。
- research.md 各 `Decision` 採用、需要選用的語言、平台、框架、套件、服務、資料儲存與工具，都必須出現在某一列。
- 平台內建的功能（瀏覽器 API、Node.js 內建模組與命令列旗標、程式語言標準函式庫的模組、CSS 功能等不需另外選用或安裝的能力）不得出現在任何一格；平台本身（例如原生 JavaScript、Node.js、Python）依前一條列出。
- 只決定設計或實作方式、沒有引入技術的內容（例如資料表欄位、排序策略、API 端點）不得列入。

## Good Example

- 球場預約系統的 research.md 有兩個主題；FastAPI 與 Uvicorn 都負責 HTTP API，寫在同一格；PostgreSQL 與 `psycopg` 都負責預約資料，同一列以 `research §1、§2` 列出來源；標準函式庫 `zoneinfo` 是平台內建功能，`tstzrange` 欄位是設計方式，都不列。

research.md 片段：

```markdown
## 1. 後端與資料庫
- **Decision**: 後端採用 **Python 3.12 以上**與 **FastAPI**，以 **Uvicorn** 執行，資料庫使用 **PostgreSQL 16**，以 **`psycopg` 3** 連線；時區轉換使用標準函式庫 `zoneinfo`。

## 2. 預約衝突防止
- **Decision**: 以 **PostgreSQL 16** 的 `EXCLUDE USING gist` 排除約束搭配 `tstzrange` 時段欄位，防止同一球場的預約時段重疊；後端在單一交易中寫入預約。
```

techstack.md 片段：

```markdown
| 後端 | 執行環境 | Python 3.12 以上 | research §1 |
| 後端 | HTTP API | FastAPI、Uvicorn | research §1 |
| 資料儲存 | 預約與球場資料 | PostgreSQL 16、`psycopg` 3 | research §1、§2 |
```

## Bad Example

- 同一份 research.md，FastAPI 與 Uvicorn 拆成兩列；PostgreSQL 依主題拆成兩列；平台內建的 `zoneinfo` 與設計方式 `tstzrange` 各列一列。

```markdown
| 後端 | 執行環境 | Python 3.12 以上 | research §1 |
| 後端 | HTTP API | FastAPI | research §1 |
| 後端 | ASGI 伺服器 | Uvicorn | research §1 |
| 後端 | 時區轉換 | `zoneinfo` | research §1 |
| 資料儲存 | 預約與球場資料 | PostgreSQL 16、`psycopg` 3 | research §1 |
| 資料儲存 | 時段重疊約束 | PostgreSQL 16 | research §2 |
| 資料儲存 | 時段欄位 | `tstzrange` | research §2 |
```

# Rule 2 - 角色與版本只寫事實

- 角色欄必須只寫該列在系統中負責的部分。
- 角色欄不得寫採用理由，不得引用 FR／SC 編號，也不得出現「以符合」、「因為」等理由句。
- 角色欄不得描述各技術在什麼時候使用或如何分工。
- 版本必須寫在採用技術格的技術名稱之後，只寫 research.md 明確指定的版本或版本下限，並照 research.md 的寫法。
- research.md 沒有指定版本時，不得寫版本，也不得依查證結果或自行判斷補上版本。

## Good Example

- research.md 只指定了「Python 3.12 以上」、「PostgreSQL 16」與「`psycopg` 3」；這三項照原寫法接在名稱後，FastAPI 與 Uvicorn 沒有指定版本，只寫名稱；角色欄都只寫負責的部分。

```markdown
| 後端 | 執行環境 | Python 3.12 以上 | research §1 |
| 後端 | HTTP API | FastAPI、Uvicorn | research §1 |
| 資料儲存 | 預約與球場資料 | PostgreSQL 16、`psycopg` 3 | research §1、§2 |
```

## Bad Example

- 同一份 research.md，FastAPI 寫出 research 沒有指定的 `0.115`，Uvicorn 寫成 `—`；HTTP API 的角色欄描述兩個套件在什麼時候使用，資料庫的角色欄寫成理由並引用 FR-003。

```markdown
| 後端 | 執行環境 | Python 3.12 以上 | research §1 |
| 後端 | FastAPI 處理請求、Uvicorn 在部署時啟動服務 | FastAPI 0.115、Uvicorn — | research §1 |
| 資料儲存 | 以排除約束滿足 FR-003 的防重複預約 | PostgreSQL 16、`psycopg` 3 | research §1、§2 |
```

# Rule 3 - 分層依專案實際架構命名

- 分層名稱必須依本次專案實際具備的架構部分命名。
- 不得列出專案沒有的分層。
- 同一分層的列必須相鄰排列。

## Good Example

- 球場預約的每日對帳工具只是命令列程式，沒有畫面與 HTTP 伺服器；分層只有執行環境、命令列、資料儲存與品質與測試，兩個命令列的列相鄰。

```markdown
| 執行環境 | 命令列程式執行環境 | Python 3.12 以上 | research §1 |
| 命令列 | 指令與參數 | Typer | research §1 |
| 命令列 | 終端機報表輸出 | Rich | research §2 |
| 資料儲存 | 讀取當日預約紀錄 | PostgreSQL 16、`psycopg` 3 | research §3 |
| 品質與測試 | 單元測試 | pytest | research §4 |
```

## Bad Example

- 同一個對帳工具照抄 Web 專案的分層，列出專案沒有的「前端」與「後端」；兩個命令列的列被資料儲存隔開。

```markdown
| 執行環境 | 命令列程式執行環境 | Python 3.12 以上 | research §1 |
| 前端 | 無 | — | — |
| 後端 | 無 | — | — |
| 命令列 | 指令與參數 | Typer | research §1 |
| 資料儲存 | 讀取當日預約紀錄 | PostgreSQL 16、`psycopg` 3 | research §3 |
| 命令列 | 終端機報表輸出 | Rich | research §2 |
| 品質與測試 | 單元測試 | pytest | research §4 |
```

# Rule 4 - 不引入清單只列整類不用的技術類別

- 「本次開發不引入的技術」每一列必須是一個技術類別（例如前端框架、雲端儲存服務、ORM、訊息佇列），且「技術堆疊總覽」中沒有任何技術屬於該類別。
- 代表技術欄必須只列 research.md 中屬於該類別、被捨棄的具名技術，且每個都出自決策來源所指主題的 `Alternatives considered`。
- 決策來源欄必須以 `research §<主題編號>` 指向代表技術所在的主題，多個主題以「、」並列。
- 代表技術採用後會承擔總覽某一列的角色、取代該列的採用技術時（例如已採用 Vitest 時的 Jest、已採用 Caddy 時的 Nginx），屬於總覽已採用的同類技術，不論技術類別如何命名，都不得列入。
- 實作或寫法的取捨（例如分頁方式、欄位型別、排序演算法、資料格式、部署寫法）與自行撰寫同樣功能的替代方案不得列入。
- 不得寫不引入的原因、比較或替代方案的說明。
- 沒有可列的技術類別時，必須保留段落標題，並以一句「本次沒有整類不引入的技術。」取代表格。

## Good Example

### Example 1

- 球場預約系統的總覽已採用 FastAPI 與 PostgreSQL，沒有雲端資料庫服務與分散式鎖服務；清單只列這兩類。Django 與 FastAPI 同屬 Web 框架，「應用層先查詢再寫入」是實作取捨，時段比對函式是自行撰寫，都不列；表格不寫原因。

research.md 片段：

```markdown
## 1. 後端與資料庫
- **Alternatives considered**:
  - **Django**：內建管理後台與 ORM，但本次只需要 JSON API，額外的功能用不到。
  - **Firebase Realtime Database**：屬於雲端服務，違反使用者「不要用雲端服務」的限制。

## 2. 預約衝突防止
- **Alternatives considered**:
  - **Redis 分散式鎖**：需要多部署一個服務，且鎖逾時時仍可能重複預約，違反 FR-003。
  - **應用層先查詢再寫入**：兩個請求同時通過查詢時會重複預約，違反 FR-003。
  - **自行撰寫時段比對函式**：與先查詢再寫入有相同的競態問題，違反 FR-003。
```

techstack.md 片段：

```markdown
| 技術類別 | 代表技術 | 決策來源 |
| -------- | -------- | -------- |
| 雲端資料庫服務 | Firebase Realtime Database | research §1 |
| 分散式鎖服務 | Redis | research §2 |
```

### Example 2

- 每日對帳工具的總覽已採用 Typer，research.md 只捨棄了同類的 Click 與自行解析 `sys.argv`；沒有可列的技術類別，段落保留標題，以一句話取代表格。

research.md 片段：

```markdown
## 1. 命令列介面
- **Alternatives considered**:
  - **Click**：功能相近，但 Typer 以型別註記宣告參數，程式碼較少。
  - **自行解析 `sys.argv`**：子指令與說明文字都要自己處理，維護成本高。
```

techstack.md 片段：

```markdown
## 本次開發不引入的技術

本次沒有整類不引入的技術。
```

## Bad Example

### Example 1

- 同一份球場預約 research.md，清單列入總覽已有同類技術的 Django 與實作取捨「應用層先查詢再寫入」，並在代表技術後加上不引入的原因。

```markdown
| 技術類別 | 代表技術 | 決策來源 |
| -------- | -------- | -------- |
| Web 框架 | Django（只需要 JSON API） | research §1 |
| 雲端資料庫服務 | Firebase Realtime Database（違反不用雲端服務的限制） | research §1 |
| 預約寫入方式 | 應用層先查詢再寫入 | research §2 |
```

### Example 2

- 同一個每日對帳工具，沒有可列的技術類別時留下只有表頭的空表格。

```markdown
## 本次開發不引入的技術

| 技術類別 | 代表技術 | 決策來源 |
| -------- | -------- | -------- |
```

### Example 3

- 球場預約系統的總覽有「部署｜反向代理與 HTTPS｜Caddy 2」；Nginx 採用後會接手同一個角色、取代 Caddy，清單卻把它改稱「網頁伺服器」列入，類別名稱與總覽的角色對不上，看起來像整類不用。

research.md 片段：

```markdown
## 3. 部署與加密連線
- **Decision**: 以 **Caddy 2** 作為唯一對外入口，自動申請與續期 HTTPS 憑證，並把 `/api` 轉給 FastAPI。
- **Alternatives considered**:
  - **Nginx 搭配 Certbot**：要多一個憑證容器或排程來續期憑證，Caddy 一個服務就能處理。
```

techstack.md 片段：

```markdown
| 技術類別 | 代表技術 | 決策來源 |
| -------- | -------- | -------- |
| 網頁伺服器 | Nginx | research §3 |
```
