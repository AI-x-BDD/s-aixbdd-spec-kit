# Rule 1 - Decision 必須是單一確定、符合使用者限制與 spec 必須規則的方案

- 每個主題的 `Decision` 必須只採用一個方案；同一個需求點不得以「或」、「／」或括號並列兩個以上尚未決定的方案。
- 列舉同時採用的多個元件（例如「A 搭配 B」），或列舉不採用的項目（例如「不引入 X 或 Y」），不屬於並列未決方案。
- `Decision` 必須寫出採用的套件、API、資料結構或端點名稱，不得只寫方向，例如「使用適合的快取機制」。
- `Decision` 不得違反使用者在輸入中提出的技術限制。
- 使用者限制的字面有多種解讀，且 `Decision` 依其中一種解讀採用方案時，必須在 `Rationale` 寫出所採用的解讀。
- `Decision` 不得在任何適用情境下違反目標 spec 的必須／不得規則。比對前，必須列出「受影響的必須規則」：目標 spec 中，和 `Decision` 涉及同一個操作、狀態、實體或資料的 FR、NFR、SC、驗收情境、Edge Cases 與 Key Entities 的結構約束，以及 `Rationale` 寫為「滿足」的條目；不限本主題在「主題清單」列出的編號。
- 每條受影響的必須規則，必須列出 `Decision` 適用的情境：和其他操作同時發生、先後發生，以及需人工審核等分支。「其他操作」包括本次 spec 新增的操作，以及 spec 保留或沿用、會建立或改變該規則所依賴之狀態的既有操作；既有操作從既有 spec、程式與資料庫遷移找出。
- `Decision` 在任一情境下產生規則禁止的結果，或沒有產生規則要求的結果（包括規則指定的拒絕訊息與判斷順序），就是違反，必須改用能滿足規則的方案。
- 沒有候選方案能同時滿足受影響的必須規則，或要滿足規則必須先決定需求層面的問題（例如某個操作是否算規則的例外）時，不得自行決定，必須記為決策缺口，寫出規則的位置、衝突的情境，以及需要使用者決定的問題。
- 記為違反或決策缺口的每一項，必須指出目標 spec 中實際存在的條目；候選方案都滿足受影響的必須規則、只差在效能或維護等取捨時，不得記為規則衝突。

## Good Example

### Example 1

- 球場預約系統的「預約衝突」主題只採用一個方案，寫出具體的資料庫機制，且自架 PostgreSQL 符合使用者「不要用雲端服務」的限制。

```markdown
- **Decision**: 以 **PostgreSQL 16** 的 `EXCLUDE USING gist` 排除約束搭配 `tstzrange` 時段欄位，防止同一球場的預約時段重疊；後端以 **FastAPI** 在單一交易中寫入預約。
```

### Example 2

- 「停用球場的並發控制」主題列出受影響的必須規則與每個情境，包含上一個功能保留的會員報到；Decision 讓每個情境都滿足規則，並先比對預期狀態。

情境：

1. 目標 spec：
   - FR-005：管理員停用球場時，系統必須 (MUST) 取消該球場所有尚未開始的預約。
   - FR-006：球場有已報到的預約時，系統必須 (MUST) 拒絕停用。
   - FR-009：管理員送出時，球場狀態已被其他管理員變更（包含改成同一個狀態），系統必須 (MUST) 拒絕，並顯示「球場狀態已變更，請重新整理」。
   - FR-012：會員報到、候補遞補的現有行為保留不變。
2. 受影響的必須規則：FR-005、FR-006、FR-009。
3. 其他操作：新增預約、候補遞補（建立預約），會員報到（既有操作，把預約改成已報到）。
4. 情境：停用和新增預約同時；停用和候補遞補同時；停用和會員報到同時；另一位管理員先停用了同一個球場。
5. Decision：

```markdown
- **Decision**: 停用交易先以 `SELECT ... FOR UPDATE` 鎖定球場列，先比對送出時的預期狀態，不同就回 `COURT_STATUS_CHANGED`（FR-009 的訊息），再檢查已報到預約並取消尚未開始的預約；新增預約、候補遞補、會員報到都在各自交易開頭以 `SELECT ... FOR SHARE` 鎖定同一個球場列。
```

### Example 3

- 「demo seed 重設」主題沒有候選方案能同時滿足兩條必須規則，記為決策缺口，交給使用者決定。

情境：

1. 目標 spec：
   - FR-010：球場狀態變更紀錄不得 (MUST NOT) 刪除。
   - US2 驗收情境 4：執行 demo seed 後，資料回到初始狀態。
2. 候選方案：seed 以 `deleteMany` 清空後重建，會刪除紀錄，違反 FR-010；seed 只補資料不刪除，無法回到初始狀態，違反 US2 情境 4。
3. 決策缺口：`FR-010 與 US2 情境 4：demo seed 重設時，清空紀錄違反 FR-010，保留紀錄無法回到初始狀態；需決定 demo seed 重設是否算 FR-010 的例外。`

### Example 4

- 「查詢快取」主題的兩個候選方案都滿足 FR-003 與 SC-002，只差在記憶體用量，依 Rule 1～3 決定，不記為規則衝突。

情境：

1. 候選方案：程序內 LRU 快取、Redis。兩者在每個情境都滿足 FR-003 與 SC-002。
2. Decision：採用程序內 LRU 快取，`Alternatives considered` 寫出 Redis 增加一個部署元件。
3. 決策缺口：無。

## Bad Example

### Example 1

- 同一主題以括號並列尚未決定的加鎖方案，又保留改用 Firebase 的選項；Firebase 是雲端服務，違反使用者「不要用雲端服務」的限制。

```markdown
- **Decision**: 預約衝突以 PostgreSQL 排除約束處理（或改在應用層加鎖檢查），資料庫視流量再決定是否改用 Firebase。
```

### Example 2

- 同 Good Example 2 的 spec，只比對本主題列出的 FR-005，沒有列出會員報到這個既有操作；判斷順序也和 FR-009 不符。

情境：

1. Decision：`停用交易以 SELECT ... FOR UPDATE 鎖定球場列，先判斷球場已停用時回 COURT_ALREADY_DISABLED，再比對預期狀態；只有新增預約以 FOR SHARE 鎖定球場列。`
2. Rationale：`單一交易滿足 FR-005、FR-006。`
3. 結果：會員報到在停用檢查之後提交時，球場停用後仍有已報到的預約，違反 FR-006；另一位管理員先停用同一個球場時，回的不是 FR-009 的訊息。

### Example 3

- 同 Good Example 3 的 spec，自行決定 seed 重設是 FR-010 的例外，沒有記為決策缺口。

```markdown
- **Decision**: demo seed 以 Prisma `deleteMany` 清空球場狀態變更紀錄後重建初始資料。
- **Rationale**:
  - demo seed 只在展示時使用，不受 FR-010 限制。
```

### Example 4

- 同 Good Example 4 的情境，把一般的效能取捨記為規則衝突；FR-003 與 SC-002 在任何情境下都沒有要求不同結果。

情境：

1. 決策缺口：`FR-003 與 SC-002 衝突：快取可能讓查詢結果延遲更新。`
2. spec 中 FR-003、SC-002 都沒有規定查詢結果的更新時效。

# Rule 2 - Rationale 的依據必須可追溯

- 每個主題的 `Rationale` 必須至少有一條引用下列任一依據：使用者輸入中的技術限制、目標 spec 中的 FR／SC 等編號、專案原則文件中的條目、經 `clarify` 由使用者確認的決定。
- 引用的 spec 編號必須存在於目標 spec。
- 引用使用者限制時，必須寫出使用者的原意，可以引用原話；不得改寫成使用者沒有提出的限制。
- `Decision` 依經 `clarify` 確認的決定採用方案時，`Rationale` 必須寫出該決定的內容。
- `Decision` 有 Rule 1 列出的受影響必須規則時，`Rationale` 必須寫出這些規則的編號，以及比對時考慮的其他操作，並標出哪些是既有操作。
- 依據的 spec 條目有量化目標（例如延遲、數量、檔案大小）時，`Rationale` 必須寫出本方案的預期數值並與該目標比較。
- `Rationale` 不得只寫沒有依據的優點，例如「效能較好」、「業界常用」、「較易維護」。

## Good Example

### Example 1

- 理由分別引用 spec 的 FR-003、使用者限制原話與 SC-002 的量化目標，寫出預期數值，並列出受影響的必須規則與比對的操作。

```markdown
- **Rationale**:
  - 排除約束在資料庫層保證同一球場時段不重疊，滿足 FR-003「同一時段不得重複預約」，兩個請求同時送達也不會重複預約。
  - 符合使用者「不要用雲端服務」的限制：PostgreSQL 與 API 伺服器部署在同一台主機。
  - SC-002 要求預約送出到確認 `< 1 秒`；單筆交易加上 gist 索引檢查，預估 `< 20ms`。
  - 受影響的必須規則：FR-003；比對的其他操作：新增預約、改期、候補遞補（既有操作）。
```

### Example 2

- Decision 依 `clarify` 的決定採用方案，Rationale 寫出決定的內容。

```markdown
- **Rationale**:
  - 使用者經 `clarify` 決定：demo seed 重設算 FR-010 的例外，只在開發環境執行；正式環境的紀錄不得刪除。
  - 受影響的必須規則：FR-010、US2 驗收情境 4；比對的其他操作：demo seed 重設、停用球場、恢復可用。
```

## Bad Example

### Example 1

- 同一主題的第一條理由只寫「業界常用」「效能較好」；第二條引用的 FR-012 不存在於目標 spec（目標 spec 只有 FR-001～FR-008）。

```markdown
- **Rationale**:
  - PostgreSQL 是業界常用的資料庫，效能較好。
  - 滿足 FR-012 的多館別預約需求。
```

### Example 2

- 同 Good Example 2 的決策，Rationale 只寫結論，沒有寫出使用者的決定，也沒有列出受影響的必須規則與比對的操作。

```markdown
- **Rationale**:
  - demo seed 以 `deleteMany` 重設，流程最簡單。
```

# Rule 3 - Alternatives considered 必須寫出方案名稱與具體捨棄原因

- 每個主題的 `Alternatives considered` 必須至少有一條。
- 每條必須以 `**<方案名稱>**：<捨棄原因>` 撰寫。
- 捨棄原因必須引用 Rule 2 所列的同類依據或查證到的套件限制，或指出與採用方案相比的具體缺點；不得只寫「不適合」、「比較複雜」。
- 「主題清單」中該主題的候選方案，凡未被 `Decision` 採用，都必須列入 `Alternatives considered`。

## Good Example

- 主題清單列了三個候選方案，未採用的兩個都列入，每條都有粗體名稱，並以 FR-003、SC-002 或使用者限制說明捨棄原因。

```markdown
- **Alternatives considered**:
  - **應用層先查詢再寫入**：兩個請求同時通過查詢時會重複預約，違反 FR-003；改加表級鎖可避免重複，但尖峰時段的排隊會拉長 SC-002 的確認時間。
  - **Firebase Realtime Database**：屬雲端服務，違反使用者「不要用雲端服務」的限制。
```

## Bad Example

- 同一主題只列一條，方案名稱沒有粗體，捨棄原因只寫「比較不適合」；主題清單中的 Firebase 候選方案沒有列入。

```markdown
- **Alternatives considered**:
  - 應用層檢查：比較不適合。
```
