# Rule 1 - 篇幅與操作內容依逐字稿決定

- 文章篇幅必須是 500～600 字或 2,000～3,000 字其中一個範圍，依素材量與需要的解說決定。
- 不得為了湊字數而增加逐字稿沒有的內容。
- 逐字稿含操作步驟或可執行提示詞時，文章必須納入；提示詞必須寫明輸入、預期結果與核對方式。
- 逐字稿只講概念時，文章不得加入操作步驟、練習或提示詞。

## Good Example

- 素材只講概念，規劃成 600 字內的概念短文，沒有步驟、練習與提示詞。

情境：

1. 逐字稿：講師用兩段話說明 Git 分支是指向某個提交的可移動標籤，沒有任何操作示範。
2. 規劃：篇幅 500～600 字，只解說分支的定義與講師的比喻。
3. 規劃不含步驟、練習與提示詞。

## Bad Example

- 同一份只講概念的素材，被規劃成含「動手練習」的 1,200 字文章；篇幅不在兩個範圍內，練習也不在逐字稿中。

情境：

1. 逐字稿：同上，沒有操作示範。
2. 規劃：1,200 字，並加入「動手練習：建立三個分支並合併」。

# Rule 2 - 關鍵字與標題承接課程所回答的問題

- 關鍵字候選必須是 1～3 個，從收穫清單推導，每個必須標示搜尋意圖類型，例如資訊型、比較型或操作型。
- 未查證的關鍵字不得寫搜尋量；搜尋量只有在附來源、適用市場與期間時才可以寫。
- 標題與開頭必須直接承接課程所回答的問題。
- 開頭不得使用逐字稿以外的讀者案例或產品情境。

## Good Example

- 標題與開頭直接承接課程回答的問題，關鍵字標示意圖類型，未查證者不寫搜尋量。

情境：

1. 逐字稿回答「Git 分支是什麼」。
2. 標題：「Git 分支是什麼？一個指向提交的可移動標籤」。
3. 關鍵字：「git 分支是什麼」，資訊型，未查證，沒有搜尋量。

## Bad Example

- 開頭用逐字稿沒有的產品情境，關鍵字沒有查證卻寫了搜尋量。

情境：

1. 逐字稿回答「Git 分支是什麼」。
2. 開頭：「你的團隊用某自動化工具部署時，是否遇過合併衝突？」
3. 關鍵字：「git 分支」，月搜尋量 8,100，未查證，沒有來源。
