# Rule 1 - 決策必須寫回最適合的段落

- 每項決策必須依類型寫入下表對應的 spec 段落；一項決策影響多個類型時，必須寫入每個對應段落。

| 決策類型 | 寫入段落 |
| -------- | -------- |
| 功能行為 | 所屬使用者故事的 FR；跨故事時寫入 Global Requirements 的 FR |
| 角色或流程 | 使用者故事敘述與驗收情境 |
| 資料、狀態或識別規則 | Key Entities |
| 非功能品質 | NFR；決策把模糊形容詞改成門檻時，同時寫入 Success Criteria 的可量測門檻 |
| 邊界或錯誤處理 | Edge Cases |
| 範圍排除 | Out of Scope，來源標「使用者決定」 |

- 決策不得只寫在 `## Clarifications`，而沒有寫入上表的段落。
- 寫入的內容必須是可測試的最小敘述，不得加入使用者沒有決定的行為。

## Good Example

- 「候補名額自動遞補」屬於功能行為，寫入預約故事的 FR；「不支援團體課程」屬於範圍排除，寫入 Out of Scope 並標來源。

情境：

1. 決策一：課程額滿後，有人取消時由候補第一順位自動遞補。
2. 寫入：User Story 2 的 Functional Requirements 新增 `**FR-007**: 系統必須 (MUST) 在已預約會員取消時，自動把名額遞補給候補第一順位的會員。`
3. 決策二：第一版不提供團體課程預約。
4. 寫入：Out of Scope 新增 `**團體課程預約**（使用者決定）：第一版只提供一對一課程預約。`

## Bad Example

- 兩項決策只記在 Clarifications，FR 與 Out of Scope 都沒有更新；遞補敘述又加入使用者沒有決定的通知方式。

情境：

1. 決策一：課程額滿後，有人取消時由候補第一順位自動遞補。
2. 寫入：只在 Clarifications 新增 `- Q: 額滿後如何處理取消名額? (FR-007) → A: 候補第一順位自動遞補，並以簡訊通知。`
3. 決策二：第一版不提供團體課程預約。
4. 寫入：沒有更新 Out of Scope。

# Rule 2 - 新決策必須取代矛盾的舊敘述

- 被決策推翻的舊敘述必須改寫或刪除，不得與新敘述並列。
- 寫入每項決策後，必須找出 spec 中與決策涉及同一個操作、狀態或實體的 FR、NFR、驗收情境、Edge Cases、Success Criteria 與 Assumptions，逐條和決策比對。
- 比對時，必須列出決策適用的每個情境，包括決策涉及的操作和其他操作同時發生或先後發生的順序；舊敘述在任一情境要求的結果和決策不同時，就是矛盾，即使兩者沒有共用的數值或字句。
- 只從決策就能推出一致寫法的矛盾，必須改寫或刪除舊敘述；寫入後，spec 中不得留下這類矛盾。
- 一致寫法需要使用者新的決定時（例如有多種一致寫法，或要決定驗收標準在哪個時間點量測），不得自行選擇，必須保留舊敘述原文，記為「待決定矛盾」，寫出決策與舊敘述的位置，以及兩者矛盾的情境。
- 使用者確認了 Assumptions 中標為（推定）的需求或門檻時，必須刪除該條推定引用。
- 使用者確認了 Out of Scope 中標為（推定）的排除項時，必須把來源改標「使用者決定」。

## Good Example

### Example 1

- 決策改成「開課前 2 小時內不可取消」，原本 24 小時的敘述在 FR 與 Edge Cases 都改寫；FR-004 的推定引用因使用者確認而刪除。

情境：

1. 原 FR-004：`系統必須 (MUST) 允許會員在開課 24 小時前取消預約。`
2. 原 Edge Cases：`**臨時取消**：開課前 24 小時內取消時，系統拒絕取消。`
3. 原 Assumptions：`**開課 24 小時前可取消**（推定）：見 FR-004。`
4. 決策：開課前 2 小時內不可取消，其餘時間都可以取消。
5. 寫入後 FR-004：`系統必須 (MUST) 允許會員在開課 2 小時前取消預約。`
6. 寫入後 Edge Cases：`**臨時取消**：開課前 2 小時內取消時，系統拒絕取消。`
7. 寫入後 Assumptions：刪除「開課 24 小時前可取消」這條推定引用。

### Example 2

- 決策和 SC-002 沒有共用的數值或字句，但在「名單鎖定後才有人取消」的先後情境下要求不同結果；一致寫法可以直接從決策推出，所以改寫 FR-005 與 SC-002。

情境：

1. 原 FR-005：`會員取消預約時，系統必須 (MUST) 立即釋出名額，遞補給候補第一順位。`
2. 原 SC-002：`額滿課程有人取消後，候補第一順位在 1 分鐘內收到遞補結果。`
3. 決策：管理員在開課前 1 天鎖定名單；鎖定後有人取消時，名額不釋出也不遞補。
4. 比對：涉及「取消預約」與「遞補」的敘述有 FR-005、SC-002。情境「名單鎖定前取消」兩者一致；情境「名單鎖定後取消」FR-005 與 SC-002 都要求遞補，決策要求不遞補，兩處都是矛盾。
5. 寫入後 FR-005：`名單鎖定前有會員取消預約時，系統必須 (MUST) 立即釋出名額，遞補給候補第一順位。`
6. 寫入後 SC-002：`名單鎖定前，額滿課程有人取消後，候補第一順位在 1 分鐘內收到遞補結果。`

### Example 3

- 一致寫法有兩種，要使用者決定 SC-003 在哪個時間點量測，所以保留舊敘述並記為「待決定矛盾」。

情境：

1. 原 SC-003：`被取消的名額 100% 在開課前遞補完成。`
2. 決策：候補會員收到遞補通知後有 30 分鐘確認，逾時改通知下一位。
3. 比對：情境「開課前 30 分鐘內有人取消，候補會員沒有在開課前確認」時，名額在開課前沒有遞補完成，和 SC-003 矛盾。
4. 一致寫法有兩種：只計算開課前 30 分鐘以前的取消，或把「遞補完成」改成「遞補通知已送出」。兩種都改變驗收標準，要使用者決定。
5. 寫入後 SC-003：保留原文。
6. 待決定矛盾：`SC-003 與 FR-008（30 分鐘確認）：開課前 30 分鐘內取消且候補沒有確認時，名額無法在開課前遞補完成；需決定 SC-003 的計算範圍或「遞補完成」的定義。`

## Bad Example

### Example 1

- 新決策加在 FR-004 後面，舊的 24 小時敘述仍留在 Edge Cases 與 Assumptions，讀者看到兩個互相矛盾的期限。

情境：

1. 寫入後 FR-004：`系統必須 (MUST) 允許會員在開課 24 小時前取消預約；依澄清結果，改為 2 小時前。`
2. 寫入後 Edge Cases：`**臨時取消**：開課前 24 小時內取消時，系統拒絕取消。`
3. 寫入後 Assumptions：仍保留 `**開課 24 小時前可取消**（推定）：見 FR-004。`

### Example 2

- 同 Good Example 2 的決策，只搜尋決策中出現的字句，沒有比對先後情境，FR-005 與 SC-002 仍要求鎖定後也遞補。

情境：

1. 新增 FR-012：`管理員鎖定名單後有人取消時，系統必須 (MUST) 不釋出名額，也不遞補。`
2. 檢查：搜尋「鎖定」，只找到 FR-012，判定沒有矛盾。
3. 寫入後 FR-005、SC-002：保留原文。

### Example 3

- 同 Good Example 3 的決策，自行把 SC-003 改成「遞補通知已送出」，替使用者決定了驗收標準，也沒有記為待決定矛盾。

情境：

1. 寫入後 SC-003：`被取消的名額 100% 在開課前送出遞補通知。`
2. 待決定矛盾：無。

# Rule 3 - 同一概念必須使用同一術語

- 決策確定某個概念的名稱，或掃描發現同一概念使用多個名稱時，全份 spec 必須改用同一個術語。
- 需要保留舊稱時，只能在新術語第一次出現處加一次「（原稱「X」）」，其他位置不得再使用舊稱。

## Good Example

- 決策確定使用「會員」，全份 spec 改用同一術語，只在第一次出現處保留舊稱。

情境：

1. 原 spec：User Story 1 使用「學員」，FR-003 使用「會員」，Key Entities 使用「用戶」。
2. 決策：統一稱為「會員」。
3. 寫入後：User Story 1 寫「會員（原稱「學員」）可以查看本週課表」，FR-003 與 Key Entities 都寫「會員」。

## Bad Example

- 只改了提問涉及的 FR-003，其他段落仍混用三個名稱。

情境：

1. 原 spec：User Story 1 使用「學員」，FR-003 使用「會員」，Key Entities 使用「用戶」。
2. 決策：統一稱為「會員」。
3. 寫入後：FR-003 寫「會員」，User Story 1 仍寫「學員」，Key Entities 仍寫「用戶」。

# Rule 4 - Clarifications 必須逐題記錄並標註受影響的位置

- 當日的 `### Session YYYY-MM-DD` 不存在時，必須在 `## Clarifications` 下新增；已存在時，必須接在該 Session 的最後一條後面。
- 既有的其他日期 Session 必須保留原文。
- 每個已回答的問題必須恰好有一條 `- Q: <問題> (<標註>) → A: <最終答案>`；同一題不得重複記錄，沒有回答的問題不得記錄。
- `<標註>` 必須優先列出受影響的 FR 或 NFR 編號；決策沒有影響任何 FR 或 NFR 時，必須改列受影響的 SC 編號或段落名稱（例如 `Out of Scope`）。這是 s-specify `spec-文件-格式規範` Rule 2 只允許標註 FR 或 NFR 的例外。
- `A:` 後面必須寫寫回 spec 的最終決策，不得寫選項編號。

## Good Example

- 新紀錄接在當日 Session，舊 Session 保留；沒有影響 FR／NFR 的決策標註段落名稱，答案寫成最終決策。

```markdown
## Clarifications

### Session 2026-10-30

- Q: 會員可以同時預約幾堂課? (FR-002) → A: 同時最多預約 3 堂未開始的課程。

### Session 2026-11-03

- Q: 額滿後有人取消時，名額如何處理? (FR-007) → A: 由候補第一順位自動遞補。
- Q: 第一版是否提供團體課程預約? (Out of Scope) → A: 不提供，第一版只做一對一課程預約。
```

## Bad Example

- 舊 Session 被覆蓋，同一題記錄兩次，範圍排除的決策沒有標註，答案只寫選項編號。

```markdown
## Clarifications

### Session 2026-11-03

- Q: 額滿後有人取消時，名額如何處理? (FR-007) → A: 選項 1
- Q: 額滿後有人取消時，名額如何處理? (FR-007) → A: 由候補第一順位自動遞補。
- Q: 第一版是否提供團體課程預約? → A: 不提供。
```
