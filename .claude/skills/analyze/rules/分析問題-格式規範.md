# Rule 1 - 問題必須歸入固定類別並使用類別字母加流水號作為 ID

- 每個問題必須歸入下列六個類別之一，同一個問題不得拆成多筆，也不得同時列在兩個類別。
- A 重複：兩處文字描述同一件事。
- B 歧義：模糊形容詞沒有量化標準，或出現 `{{`、`TODO`、`TBD`、`TKTK`、`???` 等佔位符號。
- C 不足：需求缺少對象或可量測結果，或任務引用 spec 與 plan 沒有定義的元件。
- D 憲法：違反 `.agents/constitution/` 的規則。
- E 涵蓋：需求沒有任務、介面沒有 Planner 或 `notification-plan` 產出或沒有任務，或需要建置的 SC 沒有任務。
- F 不一致：同一概念在不同文件的命名或值不同、同一情境的行為說法不同、合約的錯誤碼在 `ui/plan.md` 沒有對應的回饋，或 spec 與 plan 的技術或資料實體互相矛盾；包括 `contracts/`、`data/`、`ui/`、`notification/` 之間的差異。命名不同但可以一一對應時仍必須列為 F。
- ID 必須是類別字母加從 1 開始的流水號，例如 `F2`；同一類別的流水號必須連續。

## Good Example

- 合約把訂單狀態寫成 `PAID`、`FAILED`，資料表寫成 `paid`、`payment_failed`，兩者可以一一對應，仍列為一筆 F 類問題，只寫一筆而不是每個值各一筆。

| ID | 類別 | 摘要 |
| --- | --- | --- |
| F2 | 不一致 | `OrderStatus` 的值與 `order_status` 的值命名不同，可以一一對應 |

## Bad Example

- 命名可以一一對應就不列問題，並把同一件事拆成兩筆、分別歸入 A 與 F。

| ID | 類別 | 摘要 |
| --- | --- | --- |
| A1 | 重複 | `PAID` 與 `paid` 重複 |
| F1 | 不一致 | `FAILED` 與 `payment_failed` 不一致 |

# Rule 2 - 位置必須指向可搜尋的識別字

- 每個位置必須寫成 `` `檔案` → 識別字 ``，識別字必須能用 `grep -n` 在該檔案找到。
- 識別字可以是 operationId、schema 名稱、`Table`／`Enum` 名稱、§ 編號、FR／NFR／SC 編號，或表格中的畫面與狀態名稱。
- F 類問題的位置必須至少列出兩個不同的文件。
- 位置不得只指向 `tasks.md` 的 Notes；問題已寫在 `tasks.md` Notes「待確認 n」時，位置仍必須指向造成問題的上游文件，且摘要必須以「已記錄：tasks.md 待確認 n」開頭。

## Good Example

- 付款被拒的錯誤碼在合約有、在 UI 規劃沒有，位置列出兩個文件的識別字，摘要標出已記錄的待確認。

| 位置 | 摘要 |
| --- | --- |
| `contracts/openapi.yaml` → `payOrder` 的 `PAYMENT_DECLINED`；`ui/plan.md` → §5 | 已記錄：tasks.md 待確認 1。`PAYMENT_DECLINED` 在 `ui/plan.md` §5 沒有對應的畫面回饋 |

## Bad Example

- 位置只寫 `tasks.md` 待確認 1，沒有指出上游文件與識別字，也不能 grep 驗證。

| 位置 | 摘要 |
| --- | --- |
| `tasks.md` → 待確認 1 | 付款被拒的處理有問題 |

# Rule 3 - 憲法遵循必須逐份憲法檔、逐條 Rule 對照產出物

- 每份憲法檔的每條 Rule 都必須在「憲法遵循」記一筆結果，結果只能是「通過」、「違反」、「不適用」或「不套用（鎖定項目）」。
- 憲法檔對應的產出物如下：`shared.md` 依其 Rule 寫明的範圍；`skills/s-specify/spec.md` 對應 `spec.md`；`skills/technical-research/research.md`、`techstack.md` 對應同名文件；`skills/system-analysis/plan.md` 對應 `plan.md`；`skills/api-plan/openapi.md`、`asyncapi.md` 對應 `contracts/` 的同名合約；`skills/data-plan/data-model.md` 對應 `data/data-model.dbml`；`skills/ui-plan/ui-plan.md` 對應 `ui/plan.md`，`ui-page.md` 對應 `ui/*.html`；`skills/notification-plan/notification-plan.md` 對應 `notification/plan.md`；`skills/tasks/tasks.md` 對應 `tasks.md`。
- `skills/implement/code.md` 約束程式碼，不在分析範圍，結果必須寫「不適用」。
- Rule 中的例外成立時，不得列為違反。
- Rule 要求改變對應 Skill 的鎖定項目時，不得列為違反，結果必須寫「不套用（鎖定項目）」。
- 產出物早於憲法時，仍必須照常對照。
- 結果為「違反」的 Rule 必須對應一筆 D 類問題，並在「問題 ID」欄寫出該問題的 ID。

## Good Example

- `api-plan` 的鎖定項目是 operation 的 `tags` 以介面編號開頭；憲法 Rule 2 要求 `tags` 使用資源名稱，改變了鎖定項目，所以結果寫「不套用（鎖定項目）」，不列問題。

| 憲法檔 | Rule | 結果 | 問題 ID |
| --- | --- | --- | --- |
| `skills/api-plan/openapi.md` | Rule 2 每個 operation 的 `tags` 必須使用資源名稱，例如 `cart` | 不套用（鎖定項目） | — |

## Bad Example

- 把鎖定項目與憲法 Rule 的衝突列為違反，並建立 CRITICAL 問題，要求合約改掉介面編號。

| 憲法檔 | Rule | 結果 | 問題 ID |
| --- | --- | --- | --- |
| `skills/api-plan/openapi.md` | Rule 2 每個 operation 的 `tags` 必須使用資源名稱，例如 `cart` | 違反 | D1 |

# Rule 4 - 嚴重度必須依影響分為四級

- CRITICAL：違反「必須」或「不得」規則、缺少核心文件，或 P1 User Story 的需求沒有任何任務。
- HIGH：上游文件互相矛盾且會讓實作做出不同行為、需求互相衝突，或驗收標準無法測試。
- MEDIUM：命名不同但可以一一對應、違反「應」規則、缺少非功能需求的任務，或邊界情況說明不足。
- LOW：文字與輕微重複。
- 一個問題符合多個等級時，必須採用最高的等級。
- 命名不同但可以一一對應時，不得列為 HIGH。

## Good Example

- 資料表缺少 `updated_at`，違反憲法的「必須」規則，列為 CRITICAL；合約與資料表的狀態值只是大小寫不同、可以一一對應，列為 MEDIUM。

| ID | 嚴重度 | 摘要 |
| --- | --- | --- |
| D1 | CRITICAL | `orders` 沒有 `updated_at`，違反 Rule 1「必須」 |
| F2 | MEDIUM | `PAID` 與 `paid` 可以一一對應，只有命名不同 |

## Bad Example

- 把可以一一對應的命名差異列為 HIGH，並把違反「必須」的規則降為 MEDIUM。

| ID | 嚴重度 | 摘要 |
| --- | --- | --- |
| D1 | MEDIUM | `orders` 沒有 `updated_at`，違反 Rule 1「必須」 |
| F2 | HIGH | `PAID` 與 `paid` 可以一一對應，只有命名不同 |

# Rule 5 - 每個問題必須有具體建議與處理 Skill

- 建議必須寫出要修改哪個文件的哪個部位，以及往哪個方向修改；只寫「請修正」之類沒有文件、部位與方向的建議不得使用。
- 處理 Skill 必須填產出該文件的 Skill：`spec.md` 填 `s-specify` 或 `clarify-over-specs`；`research.md`、`techstack.md` 填 `technical-research`；`plan.md` 填 `system-analysis`；`contracts/` 填 `api-plan`；`data/` 填 `data-plan`；`ui/` 填 `ui-plan`；`notification/` 填 `notification-plan`；`tasks.md` 填 `tasks`；需要修改憲法時填 `constitution`。
- 端點類型不是前端、後端、資料庫，且負責通知的介面沒有任何規劃產出時，處理 Skill 必須填 `notification-plan`。
- 問題涉及多個文件而無法判斷以哪一方為準時，處理 Skill 必須寫「需要使用者決定」，並列出候選的 Skill。
- 「下一步」在有 CRITICAL 問題時，必須寫明 `implement` 前先處理這些問題；只有 HIGH 以下的問題時，必須寫可以繼續，並列出建議先處理的問題。

## Good Example

- 折扣碼次數的規定在 `spec.md` 與合約互相矛盾，無法判斷以哪一方為準，寫「需要使用者決定」並列出兩個候選；下一步因為有 CRITICAL 問題而要求先處理。

| 建議 | 處理 Skill |
| --- | --- |
| 以 FR-005 為準時，改 `contracts/openapi.yaml` 的 `applyDiscount` 並新增已使用的錯誤碼；以合約為準時，改 `spec.md` 的 FR-005 | 需要使用者決定（候選：`api-plan`、`s-specify`） |

- 下一步：有 CRITICAL 問題，`implement` 前先處理 D1。

## Bad Example

- 建議只寫「請修正」，處理 Skill 填寫整個流程的入口而不是產出該文件的 Skill；有 CRITICAL 問題時下一步卻寫可以繼續。

| 建議 | 處理 Skill |
| --- | --- |
| 請修正 | `analyze` |

- 下一步：可以繼續 `implement`。
