# Rule 1 - 介面必須從需求部位切出並歸類端點類型

- 盤點時必須逐一檢視目標 spec 的 User Story 情境、FR、NFR、SC、Edge Cases 與 Key Entities。
- 描述同一組使用者操作或系統職責的需求，必須歸成一個需求部位。
- 每個需求部位必須依實際負責的技術端點類型各列一個介面；一個需求部位涉及多個端點類型時，每個端點類型各列一個介面。
- 端點類型包含前端、後端、資料庫、手機、硬體與雲端第三方（例如金流、通知服務）；需求涉及其他技術端點時，也必須列為一個端點類型。
- 不得列出需求沒有涉及的端點類型。
- 介面名稱必須指出需求部位，不得只寫端點名稱（例如只寫「前端」或「後端 API」）。
- 端點類型欄必須寫成「<端點類型>（<這個端點的使用者> → <這個端點>）」；箭頭右側可以寫端點類型，或技術研究採用的具體產品名稱，例如「後端（前端 → 後端）」、「資料庫（後端 → MySQL）」、「金流（後端 → Stripe）」。

## Good Example

- 線上課程訂閱的 spec 有 US1 瀏覽與試看課程、US2 訂閱並付款，付款使用 Stripe。每個需求部位依負責的端點類型各列一個介面，「訂閱並付款」涉及前端、後端、資料庫與金流，因此四種端點類型各有一列；介面名稱都指出需求部位，端點類型欄寫出使用關係。

| 編號 | 介面 | 端點類型 |
| --- | --- | --- |
| F1 | 課程目錄與試看介面 | 前端（使用者 → 前端） |
| F2 | 訂閱方案選擇與結帳介面 | 前端（使用者 → 前端） |
| B1 | 課程查詢 API | 後端（前端 → 後端） |
| B2 | 訂閱建立 API | 後端（前端 → 後端） |
| B3 | 付款結果通知 API | 後端（Stripe → 後端） |
| D1 | 課程與訂閱資料存取 | 資料庫（後端 → MySQL） |
| P1 | Stripe 結帳與付款事件串接 | 金流（後端 → Stripe） |

## Bad Example

- 同一份 spec，只列出端點名稱，看不出各介面對應哪個需求部位；付款明確使用 Stripe，金流端點卻沒有列出；端點類型欄也沒有使用關係。

| 編號 | 介面 | 端點類型 |
| --- | --- | --- |
| F1 | 前端 | 前端 |
| B1 | 後端 API | 後端 |
| D1 | 資料庫 | 資料庫 |

# Rule 2 - 需求依據必須可追溯並涵蓋所有 User Story

- 每一列的需求依據必須引用目標 spec 中存在的 User Story 情境、FR、NFR、SC 編號，或 Edge Cases、Key Entities 中的項目名稱。
- 每個引用的編號之後必須接一句摘要，說明該項需求與這個介面相關的內容。
- 目標 spec 的每個 User Story 必須至少被一列的需求依據引用。
- 不得引用目標 spec 中不存在的編號或項目，也不得只寫「依需求」或「參見 spec」等無法追溯的依據。

## Good Example

- 同一份線上課程訂閱 spec（US1–US2、FR-001–FR-006、NFR-001、SC-001–SC-002，Key Entities 有課程與訂閱）。每列都引用存在的編號或項目並附摘要，US1 與 US2 都至少被引用一次。

| 編號 | 介面 | 需求依據 |
| --- | --- | --- |
| F1 | 課程目錄與試看介面 | US1 情境 1–2；FR-001 依分類瀏覽課程；FR-002 未訂閱者可試看前 3 分鐘 |
| F2 | 訂閱方案選擇與結帳介面 | US2 情境 1；FR-003 月繳與年繳方案；SC-002 結帳流程 3 步內完成 |
| P1 | Stripe 結帳與付款事件串接 | US2 情境 2；FR-004 付款成功後立即開通；FR-005 付款失敗時通知使用者；NFR-001 付款結果 5 秒內反映到訂閱狀態 |
| D1 | 課程與訂閱資料存取 | Key Entities 課程、訂閱；FR-006 取消訂閱後保留觀看權限到到期日 |

## Bad Example

- 同一份 spec，F1 只寫「依需求」；F2 引用 spec 不存在的 FR-009；P1 的依據沒有摘要；整張表沒有任何一列引用 US1。

| 編號 | 介面 | 需求依據 |
| --- | --- | --- |
| F1 | 課程目錄與試看介面 | 依需求 |
| F2 | 訂閱方案選擇與結帳介面 | US2 情境 1；FR-009 |
| P1 | Stripe 結帳與付款事件串接 | FR-004、FR-005 |
