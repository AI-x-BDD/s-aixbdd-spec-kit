# Rule 1 - 工作位置與版本必須可追溯

- 工作位置必須採作者指定的output-root；未指定時使用宿主articles。新course-id及article-id必須用小寫kebab-case；既有目錄必須沿用，不搬動舊成果。同名目錄素材不同時必須另取名稱。
- 課程成果必須在output-root/courses/course-id下保存source、lessons/lesson-id/harvest、learning-index、decisions/scope-id及progress；文章成果必須在指定文章目錄保存idea、directions、outline、outline-review、稿件及progress。
- 採用版本必須以進度的明確採用紀錄及實際可讀檔案為依據，不得按最大檔號推定。成果已寫入但未登記時必須核對內容與依賴，未經核對不得標完成。
- 重跑或修訂成果必須選未使用的版本檔名，保留原成果；progress可以追加事件，來源更新亦須保留舊來源版本。
- 確認有效性必須同時核對展示版本、實際回覆、確認範圍及依賴版本。依賴改變時必須列出受影響成果與確認，未受影響的確認保持有效。
- 舊第8步接續必須保留原progress、07大綱與08清單及其確認，首次接續只建立索引／版本對照，不覆寫舊文。

## Good Example

- 自製情境保留可核對依據與限制。

- 進度採用outline-v2，雖另有未確認v3，仍使用v2；來源v2改了作者欄時，只列受該欄影響的段落及確認失效。

## Bad Example

- 相同情境遺漏依據或超出可支持的結論。

- 看到最大檔號v3便當作採用版，覆寫v2，並要求作者重做所有確認。

# Rule 2 - 執行依賴必須隨兩個Skill提供

- 必要執行依賴必須為同一skills-root的同版本lesson-prep-workflow與lesson-prep-writing及其rules／templates；不得回讀開發repo的docs、AGENTS、materials說明或工程報告取得執行規則。
- 素材與成果位置必須由本次工作輸入提供；已有可讀檔案必須直接讀取，不得要求作者重貼。
- 工具需求必須按分支列明：檔案讀寫agent；研究需已授權的搜尋／SERP及量來源；新角色檢查需隔離子代理；交付核對需shasum及來源有Git時的Git。缺項必須列具體受阻與取得方式。

## Good Example

- 自製情境保留可核對依據與限制。

- 兩目錄副本已齊，讀本次指定的書目資料；搜尋量工具未提供，列量資料待補。

## Bad Example

- 相同情境遺漏依據或超出可支持的結論。

- 第二站缺規則時偷偷讀開發repo的docs；要求作者重貼已可讀的書目檔。

# Rule 3 - 交付內容與來源必須可核對

- 候選payload必須包含兩個完整Skill及實際適用的來源聲明／許可文件；付費教材、第三方逐字背景貼文與既有文章不得自動打包。
- 每個payload檔必須有實際SHA-256及來源／權利依據；適用內容要求保留的原授權全文必須隨附，未知條件必須明列待補，不得推定開放授權。
- 來源必須保留原開發位置、Git commit（有Git時）、版本標籤及實際working-tree snapshot。存在未提交內容時不得只用HEAD識別。
- 兩份package-record必須一致，payload hash必須排除紀錄自身，以避免自我參照。
- 副本必須保留原來源及轉交站歷程，攜帶可獨立讀取的驗證摘要、實際結果與原紀錄定位；原repo不可讀時摘要仍可用。
- 更新版本的已驗證宣告必須有來源驗收依據；測試尚未完成時必須保留候選／未驗證狀態。

## Good Example

- 自製情境保留可核對依據與限制。

- 書目範例套件有commit與未提交snapshot hash，兩份紀錄一致；許可未明列待補，課程素材排除。

## Bad Example

- 相同情境遺漏依據或超出可支持的結論。

- 只填HEAD便聲稱包含未提交改動，將教材全包進去，並把未測套件標已驗證。
